Stratum Pre-release EMIT Critical Minerals L3

Status

What exists, what is specified, and what is still undecided. As of 2026-09-02.

The first slice is built

A local run exists end to end: stratum run -m manifest.yaml over granules on disk plans, regrids, resolves, reduces and publishes, with content-addressed caching, a STAC item and collection, and a provenance record. The same command over a kind: cmr source discovers granules in NASA's catalogue and downloads them over HTTPS on first touch into a checksum-verified asset cache. 282 tests pass and 3 live tests skip without STRATUM_LIVE=1 (pixi run test). The cloud and cluster paths, direct S3 access, STAC and Parquet sources, prepared assets and the approval gate are specified but not built; each refuses with its spec section named. The specs in docs/specs/ remain the contract, and the code is authoritative for signatures.

First implementation slice

Scope as agreed

One tile, one epoch, MinViewZenith, granules staged on local disk, output compared against an existing V002 cell. No blocks, caching, Step Functions, Batch or manifest patching.

Blocks and cache keys were built from the start after all, because the two non-negotiable tests — seam equivalence and cache-key sensitivity — need them; both pass. The build contract is docs/notes/2026-09-02-first-slice-plan.md (internal).

Validation target and result

The success criterion is parity: a streaming scorer over a single epoch with no reducer must reproduce the existing V002 output exactly. No V002 output for the pilot tile was available locally, so the first slice was validated against the next best thing — SpectralUtil's build_obs_nc fused mosaic over exactly the same grid, criterion and granules.

TrialResult
Tile (−118, 41), June 2026, 14 granules, one arcsecond, block_size: 720Plan through publish in 40 s on a laptop; a fully cached re-run in 11 s

Independent check, no shared code (per-granule KD-tree, nearest within max_distance, minimum zenith, earliest wins)3000 / 3000 sampled cells match
Seam equivalence and key sensitivityPass, in the suite

Parity against a real V002 cell is still owed once a V002 product for the tile is obtainable; the abstraction has passed the test that was available.

Planned enhancements

Deliberately deferred rather than undecided. Each has a shape in mind and a reason for waiting.

EnhancementWhy deferredCost of adding it later
Scorer-derived snapshot bands
Scorer.outputs + emit(), for bands the scorer computes rather than copies — runner-up margin, per-candidate evidence, broadcast timestamps		 Several motivating bands (source_granule, acquired, runner_up_score) are already known to the selection loop and may belong as framework built-ins instead, which would leave the plugin-facing form much smaller. Per-candidate evidence also needs a representation decision that is premature without a reducer that consumes it. Reprocessing. Snapshots are cached artifacts; a band that was never emitted cannot be recovered from them. Adding this invalidates and rebuilds resolve.
Classify-last reduction — aggregate per-candidate evidence across epochs, then classify the aggregate, instead of voting on labels Blocked on the row above: it is the main consumer of derived outputs. Same reprocessing cost. Voting on labels stays the v1 baseline.
Stack-level emitted bands — a stack-capability scorer emitting a property of the whole epoch (a within-epoch median) rather than of one observation Blurs the scorer/reducer split. Current rule is per-observation arrays only, gathered from the winner. Contract change, but additive.
tile capability — plugins needing a whole-tile view Nothing needs it yet. It is specified so the escape hatch exists, but building it before a real case would be speculative. Low — it routes to Batch and gives up block parallelism, which is already described.
Why this list exists

The rows differ in one important way: the first two cost a reprocessing pass if adopted after data exists, because they change what resolve writes. The others are additive. That distinction is worth weighing before the first production run, not after.

Beyond EMIT

The core is instrument-agnostic by requirement, not by aspiration — a second group is independently building the same kind of mosaic for a different instrument family, working toward cross-scale products from 60 m satellite imagery down to centimetre-scale UAV data. That is why input roles and band aliases resolve per collection rather than being hard-coded, and why nothing about minerals appears in the core package.
