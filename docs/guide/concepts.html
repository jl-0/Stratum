Concepts

The model you need to hold in your head to write a manifest or a plugin.

Grid

A grid is CRS, resolution and origin. It has no extent. It is a rule — cell edges fall at origin + n × resolution — which fixes where cell boundaries lie anywhere in the CRS's domain, without anyone having to say where the data is.

That is what makes tiles align. Tile bounds are derived from the grid, never from the extent of your granules, so two runs over the same ground at the same grid produce identical tile bounds and can share cached geometry. A grid that took its bounds from data would give every run subtly different tiles.

The crs field decides what the other numbers mean. Everything below it is expressed in that CRS's units — degrees for EPSG:4326, metres for most projected systems.

The mistake that bites

In EPSG:4326, resolution: 0.000277778 means that many degrees — one arcsecond, roughly 31 m at the equator. In a metre-based projected CRS the same number would mean 0.3 mm. Confusing the two is the most common configuration error in this system, which is why Stratum rejects the obvious cases below.

What is a CRS, and what does EPSG:4326 mean?

A pair of numbers like (-115.3, 37.5) means nothing on its own. A coordinate reference system — CRS, sometimes called a spatial reference system — says which point on Earth those numbers refer to: what shape the Earth is taken to be, where the origin sits, and what the units are.

KindCoordinates areUnitsExample
GeographicAngles on an ellipsoid — longitude and latitudeDegreesEPSG:4326 (WGS 84)
ProjectedDistances on a flat plane, after flattening the curved surfaceMetres, usuallyEPSG:32611 (UTM zone 11N)

EPSG codes are short numeric identifiers from a public registry of CRS definitions, maintained by the IOGP Geomatics Committee. EPSG:4326 is a compact, unambiguous way of saying "WGS 84 longitude/latitude in degrees" — the same system a GPS receiver reports. Geographic CRSs occupy the 4xxx range, which is what the guard rail below keys on.

One more consequence worth knowing: a cell in a geographic CRS is not a constant size on the ground. One arcsecond of longitude is about 31 m at the equator and about 22 m at 45° latitude. That is workable here because the source products are themselves distributed on a geographic grid, but it matters before you read a cell count as an area.

grid:
  # Which coordinate system the numbers below are in.
  # EPSG:4326 = WGS 84 lon/lat in degrees - the system GPS reports.
  crs: EPSG:4326

  # Cell size as [x_step, y_step], in the CRS's units - here, degrees.
  #   1/3600 deg, one arcsecond, is about 31 m at the equator, less toward the poles.
  #   y is NEGATIVE because raster rows run north to south, so moving
  #   one row down decreases latitude. Positive y is nearly always a
  #   mistake, and Stratum rejects it unless you force it.
  resolution: [0.000277778, -0.000277778]

  # The anchor cell edges are measured from: edges fall at
  #   origin + n * resolution. This fixes the grid's phase.
  #   Two runs sharing an origin produce cells that line up exactly;
  #   change it and nothing aligns with anything built before.
  #   [-180, -90] is the south-west corner of the lon/lat domain.
  origin: [-180, -90]

  # Edge length of one output tile, in CRS units - 1.0 = one degree.
  #   A PRODUCT decision: this is what a consumer downloads.
  tile_size: 1.0

  # Edge length of one compute block, in CELLS (not CRS units).
  #   An ENGINEERING decision: what one worker handles. Invisible in
  #   the output, and cannot change your result.
  block_size: 720

So this grid puts cell edges every arcsecond starting from (−180°, −90°), groups them into 1° tiles of exactly 3600 × 3600 cells, and hands workers 720 × 720 pieces of those tiles.

Stratum refuses three configurations at plan time because they are almost always mistakes:

  • a positive y resolution, unless you explicitly force it;
  • resolution > 1 with a 4xxx EPSG — metres and degrees confused;
  • a tile whose cell count at the configured resolution will not fit a worker (warning).

Tile and block

Two different units for two different reasons, and it is worth keeping them straight.

Typical1°512 × 512 cells
Guarantee

Block-wise output is bit-identical to tile-wise output. Tune grid.block_size freely for memory and parallelism; it cannot change your result.

Tiles are named by their grid indices, so a tile name is a position:

{grid_id}/{tile_x}_{tile_y}          e.g.  emit30/-111_32

Tiles need not cover the world. An area of interest resolves to the set of tiles intersecting it, so a global EMIT run should clip to the coverage band rather than iterate dead cells.

Halos

A halo is a ring of extra pixels a block reads beyond its own edges, so that a calculation needing neighbouring pixels still has them at the block boundary.

You need one because splitting a tile into blocks is only safe when each output cell depends on observations over that cell alone. Mode, median, percentile and count all qualify. Anything with spatial extent — a smoothing filter, a neighbourhood test — does not, and would produce visible seams at block boundaries.

A plugin that needs neighbouring pixels declares how many:

class MyScorer:
    halo = 1        # pixels of overlap needed on every side

Stratum materializes halo extra pixels around the block, runs your plugin, and trims before writing. Halo cost is (1 + 2h/B)² — at block_size: 720, a one-pixel halo costs 0.6% and a 32-pixel halo 19%.

A plugin that genuinely needs the whole tile at once declares capability = "tile" instead. That gives up block parallelism and routes the work to Batch, but it is honest about the cost rather than silently wrong.

Epochs and delivery

Temporal reduction happens in two stages, and the reason for that is the thing worth understanding before you configure it.

StageUnitWhat happensDecided by
3 · Resolveone epochEvery observation overlapping a cell in that epoch competes; one wins. Result is a snapshot.Your Scorer
4 · Reduceone delivery periodThe snapshots in that period are combined into the delivered bands.Your Reducer
The point of the intermediate stage

An epoch is one vote. Not one observation — one epoch. A month with twenty overpasses and a month with one each contribute exactly one snapshot to the reduction.

That is what the two stages buy you. If you pooled a whole year of observations and took the most frequent class directly, a densely revisited month would outvote the rest of the year, and the result would describe the satellite's schedule as much as the ground. Resolving each month first normalises that away.

So epoch: P1M with deliver: P1Y means: within each month the scorer picks a winner per cell, and the year's twelve snapshots then vote. You do not vote "on the month level" — the month is the vote.

Setting epoch equal to the delivery period collapses this to one stage: a single snapshot, no reduction, and the scorer alone decides from all observations pooled.

Delivering more often than the window slides

By default each product is built from the epochs inside its own period — consecutive products share nothing. That is often not what you want. A rolling composite delivers frequently while each output still draws on a longer span:

time:
  start: 2022-08-01
  end:   2026-07-31
  epoch: P1M              # the voting unit - one snapshot per month
  deliver:
    every: P1M            # one product per month
    window: P13M          # each draws on 13 months of epochs
    align: center         # centred on the month being delivered

The July 2024 product is then reduced from the thirteen monthly snapshots spanning January 2024 through January 2025 — thirteen votes, centred on July. The August 2024 product uses twelve of the same snapshots plus one more.

alignThe window sitsUse for
exactExactly the delivery period. Default.Non-overlapping products — "the 2024 mosaic"
centerCentred on the delivery periodSmoothed time series where each output is best-supported
trailingEnding at the end of the delivery period"Best estimate as of now", using only past data
leadingStarting at the start of the delivery periodForward-looking composites

The shorthand deliver: P1Y is exactly {every: P1Y, window: P1Y, align: exact}.

Overlapping windows are nearly free

A snapshot is cached per (tile, epoch, block, scorer) — the delivery period is not part of its key. So in the example above each monthly snapshot is computed once and read by thirteen different products. Rolling windows cost you stage-4 reductions, not stage-3 scoring.

Rules that decide edge cases

  • A granule belongs to the epoch containing its acquisition start, regardless of end time.
  • Epoch bounds are half-open, [start, end), in UTC.
  • Epochs are generated from time.start by the epoch period, not aligned to the calendar, unless you set align: calendar.
  • window must be a whole multiple of epoch, and at least every. Both are checked at plan time.
  • Near time.start and time.end a window is truncated, so the first and last products are built from fewer epochs. That is visible in the n_epochs band, and min_count on the reducer is the lever for suppressing pixels that end up under-supported. The plan report lists the epoch count for every delivery period, so short ones are obvious before you run.
  • A granule falling outside every epoch is an error at plan time, not a silent drop.

Roles and band aliases

Plugins never name a collection or a band index. They name a role, and the manifest resolves it — which is what lets the same scorer run against a different instrument.

inputs:
  roles:
    geometry: {collection: EMITL1BOBS,  var: obs}
    mineral:  {collection: EMITL2BMIN,  var: group_1_mineral_id}
    mask:     {collection: EMITL2AMASK, var: mask}
  band_aliases:                             # band: is a 0-based index into the role's variable
    view_zenith:  {role: geometry, band: 2}
    solar_zenith: {role: geometry, band: 4}

Your scorer then writes obs["view_zenith"], never obs[:, :, 2]. If a plugin declares a role the manifest does not define, the run fails at plan time rather than in several thousand workers.

Coordinate spaces

Three spaces exist, and every array you receive tells you which one it is in.

SpaceAxesYou see it in
sensor(downtrack, crosstrack)Raw granule variables; a PixelMask with space = "sensor"
granule-ortho(ortho_y, ortho_x)The GLT shipped inside a granule. Not the run grid.
block(y, x)Everything from resolve onward, and any space = "map" mask

The distinction matters for masks. Some conditions are properties of a location — this cell is water — and are expressed in map space, after the gather through the GLT. Others are properties of the detector — this cross-track column is unreliable — and can only be expressed in sensor space, because the gather through the GLT discards the source column. Declare which one you mean; see Writing plugins.

EMIT specifics

EMIT is a push-broom: every column is a different detector. Cross-track edges therefore need trimming, but along-track granule boundaries are a download convenience with no physical meaning and need nothing. stratum_emit ships this as a built-in mask, so you do not configure it by hand.

What is a push-broom sensor, and why does it matter here?

A push-broom instrument has a single line of detectors laid out across the flight direction. It builds an image by sweeping that line forward as the platform moves — one row at a time, the way a push broom sweeps a floor.

The consequence for you is that every column of the raw image comes from a different physical detector, each with its own calibration and its own defects. A bad detector shows up as a persistent stripe down the whole scene, not as a blob. Rows, by contrast, are just moments in time: the boundary between one granule and the next is a decision about where to cut a continuous strip for distribution, and carries no physical meaning.

That asymmetry is why masks need to say which space they operate in, why cross-track edge columns are trimmed, and why along-track edges are left alone.

Missing data

Two kinds of "nothing here" exist and they are not interchangeable:

The rule

-9999 means not observed. 0 in a class band means observed, nothing identified. A reduction that treats them alike will report confident agreement over pixels nobody ever looked at.

Inside Stratum you never see either. Integer fills are converted to a validity mask on read and sentinels are re-applied only on write, so a plugin works with obs.valid and with NaN for floats:

def score(self, obs, aux):
    s = -obs["view_zenith"]
    s[~obs.valid] = np.nan      # never compare against -9999 yourself
    return s

Returning NaN from a scorer means this observation may not occupy this cell. It loses to any observation with a real score, and if every observation returns NaN the cell is left empty.

How is missing data declared in the source files?

NetCDF and GeoTIFF both carry an attribute naming the value that stands for "no data" — _FillValue in NetCDF, the nodata tag in GeoTIFF. It is a convention, not a type: the value is an ordinary number in the array, and nothing stops arithmetic from running over it. That is exactly how a -9999 ends up averaged into a result.

Stratum converts these to an explicit validity mask on read and re-applies the sentinel only on write, so plugin code never has to remember which number is special.

Class tables

A categorical band's integer values index a table of classes. Stratum carries that table around generically: it has a key column whose values appear in the pixels, plus any number of attribute columns.

Where the table lives is declared per role, because some products embed one and some do not:

inputs:
  roles:
    mineral:
      collection: EMITL2BMIN
      var: group_1_mineral_id
      class_table:
        source: embedded          # embedded | file
        path: /mineral_metadata   # group within the product
        key: index                # column matching pixel values
        attributes: [name, record, library, group, url]

Prefer source: embedded whenever a product offers it. The table then travels with the data it describes and cannot drift from it.

Why you match on attributes, not integers

A mosaic spans many granules, and a pixel value of 15 has to mean the same thing in all of them. Key columns are usually positional, and the class list can change when the upstream producer is upgraded — so the same integer can mean different things in two granules of different vintages.

Stratum handles this in two ways, and both are things you configure rather than code:

  1. Refuse mixed vintages at plan time, by fingerprinting every contributing granule's class table. This is automatic and required — see Running a mosaic. Pinning a build_version is an optional filter, not the guard: one collection already spans eight builds with no change to its classes.
  2. Refer to classes by attribute wherever you name one — in the classes file a snapshot layer declares, in colour tables. Stratum resolves the attributes per granule at plan time and remaps pixels into the product's own enumeration as they are read.
match_on: [library, record, group]
classes:
  - {id: 1, name: goethite, members: [{library: sprlb06, record: 882,  group: 1},
                                      {library: splib06, record: 5736, group: 1}]}

At plan time Stratum fingerprints every contributing granule's class table. If they all agree, it proceeds and records the fingerprint in provenance. If they differ, it fails and tells you — unless you have explicitly permitted mixed vintages, in which case every table must still resolve fully into the enumeration, and it reports any entry it cannot resolve unambiguously.

An entry that matches zero or multiple rows is a plan-time error, never a guess.

A mosaic's classes are its own — after lumping they are not the input classes — so the published class table describes the product, not the granules that fed it.

What are COG and STAC?

COG — Cloud Optimized GeoTIFF — is an ordinary GeoTIFF whose internal layout is arranged so a reader can fetch just the part it needs over HTTP range requests, rather than downloading the whole file. Internal tiling (typically 512 × 512) and precomputed overviews are what make that work, and it is why the default block size aligns with the tile size.

STAC — SpatioTemporal Asset Catalog — is a JSON schema for describing a geospatial asset: its footprint, its time, its bands, and links to the files themselves. Writing one per output tile is what makes the products discoverable by standard tooling instead of by knowing the bucket layout.
