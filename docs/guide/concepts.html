Concepts

The model you need to hold in your head to write a manifest or a plugin.

Grid

A grid is CRS, resolution and origin. It has no extent. It is a rule — cell edges fall at origin + n × resolution — which fixes where cell boundaries lie anywhere in the CRS's domain, without anyone having to say where the data is.

That is what makes tiles align. Tile bounds are derived from the grid, never from the extent of your granules, so two runs over the same ground at the same grid produce identical tile bounds and can share cached geometry. A grid that took its bounds from data would give every run subtly different tiles.

grid:
  crs: EPSG:4326
  resolution: [0.0003, -0.0003]    # x positive, y negative
  origin: [-180, -90]
  tile_size: 1.0
  block: 512

Stratum refuses three configurations at plan time because they are almost always mistakes:

  • a positive y resolution, unless you explicitly force it;
  • resolution > 1 with a 4xxx EPSG — metres and degrees confused;
  • a tile whose cell count at the configured resolution will not fit a worker (warning).

Tile and block

Two different units for two different reasons, and it is worth keeping them straight.

Guarantee

Block-wise output is bit-identical to tile-wise output. Tune grid.block freely for memory and parallelism; it cannot change your result.

Tiles are named by their grid indices, so a tile name is a position:

{grid_id}/{tile_x}_{tile_y}          e.g.  emit30/-111_32

Tiles need not cover the world. An area of interest resolves to the set of tiles intersecting it, so a global EMIT run should clip to the coverage band rather than iterate dead cells.

Halos

Splitting a tile into blocks is only safe when each output cell depends on observations over that cell alone. Mode, median, percentile and count all qualify. Anything with spatial extent — a smoothing filter, a neighbourhood test — does not, and would produce visible seams at block boundaries.

A plugin that needs neighbouring pixels declares how many:

class MyScorer:
    halo = 1        # pixels of overlap needed on every side

Stratum materializes halo extra pixels around the block, runs your plugin, and trims before writing. Halo cost is (1 + 2h/B)² — at block: 512, a one-pixel halo costs 0.8% and a 32-pixel halo 13%.

A plugin that genuinely needs the whole tile at once declares capability = "tile" instead. That gives up block parallelism and routes the work to Batch, but it is honest about the cost rather than silently wrong.

Epoch and cadence

Epochs are the voting population. Cadence is the delivery unit.

time:
  start: 2022-08-01
  end:   2026-07-31
  epoch: P1M              # monthly snapshots — the voting population
  deliver: P1Y            # annual product — the delivery cadence

Monthly epochs delivered annually means up to twelve votes per output pixel. Set epoch equal to deliver and each product is built from a single snapshot, with no temporal reduction.

Rules that decide edge cases:

  • A granule belongs to the epoch containing its acquisition start, regardless of end time.
  • Epoch bounds are half-open, [start, end), in UTC.
  • Epochs are generated from time.start by the epoch period, not aligned to the calendar, unless you set align: calendar.
  • A granule falling outside every epoch is an error at plan time, not a silent drop.

Roles and band aliases

Plugins never name a collection or a band index. They name a role, and the manifest resolves it — which is what lets the same scorer run against a different instrument.

inputs:
  roles:
    geometry: {collection: EMITL1BOBS,  var: obs}
    mineral:  {collection: EMITL2BMIN,  var: group_1_mineral_id}
    mask:     {collection: EMITL2AMASK, var: mask}
  band_aliases:
    view_zenith:  {role: geometry, band: 5}
    solar_zenith: {role: geometry, band: 4}

Your scorer then writes obs["view_zenith"], never obs[:, :, 5]. If a plugin declares a role the manifest does not define, the run fails at plan time rather than in several thousand workers.

Coordinate spaces

Three spaces exist, and every array you receive tells you which one it is in.

SpaceAxesYou see it in
sensor(downtrack, crosstrack)Raw granule variables; a PixelMask with space = "sensor"
granule-ortho(ortho_y, ortho_x)The GLT shipped inside a granule. Not the run grid.
block(y, x)Everything from stage 3 onward, and any space = "map" mask

The distinction matters for masks. Some conditions are properties of a location — this cell is water — and are expressed in map space after regridding. Others are properties of the detector — this cross-track column is unreliable — and can only be expressed in sensor space, because regridding discards the source column. Declare which one you mean; see Writing plugins.

EMIT specifics

EMIT is a push-broom: every column is a different detector. Cross-track edges therefore need trimming, but along-track granule boundaries are a download convenience with no physical meaning and need nothing. stratum_emit ships this as a built-in mask, so you do not configure it by hand.

Missing data

Two kinds of "nothing here" exist and they are not interchangeable:

The rule

-9999 means not observed. 0 in a class band means observed, nothing identified. A reduction that treats them alike will report confident agreement over pixels nobody ever looked at.

Inside Stratum you never see either. Integer fills are converted to a validity mask on read and sentinels are re-applied only on write, so a plugin works with obs.valid and with NaN for floats:

def score(self, obs, aux):
    s = -obs["view_zenith"]
    s[~obs.valid] = np.nan      # never compare against -9999 yourself
    return s

Returning NaN from a scorer means this observation may not occupy this cell. It loses to any observation with a real score, and if every observation returns NaN the cell is left empty.

Class tables

A categorical band's integer values index a table of classes. Stratum carries that table around generically: it has a key column whose values appear in the pixels, plus any number of attribute columns.

Where the table lives is declared per role, because some products embed one and some do not:

inputs:
  roles:
    mineral:
      collection: EMITL2BMIN
      var: group_1_mineral_id
      class_table:
        source: embedded          # embedded | file
        path: /mineral_metadata   # group within the product
        key: index                # column matching pixel values
        attributes: [name, record, library, group, url]

Prefer source: embedded whenever a product offers it. The table then travels with the data it describes and cannot drift from it.

Why you match on attributes, not integers

A mosaic spans many granules, and a pixel value of 15 has to mean the same thing in all of them. Key columns are usually positional, and the class list can change when the upstream producer is upgraded — so the same integer can mean different things in two granules of different vintages.

Stratum handles this in two ways, and both are things you configure rather than code:

  1. Pin a vintage in granule_filter so a run does not span the change. This is required, not optional — see Running a mosaic.
  2. Refer to classes by attribute wherever you name one — in lumping, in colour tables. Stratum resolves the attributes to integers per granule at plan time.
lumping:
  match_on: [library, record, group]
  classes:
    goethite:
      - {library: sprlb06, record: 882,  group: 1}
      - {library: splib06, record: 5736, group: 1}

At plan time Stratum fingerprints every contributing granule's class table. If they all agree, it proceeds and records the fingerprint in provenance. If they differ, it fails and tells you — unless you have explicitly permitted a cross-vintage remap, in which case it computes the correspondence through the attribute columns and reports any entry it cannot resolve unambiguously.

An entry that matches zero or multiple rows is a plan-time error, never a guess.
