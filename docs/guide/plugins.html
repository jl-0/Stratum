Writing plugins

Five extension points. Most runs need none of them written from scratch — start by checking whether configuration covers what you want.

Your first cost function

A scorer is a class with one method. Higher scores win.

class MinViewZenith:
    """The most nadir look wins."""
    capability = "streaming"
    required_roles = ("geometry",)

    def score(self, obs, aux):
        return -obs["view_zenith"]

Register it, name it in a manifest, and run:

[project.entry-points."stratum.scorers"]
min_view_zenith = "my_package.scorers:MinViewZenith"
scorer:
  ref: min_view_zenith

That is the whole loop. Everything below is detail on the other four hooks and on doing more inside score.

Masking is not ranking

A PixelMask returns a boolean: usable or not. A Scorer returns a number: better or worse. Putting a preference in a mask turns "this pixel is unusable" into "this pixel is merely worse", which is rarely what you meant and is hard to see later.

Scorer

class Scorer(Protocol):
    capability: Literal["streaming", "stack", "tile"]
    halo: int = 0
    required_roles: tuple[str, ...] = ()
    required_aux:   tuple[str, ...] = ()

    def score(self, obs: ObsWindow, aux: AuxAccessor) -> FloatArray:
        """Higher wins. NaN marks a cell this observation may not occupy."""

Pick a capability

capability tells Stratum what your scorer needs to see. It determines memory behaviour and where the work runs, so pick the cheapest one that works.

CapabilityCalledBand shapeMemoryUse when
streamingOnce per granule(H, W)O(block)Each observation can be judged on its own
stackOnce with all observations(N, H, W)O(block × N)You need to compare observations to each other
tileOnce per tile(N, H, W)O(tile × N)You need global spatial context. Gives up block parallelism.

streaming keeps a running best-score array, so memory does not grow with the number of overlapping observations. Prefer it. Reach for stack only when the decision genuinely depends on the other observations — a median, a consensus, an outlier test. In stack mode observations arrive ordered by acquisition time.

Reading bands

Address bands by alias, never by index. The manifest maps aliases to a role and band per collection, so an alias-based scorer moves to another instrument without edits.

obs["view_zenith"]        # (H, W) — this block only
obs.valid                 # bool, same shape — observed and unmasked
obs.granule.datetime      # acquisition metadata
obs.grid                  # this block's transform and CRS
obs.n                     # 1 when streaming, N when stacked

Declare every alias you use through required_roles. A missing role is a plan-time error, so you find out before the run rather than in several thousand workers.

Reaching other datasets

A cost function often needs data that is not the granule — a DEM, a snow index, a landcover raster, mining-claim polygons. Declare it in the manifest and read it through aux:

aux:
  slope: {uri: "s3://.../slope.tif", kind: continuous, resampling: bilinear}
  snow:  {uri: "s3://.../snow/{date}.tif", kind: categorical, resampling: nearest,
          temporal: nearest, max_age: P3D}
class CleanestNadir:
    """Nadir-preferring, penalised for steep terrain, rejecting snow."""
    capability = "streaming"
    required_roles = ("geometry",)
    required_aux = ("slope", "snow")

    def score(self, obs, aux):
        s = -obs["view_zenith"] / 90.0
        s -= 0.5 * (aux.raster("slope") > 30)
        s[aux.raster("snow", date=obs.granule.datetime) > 0] = np.nan
        return s
The block grid is the contract

Everything aux returns is already windowed to your block, already on your block's grid and CRS, and already cached. You never reproject, resample, or window anything yourself.

Two rules that come with it:

  • Declare what you read. The accessor refuses an undeclared alias rather than opening a path. Undeclared reads would produce a cache key that does not mention them, and your cached results would silently go stale when the file changed.
  • Declare the resampling. kind and resampling are both required. Bilinear-interpolating a landcover class and nearest-neighbouring a DEM are both wrong and neither raises an error on its own, so Stratum will not guess — a categorical source with a continuous resampling method is a plan-time error.
aux.raster("dem")                          # (H, W) on this block's grid
aux.raster("snow", date=obs.granule.datetime)
aux.vector("claims")                       # rasterized to this block
aux.table("climate_index").at(date)         # scalar, no gridding
aux.granule_index                          # the frozen index

A worked example

Given several observations of a pixel, most of which see vegetation, prefer the one that sees ground:

class PreferBareEarth:
    capability = "streaming"
    required_roles = ("frcov",)

    def __init__(self, min_soil=0.80, hard_floor=0.65):
        self.min_soil, self.hard_floor = min_soil, hard_floor

    def score(self, obs, aux):
        soil = obs["soil_fraction"]
        s = soil.copy()
        s[soil < self.hard_floor] = np.nan     # unusable, not merely worse
        return s

Two thresholds rather than one, deliberately. Below hard_floor the observation is rejected outright; between hard_floor and min_soil it still ranks, so a marginal observation can win a cell where nothing better exists. Collapsing them into a single cutoff throws that range away.

Constructor arguments come from the manifest:

scorer:
  ref: prefer_bare_earth
  params: {min_soil: 0.85, hard_floor: 0.7}

The score is kept

Stage 3 writes the winning score alongside the winning value, so "why did this pixel win?" is answerable from the artifact afterwards. You get this for free; there is nothing to declare.

PixelMask

class PixelMask(Protocol):
    space: Literal["map", "sensor"] = "map"
    required_roles: tuple[str, ...] = ()

    def valid(self, obs: ObsWindow, aux: AuxAccessor) -> BoolArray:
        """(H, W) bool. True = usable."""

Set space to match what your condition is a property of:

spaceobs isUse for
"map"On the block grid, post-regridConditions about a location — cloud, water, land cover
"sensor"Raw (downtrack, crosstrack), pre-regridConditions about the instrument — bad columns, detector artifacts

Sensor-space masks must be applied before the GLT is built, because regridding discards the source column. Declaring the space is how Stratum knows to run yours at the right point.

Reducer

A reducer receives every epoch snapshot for one block and returns the delivered bands.

class Reducer(Protocol):
    outputs: tuple[BandSpec, ...]
    halo: int = 0

    def reduce(self, snaps: SnapshotStack, aux: AuxAccessor) -> dict[str, Array]:
        """snaps[name] is (n_epochs, H, W). One array per declared output."""

Declare your outputs up front. Stratum derives the raster schema, the STAC item and the OutputMapper contract from them without running anything, which is how a bad output declaration fails at plan time.

class ModeThroughTime:
    outputs = (
        BandSpec("mineral_id",   "uint16",  "most frequent class across epochs"),
        BandSpec("agreement",    "float32", "modal count / valid epochs"),
        BandSpec("n_epochs",     "uint8",   "epochs contributing"),
        BandSpec("runner_up_id", "uint16",  "second most frequent class"),
    )
reducer:
  ref: mode_through_time
  params: {min_count: 3, ignore: [0, -4], tie_break: highest_score}
ParameterEffect
min_countSuppress pixels whose modal class has fewer than this many votes
ignoreClass values excluded from the tally — typically the "nothing identified" class
tie_breakearliest | latest | highest_score | nodata

What you get

snaps["mineral_id"]     # (n_epochs, H, W) — the winning value per epoch
snaps.valid              # (n_epochs, H, W) bool — was there an observation at all
snaps.score              # (n_epochs, H, W) — the score that won each cell
snaps.epochs             # ordered ascending

snaps.valid is what keeps counts honest: an epoch with no observation over a pixel must not count toward agreement. Check it rather than testing values against a sentinel.

snaps.score lets you weight epochs by the confidence that produced them instead of treating them equally.

Reduce continuous quantities where you can

Voting over class labels discards information that voting over band depths or fit values keeps. If your product allows it, aggregate the continuous bands and classify at the end. Both approaches use the same contract — the difference is which bands your scorer carried forward.

OutputMapper

Most rendering is configuration. Reach for a plugin only when a lookup table or a ramp cannot express what you want.

outputs:
  render:
    mineral_id:
      mapper: categorical
      classes: "@ref:lumping/cm-v1.yaml"
      colors:
        pyrite:   [220,   5,  12]
        goethite: [174, 118, 163]
      nodata: transparent
      on_unmapped: fail            # fail | grey | transparent
      alpha_from: {band: agreement, domain: [0.3, 0.8], range: [60, 255]}

Built-in mappers: categorical, continuous, threshold (classed breaks) and composite (three bands to RGB).

on_unmapped: fail is the default on purpose. A class present in the data but absent from your colour table is a real error, and rendering it grey is how a class quietly disappears from a map.

alpha_from is worth knowing about: deriving opacity from an agreement or count band makes low-support pixels fade rather than assert a confident colour they have not earned.

A custom mapper

class ConfidenceShaded:
    """Class colour, hillshaded by terrain, faded by agreement."""
    outputs = (ImageSpec("mineral_id_shaded", "RGBA"),)

    def render(self, bands, aux):
        rgb = self.table[bands["mineral_id"]]
        rgb = rgb * hillshade(aux.raster("dem"))[..., None]
        alpha = np.interp(bands["agreement"], [0.3, 0.8], [60, 255])
        return np.dstack([rgb, alpha]).astype("uint8")

    def legend(self):
        return Legend.categorical(self.table, note="shaded by terrain")

bands holds every band your reducer declared, so a mapper can reason across them. legend() is not optional — it is written as a sidecar and into the STAC item, so the meaning of a colour travels with the product.

Because rendering is a pure function of the published data, changing a mapper never re-runs the pipeline. stratum render --run <id> --mapper <ref> reads the data blocks and writes a new image.

GranuleFilter

Most filtering is configuration — see Running a mosaic. Write a plugin when you need a predicate the manifest cannot express.

class GranuleFilter(Protocol):
    def keep(self, granules: GranuleFrame) -> BoolArray:
        """Vectorized over the whole candidate frame. True = keep."""

    def describe(self) -> str:
        """One line for the run report, e.g. 'cloud_fraction <= 0.5'."""

GranuleFrame is the index as a dataframe — one row per granule, with footprint, timing, cloud fraction, version and asset URIs. Operate on it vectorized; you never see individual granules.

Implement describe() properly. It is what appears in the run report next to the count of granules your filter removed, and a filter that removes 800 granules without saying why is how data goes missing unnoticed.

Registering and shipping

Plugins are ordinary Python entry points:

[project.entry-points."stratum.scorers"]
min_view_zenith = "stratum_emit.scorers:MinViewZenith"
prefer_bare_earth = "stratum_emit.scorers:PreferBareEarth"

[project.entry-points."stratum.reducers"]
mode_through_time = "stratum_emit.reducers:ModeThroughTime"
stratum plugins list        # what this image or environment provides

There are two ways to get your plugin to the workers:

PathHowUse for
IterationPoint the manifest at a wheel in S3; workers fetch it at cold startExperiments. Edit, publish, rerun in about 90 seconds.
ProductionPin the plugin in the container image; wheel-fetch disabled by policyDelivered products, reproducible from an immutable digest
 
plugins:
  wheel: s3://emit-l3/plugins/stratum_emit-0.4.2-py3-none-any.whl

Both paths record the plugin version and content hash in provenance, and both feed the cache key — so a changed plugin invalidates its own results and nothing else.

What is checked before you run

stratum plan catches all of this before any compute is provisioned:

  • the named plugin resolves and its version is recordable;
  • every required_roles entry exists in inputs.roles;
  • every required_aux entry is declared in aux, and those sources exist and are readable;
  • capability and halo are consistent with the configured block size;
  • declared outputs are non-empty and uniquely named, and have a mapper if rendering is requested;
  • every class you name in lumping or a colour table resolves to exactly one class-table row.

Testing a plugin

Plugins are plain classes over numpy arrays, so most tests need no pipeline at all — construct an ObsWindow from the test helpers and call score directly.

Two behaviours are worth testing explicitly because they fail quietly:

  1. If you set a halo, check that block-wise output matches tile-wise output. Stratum runs this check in CI for its own plugins; the same fixture is available to yours.
  2. If you take parameters, check that changing one changes the cache key. A parameter that does not reach the key will serve you stale results from a previous configuration.
