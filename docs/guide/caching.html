Caching & reruns

Every artifact is stored under a hash of the inputs that determine it. Change one thing and exactly what depended on it is rebuilt.

Iterating on a cost function

The first run over new ground pays for the geometry. Every run after that does not.

$ stratum run -m base.yaml -p scorer-v1
  Cache  GLT 0/725 hit  →  725 to build
  ~11 vCPU-hours · ~28 min

$ stratum run -m base.yaml -p scorer-v2
  Cache  GLT 725/725 hit (100%)  →  0 to build
  ~0.9 vCPU-hours · ~4 min

Running several competing scorers over the same area is therefore roughly the cost of one regrid plus n cheap passes. That is the intended way to work: build variants as patches and compare them, rather than deciding a cost function up front.

The cache is shared

GLT keys contain no run, project or area component — only the granule, the grid and the mask spec. Two consequences:

  • Across experiments. Every run over the same ground at the same grid shares cached geometry, regardless of who launched it or what they were trying.
  • Across projects. If two projects adopt the same grid, the second one's first run is nearly free over ground the first has already touched.

Because tile bounds are derived from the grid rather than from data extents, a GLT built for one project is byte-identical to one built for another over the same ground.

{root}/cache/...          shared, content-addressed, long-lived
{root}/runs/{run_id}/...  run-scoped: frozen index, work lists, reports
{root}/products/{run_id}/ delivered outputs

{root} is a local directory or an s3:// prefix — the layout and the keys are identical either way, which is what lets a locally started run be finished on a cluster.

Inspecting the cache

stratum cache stats  --run <id>     # hit rate by artifact type; what a rerun costs
stratum cache explain <key>         # the inputs that produced this artifact
stratum cache diff <key-a> <key-b>  # which input differs
stratum cache gc --dry-run          # unreferenced entries past their lifecycle

Every artifact has an .inputs.json stored beside it, holding the exact document that was hashed to produce its key. So a cache entry can always be explained:

$ stratum cache explain glt/emit30/-111_32/a3f9c1e04b28d7f6

artifact      GLT
granule_id    001_20240612T183317_2416412_012
grid_def      {crs: EPSG:4326, resolution: [0.0003, -0.0003], origin: [-180, -90]}
max_distance  0.00045
regrid_algo_version  3

written       2026-08-14T09:12:44Z by run cuprite-2024
size          41.2 MB
referenced by 6 runs

When a rerun misses and you expected a hit, cache diff is the fast answer — the cause is always one field:

$ stratum cache diff a3f9c1e0… 7b2e4419…
  max_distance   0.00045  →  0.0006
  (all other inputs identical)

Rules the cache relies on

Mostly these are the framework's problem, but two affect what you do.

RuleWhat it means for you
Undeclared reads are refusedA plugin must declare every aux source in required_aux. The accessor raises on an undeclared alias rather than opening it, because a read that is not in the key would silently go stale.
Aux sources are keyed by contentReplacing a file in place under the same URI still invalidates correctly, via ETag or an explicit version. You do not need to rename files to force a rebuild.
Plugin versions are in the keyBoth the wheel URI and its content hash. Republishing a wheel at the same URI does invalidate; you do not have to bump a version string to see your change take effect.
Algorithms are versionedregrid_algo_version is bumped when regrid output changes. If you are changing regrid behaviour, bump it, or cached geometry stays stale forever.
Writes are atomicAn interrupted task cannot leave a truncated artifact that later reads as a hit, so retries and Spot interruptions are safe.

Lifecycle

ClassRetentionWhy
GLTIndefiniteExpensive, immutable, shared, small relative to imagery
Masked observations~30 daysLarge, and cheap to rebuild from a cached GLT
Epoch snapshotsThe longest delivery window any manifest declares; at least 30 daysA rolling window re-reads snapshots rather than recomputing them; invalidated by scorer changes anyway
Product blocksUntil the tile publishesSuperseded by the stitched product
Prepared assetsWhile a frozen index references themOne transcode per asset; what makes block reads genuinely windowed on the delivered L2B
Frozen index, reports, provenanceIndefiniteTiny, and the basis of reproducibility

An expired masked observation costs one cheap rebuild from cached geometry, not a regrid. It is an optional layer — resolve builds it as it reads, and caches it only so the next scorer over the same ground can skip the granule read. The retention policy is set per deployment; these are the defaults.

Forcing a rebuild

Rarely needed — a correct key makes it unnecessary — but available when you are debugging the cache itself:

stratum run -m manifest.yaml --no-cache            # ignore hits, rebuild everything
stratum run -m manifest.yaml --no-cache-from glt   # rebuild GLTs and downstream

If you find yourself reaching for these routinely, something is missing from a cache key. That is a bug worth reporting rather than working around.
