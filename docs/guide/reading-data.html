Reading data

How granules are found, fetched and turned into the arrays a scorer sees — from a directory on your laptop or from NASA's archive, through the same interface.

Three jobs, kept apart

Getting data into a block looks like one task and is really three. Stratum keeps them separate because they run in different places, at different times, with different failure modes.

JobComponentRunsTalks to
Discovery — what granules existGranuleSourceIndex build — a periodic jobA live catalogue, or a directory
Access — a URI becomes readable bytesAssetStoreEvery workerStorage, and a credential endpoint
Read — bytes become arraysGranuleReaderEvery workerNothing external
A run never queries a catalogue

Discovery happens ahead of time and lands in an index. A run reads a frozen copy of that index and nothing else. That is what lets a run be reproduced months later — and it is what stops several thousand workers hammering a public API the moment your fan-out gets interesting.

This is about metadata, not pixels. Workers pull granule data straight from S3 when they need it. What is settled ahead of time is which granules and where they live — the URL list — not the bytes. See When the bytes actually move.

The seam that matters most is between access and read. A reader that takes a path and opens it can only ever read local files. Split apart, the reader is handed an already-open handle and never learns whether the bytes came from disk, from S3, or from a range request over HTTP — so the same reader works on your laptop and in Lambda.

How a block gets its data

Stage 3 works on one block of one tile for one epoch. Here is what happens when it needs a band, for one contributing granule:

# The work item names a block and an epoch. Which granules touch it
# comes from the frozen index — no catalogue call.
win  = block.window                                # (H, W) on the tile grid, halo included
cand = frozen_index.intersecting(block, epoch)

for granule in cand:

    # 1. The GLT was built in stage 2 and cached. It is a COG, so this
    #    reads only the bytes covering this block — not the whole tile.
    glt = assets.open(glt_key_for(granule, tile))
    g   = glt.read(win)                            # (H, W, 3) int32

    if not g[..., 2].any():
        continue                                   # granule does not reach this block

    # 2. The GLT names exactly which sensor pixels this block touches.
    #    Take their bounding box — this is the whole trick.
    sw  = SensorWindow.covering(g[..., 0], g[..., 1])

    # 3. Open the asset and read ONLY that rectangle.
    src = assets.open(granule.assets["mineral"])
    arr = reader.read(src, var="group_1_mineral_id", window=sw)   # (h, w)

    # 4. Map sensor pixels onto grid cells. The only place the two meet.
    band, valid = gather(arr, g, sw)               # (H, W) on the block grid

Why step 2 is the whole trick

A 512 × 512 block at 0.0003° spans about 0.15°, which covers roughly 170 × 170 of a granule's 60 m pixels. The granule itself is 1664 × 1242. Reading the whole scene for every block would read about fifty times more data than the block needs — and pay it again for every granule, in every epoch.

ApproachRead per block, per granule
Open the granule, take what you needThe whole scene — ~2.1 M pixels per variable
Window from the GLT first~29 k pixels — about 1.4%

Because the GLT already knows which source pixels landed in this block, the window is exact rather than estimated. Nothing is guessed from footprints.

A window remembers where it came from

SensorWindow is (row0, col0, height, width) against the full granule, not a bare shape. A sensor-space mask like EdgeTrim needs the absolute cross-track column to know whether it is looking at a detector edge. Hand it a window that has forgotten its origin and it will trim the edge of every block instead of the edge of the detector — and the output will look entirely reasonable.

Step 4, in full

The gather is the one place sensor space and block space meet, so it lives in the framework rather than in anybody's plugin:

gy, gx, fi = g[..., 1], g[..., 0], g[..., 2]

hit    = fi != 0                     # 0 is GLT nodata
interp = (gy < 0) | (gx < 0)         # negative marks an interpolated cell

r = np.abs(gy) - 1 - sw.row0         # GLT indices are 1-based
c = np.abs(gx) - 1 - sw.col0

band  = np.where(hit, arr[r, c], fill)
valid = hit & ~arr.mask[r, c]

One-based indices and the negative-means-interpolated convention are inherited on purpose, so Stratum's GLTs interoperate with artifacts the existing tooling produces. Both are easy to get wrong once and never notice.

Your scorer sees none of this

Everything above happens below ObsWindow. A Scorer gets obs["mineral"] already on the block grid, already masked, and never sees a URI, a sensor window, a reader or a credential. That is the same promise aux makes for ancillary data.

Products already on a map grid

Not every input is in sensor space. EMIT's fractional-cover product (FRCOV) ships orthorectified, so it has no sensor geometry to window and nothing to regrid — it is warped onto the block grid directly. A reader declares which space it produces, and Stratum takes the cheaper path when it can.

Where granules come from

From a directory

inputs:
  index: ./index/emit-granules.parquet   # what a RUN reads
  source:                                # how that index is BUILT
    kind: local
    root: ./granules
    pattern: "EMIT_L2B_MIN_*.nc"

stratum index build walks the directory, reads each file's header once, and writes the same index the archive path produces. No network, no Earthdata account, no catalogue. Nothing downstream can tell the difference — which is the test that this seam is in the right place.

From NASA's archive

inputs:
  index: s3://emit-l3/index/emit-granules.parquet
  source:
    kind: cmr
    provider: LPCLOUD      # the DAAC that distributes EMIT
    prefer: direct         # direct (s3://) where possible, else https
What are CMR, a DAAC, and Earthdata Login?

NASA does not keep its Earth science data in one place. It is distributed across a dozen DAACs — Distributed Active Archive Centers — each responsible for a subject area. EMIT products are distributed by LP DAAC, the Land Processes centre, whose cloud holdings appear under the provider name LPCLOUD.

The CMR — Common Metadata Repository — is the catalogue that sits in front of all of them. It does not hold the data; it holds a metadata record for every granule, and answers questions like "which EMIT L2B granules intersect this box between these dates?" Each answer includes the URLs where the actual file can be fetched.

Those metadata records follow a schema called UMM-G (Unified Metadata Model, Granule). It is generic across every NASA mission, which is why it does not look much like our index schema and why a translation layer is needed.

Earthdata Login (URS) is the single sign-on account for all of it. Downloads are authenticated even though the data is free, so a machine fetching granules needs credentials — usually a token, or a ~/.netrc entry.

Why there is a bridge layer

earthaccess is NASA's own Python client and Stratum uses it. It handles the parts that are genuinely tedious — login, .netrc, the S3 credential exchange, DAAC endpoints — and it is already a dependency of the tooling this project builds on. But it returns a thin wrapper over UMM-G JSON, and four things have to happen between that and a row in an index:

What the bridge doesWhy it cannot be skipped
Maps UMM-G fields onto the index schemaNot one-to-one, and lossy in places
Resolves assets to rolesUMM-G types URLs by access method, not by role. Choosing the s3:// entry over the HTTPS one, and deciding which file is mineral and which is mask, is our policy
Applies the missing-metadata policyCloud fraction is present on some collections and simply absent on others. Absent must arrive as null, never 0.0 — see Missing metadata
Holds an explicit sessionearthaccess.login() sets module-level global state, which is wrong in a process pool and worse in a Lambda

The field-by-field mapping, including the two fields that still need confirming against a real query, is in specs/12-data-access.md.

Building and refreshing the index

stratum index build -m manifest.yaml                  # first build, from inputs.source
stratum index build -m manifest.yaml --since 2026-09-01  # incremental refresh
stratum index verify -m manifest.yaml                 # do the asset URIs still resolve?

--since does more than make refreshes cheap. Upstream reprocessing re-delivers granules with the same identifiers and different contents, and an incremental refresh is how that becomes visible: the granule comes back as updated, the index records a new last-seen timestamp, and verify reports it.

Without that, the archive changes underneath you silently

A stable query returning different science is the failure this whole path is arranged to prevent. Pair it with vintage pinning — see Vintage pinning is required.

Fetching the bytes

Once a run has an index, reading an asset is AssetStore's problem. It supports two modes behind one interface:

ModeWhat happensWhen
Stage inThe worker copies that one asset to its own scratch and gets a path backThe default. Works with any code that expects a filename
StreamReads become HTTP range requests; only the touched bytes moveOnce a reader supports windowed reads — roughly 1% of a file for one block

Readers do not change when the mode does. Staging is what works today against existing code; streaming is where the cost goes.

When the bytes actually move

Lazily, inside the worker, on first touch. Nothing is copied before a run starts.

plan time      index query        -> URLs, footprints, times, vintages
                                     METADATA ONLY, frozen into the run index
worker starts  nothing fetched
first block    assets.open(uri)   -> this worker pulls this one asset, now
later blocks   same worker        -> asset cache hit; no second fetch
“Stage in” is just-in-time, not a pre-run copy

It means this worker downloads this one granule to its own scratch at the moment it needs it. There is no bulk copy of the archive into your bucket, no pre-run download pass, and nothing has to be resident before you invoke stratum run. A worker that never touches a granule never fetches it, and a granule no block reaches is never downloaded at all.

The line is metadata versus pixels, and the two have opposite economics:

Resolved ahead of the runFetched in the worker, on demand
WhatWhich granules qualify, their asset URLs, footprints, times, vintagesThe pixels
SizeKilobytesGigabytes
Why thereOne query, frozen, so the run reproduces and the archive sees one callerPer-block, in thousands of workers — and most of it is never touched

A catalogue query is cheap, returns URLs, and has to be frozen or a rerun reproduces nothing — so it happens once, ahead of time. Pixel data is large, sparsely accessed, and needed concurrently everywhere — so it is pulled on demand and never centralised.

Granule pixels are the one thing never prefetched. Ancillary rasters go the other way: they are small, static and touched by every block, so they are warped during planning.

The one-hour expiry shapes the design

Any worker that lives longer than an hour has to refresh mid-run, and any unit of work that cannot finish in an hour is the wrong size. This is an independent argument for many short tasks over a few long ones — the same conclusion Running at scale reaches from the cost side. Stratum refreshes on expiry and retries once, so no plugin has to know about it.

Direct S3 access to the archive works only from inside the same AWS region the data lives in (us-west-2). From elsewhere it fails in a way that reads like a permissions error, so Stratum checks the region and falls back to HTTPS rather than surfacing the confusing message.

Adding a reader

A GranuleReader turns one product family into arrays. You write one to support a new instrument or a new product; you do not write one to change what a mosaic means.

class GranuleReader(Protocol):
    collections: tuple[str, ...]        # which collections this reader claims
    space: Literal["sensor", "ortho"]

    def open(self, asset: AssetHandle) -> ReaderContext:
        """Cheap. Headers and metadata only — never the pixels."""

    def variables(self, ctx) -> Mapping[str, VarSpec]:
        """Name -> dtype, shape, fill. Used by plan-time validation."""

    def read(self, ctx, var: str, window: SensorWindow | None = None) -> MaskedArray:
        """Fills already resolved to a mask."""

    def geolocation(self, ctx) -> LocArray | None:
        """lat/lon/elev in sensor space. None when space == 'ortho'."""

    def class_table(self, ctx, path, key, attributes) -> ClassTable | None:
        """Pull an embedded class table out of the granule being read."""

Four rules come with it:

  • Selection is by declared collection, never by filename. The role says collection: EMITL2BMIN, and that picks the reader. Sniffing filenames breaks the moment a file is staged into a cache-keyed path, which is exactly what staging does.
  • The reader is where -9999 dies. read returns values with fills already converted to a mask. Nothing above a reader sees a sentinel — which is how "not observed" stays distinguishable from "observed, nothing identified" all the way to a reducer.
  • open is cheap, read is windowed. The same asset is opened once per block. A reader that parses the whole file on open becomes the dominant cost.
  • Readers ship in a plugin package. stratum core provides none; stratum_emit provides the EMIT ones.

Registration works exactly as it does for the other hooks — an entry point in your package's metadata, listed by stratum plugins list --kind readers. See Registering and shipping.

One role, two file layouts

The same logical input often arrives in more than one form. EMIT mineral products exist both as DAAC-distributed NetCDF and as the Dataset layout the Tetracorder wrapper writes. Those are two readers claiming two collection names and resolving through one role — which is what the registry is for, and what filename dispatch cannot express.

Adding a source

Rarer, and only needed for an archive Stratum does not already speak to:

class GranuleSource(Protocol):
    name: str

    def search(self, *, collections, bbox, start, end,
               updated_since: datetime | None = None) -> Iterator[GranuleRecord]:
        """Yields catalogue records. Pages internally; may be very long."""

    def assets(self, record) -> Mapping[str, str]:
        """Role -> URI. The source owns this policy; the index stores the result."""

search pages internally and yields rather than returning a list — a full-mission EMIT query is far larger than anything worth holding in memory, and CMR requires cursor-based paging past the first few thousand results anyway.

These are not science hooks

The five hooks in Writing plugins change the answer. GranuleSource and GranuleReader add a data source. A new instrument is a reader; a new archive is a source; neither changes what a mosaic means — which is why they are kept in a separate tier rather than swelling the list you have to understand to write a cost function.
