Deploying to AWS

Standing up a deployment, from an empty account to a bucket a manifest can write to. Running at scale explains what the executors are; this page is the runbook.

Where this gets you

A run whose every work item executes in Lambda, orchestrated from your laptop. The platform root creates a bucket, an image repository, a secret container and three roles; the deployment root creates the worker function from an image you build. What is not here: nothing survives closing the laptop yet, and nothing is scheduled — those are the third and fourth steps in What comes next. Status is the authority on what exists.

What you are building

One deployment serves many runs. A new experiment is a new manifest, never a new deployment (ADR-0002). The deployment is deliberately small:

ResourceWhyStatus
S3 bucketThe storage root. cache/, runs/ and products/ hang off itbuilt
ECR repositoryOne image, two entrypoints. Immutable tags, because deployments pin by digestbuilt
Secrets Manager secretThe Earthdata credential. Container only — the value never passes through Terraformbuilt
Three IAM rolesLambda worker, orchestrator task, task executionbuilt
Lambda functionRuns one work item — the same exec_item every executor callsbuilt
Log group and budgetExplicit retention, and an alarm before the first executionbuilt
ECS task definitionThe orchestrator, when a run should survive a closed laptopnot started

No EC2, and no Batch. Every work item in the reference run clears Lambda's 15-minute and 10 GB ceilings by one to three orders of magnitude, so there is no placement decision to make and nothing to provision. Running at scale has the measurements.

1. One private file

Everything account-specific lives in .env, which is gitignored. Nothing in the repository names an account, a profile, a bucket, or a site requirement.

cp .env.example .env
$EDITOR .env
VariableMeaning
AWS_PROFILEThe profile your login produces
AWS_REGIONus-west-2. Not a preference — the source data and Step Functions must share a region
STRATUM_DEPLOYMENTDeployment name, e.g. dev
STRATUM_PERMISSIONS_BOUNDARY_ARNSite requirement. Present but empty if your site imposes none
STRATUM_ROLE_NAME_PREFIXSite requirement. Present but empty if none
Empty is a valid answer; undefined is not

The two site variables have no defaults, on purpose. A site value that is missing must fail the plan loudly rather than quietly apply something the site would reject. Set them to "" when your site imposes no boundary or prefix — that is different from leaving them out, and the scripts tell you which you did.

2. Create the state bucket

Terraform keeps its state in S3, but cannot create the bucket that holds its own state. That chicken-and-egg is the entire reason this step exists — it creates a bucket and nothing else. No IAM, no roles, no site requirements.

make bootstrap

Idempotent, and safe to re-run. It enables versioning (the only recovery path from a corrupted state file), default encryption, and a public-access block.

The state bucket is a secret store

Terraform state contains every value Terraform touches, in plaintext JSON — including your site's permissions boundary and role prefix. That is true however those values are supplied, and it is why this bucket's access policy deserves the same care as the values themselves.

3. Apply the platform root

make stratum-infrastructure     # generates this root's backend.hcl from .env, then terraform init
make infra-plan     # read this before applying
make stratum-infrastructure    # PRIVILEGED — creates IAM roles

make stratum-infrastructure writes terraform/backend.hcl from .env plus the account id resolved at run time, so even the state bucket name is never hand-written or committed.

Each root has its own backend file, and its own state key

The deployment root is initialised separately with make stratum-infrastructure, which writes terraform/backend.hcl against key = deployment/terraform.tfstate. They are deliberately not one shared file: a shared one is rewritten on every init, so a hand-run terraform init -backend-config=… could point one root at the other root's state. If Terraform says backend initialisation is required, you are almost certainly in a root that has not been initialised yet — most often deployment/ after the platform root was already done.

Federated sessions expire mid-apply

If your login issues short-lived tokens, re-authenticate immediately before stratum-infrastructure and keep applies small. An apply that dies on an expired token is recoverable — the state is in S3 and locked — but it is an avoidable annoyance.

When it succeeds, make infra-output prints what the next slice consumes, including storage_root — the value a manifest's outputs.bucket will take.

Who applies what

One root, one state, one apply. There is deliberately no privileged and unprivileged split expressed in Terraform, because the two ways of expressing one are both bad:

ApproachWhy not
-target=…Terraform documents it as an escape hatch for exceptional recovery and warns that the plan is incomplete. Not a routine workflow
A count feature flag per groupWith one state file, applying with the flag off makes Terraform plan to destroy those resources
Two roots, two state filesWhat this had, and the cost was real: two inits, two backend files, and a terraform_remote_state dependency between them
AWS enforces the split, not the configuration

Everyone applies the same root and IAM decides what each person may change. In steady state this costs nothing: changing only the image digest produces a plan that touches only the function, so Terraform makes no IAM write call and a role without IAM rights succeeds anyway. Such a role needs broad read — a refresh describes every resource — and narrow write, which is an ordinary policy shape.

If an apply fails on an IAM permission, something privileged genuinely needs to change. That is information, not an obstacle: escalate rather than route around it.

A new selector is code, not configuration

Scorers resolve through entry points read from installed metadata, so a new scorer class must be in the image: make image, a new digest in .env, and make stratum-infrastructure. Choosing among registered scorers by name is a manifest edit and needs no deploy at all. Both sides of that line are in ADR-0002.

5. Site requirements

The whole mechanism is two Terraform variables with no defaults, filled from .env, consumed at the point of use:

resource "aws_iam_role" "lambda" {
  name                 = "${var.role_name_prefix}stratum-${var.deployment}-lambda"
  permissions_boundary = local.boundary       # null when the site imposes none
  assume_role_policy   = data.aws_iam_policy_document.assume["lambda"].json
}

A second site is a second .env, selected with STRATUM_ENV=…. If EC2 is ever needed, its site-specific parts — AMI or SSM parameter name, instance profile, VPC and subnet ids, Session Manager configuration — are more variables of the same kind, not a new mechanism.

6. The Earthdata credential

There are two independent credential chains in a cloud run, and only one of them is yours. Confusing them is the most common early mistake.

Your AWS identityNASA Earthdata
Issued byYour accountNASA URS / the DAAC
ReachesYour bucket, ECR, Lambdas3://lp-prod-protected/… — the granules
How a task gets itIts role, automaticallyFetched at run time from Secrets Manager, then exchanged
LifetimeRefreshed by the SDK~1 hour, and nothing refreshes it for you

Over HTTPS the Earthdata username and password are the whole story. For direct S3 access in-region the password is never used against S3: the DAAC's credentials endpoint is called with Earthdata authentication and returns temporary AWS credentials belonging to NASA, scoped to that bucket, valid about an hour. Those read the granules.

The value never passes through Terraform

Terraform creates the secret container and the policy that lets a role read it. There is deliberately no version resource — its absence is the mechanism. Anything passed through Terraform lands in state, and state lives in the bucket from step 2. Populate the value out of band with aws secretsmanager put-secret-value.

What to put in it

Key-value JSON — not the contents of a .netrc. The credential resolver tries two strategies in order: the netrc file, then the environment. A cloud worker has no .netrc, so it takes the environment path, and JSON keys map onto it directly:

Secret valueBecomesWhen
{"username": "…", "password": "…"}EARTHDATA_USERNAME and EARTHDATA_PASSWORDThe default. Same two values your ~/.netrc holds
{"token": "…"}EARTHDATA_TOKENAn Earthdata user token. Avoids storing a password, but tokens expire and must be renewed
 
./scripts/put-edl-secret.sh            # prompts for username and password
./scripts/put-edl-secret.sh token      # prompts for a token instead

It prompts without echoing, builds the JSON in Python rather than the shell so a password containing quotes or $ survives verbatim, and passes the value as file:// from a umask 077 temp file removed on exit. Passing --secret-string by hand instead would put the credential into your shell history and, briefly, into the process list.

Both shapes are already supported — no code change either way. Which one to standardise on is still open: the password pair is simpler, the token avoids holding a password but adds a renewal obligation.

Do not wire it into the function's environment block

It is tempting to pass the secret into the Lambda as a configured environment variable. Do not: a value in Terraform's environment block lands in Terraform state and in the function configuration, where anyone with lambda:GetFunction can read it. The handler fetches the secret at run time and sets the variables in its own process, before the first login.

Why plaintext netrc is the worse option

Storing the file's contents and writing them to /tmp/.netrc does work — the resolver honours $NETRC — but it puts credential material on a filesystem for no benefit, and Secrets Manager's console and rotation tooling both assume JSON. The one thing it buys, an identical code path to a laptop, you already have: the resolver tries netrc then environment on every platform, so a laptop and a Lambda differ only in which strategy answers first.

The one-hour expiry is why the orchestrator never reads granules — the workers do, and no worker runs past Lambda's 15-minute ceiling, so nothing on this path ever needs to refresh a NASA credential mid-read.

7. Build and push the worker image

make image

It builds for linux/arm64, logs in to the repository the platform root created, pushes, and prints the digest. That digest is the one thing the next step needs, so record it now — make image prints this line ready to paste:

echo 'STRATUM_IMAGE_DIGEST=sha256:<64 hex>' >> .env     # replacing any earlier line

Nothing else in the deployment changes when your code does. Every later build is make image, a new digest in .env, and make stratum-infrastructure.

PropertyWhy
The environment comes from pixi.lockThe same file your laptop resolves from, so the image cannot drift from the environment the tests ran in. GDAL comes from conda-forge; a second resolution is a second set of versions to be surprised by
arm64Graviton on Lambda, native on an Apple-silicon laptop, so the build needs no emulation
One image, two entrypointsWhich one you get is decided by whether $AWS_LAMBDA_RUNTIME_API is there to talk to — not by a second tag you have to remember
Tags are immutable, and a dirty tree is refusedA digest has to identify a commit somebody else can check out. ALLOW_DIRTY=1 overrides it, and stamps the tag so you can see what you did

What goes into it

Three Python distributions, all installed from pixi.lock, plus anything you drop in:

DistributionFromProvides
stratumpyproject.toml + src/stratum/The framework, the CLI, the two catalogue sources
stratum-emitplugins/stratum-emit/The EMIT readers, masks and scorers
spectral-utilvendor/SpectralUtil/The KD-tree nearest-neighbour search regrid uses
your pluginplugins/<name>/, or a wheel in plugins/wheels/Whatever it registers

The root pyproject.toml is the workspace manifest, and that is what ties them together. Its [project] table is the stratum distribution; its [tool.pixi.pypi-dependencies] table names the other two as path dependencies, and pixi.lock pins all of it:

[tool.pixi.pypi-dependencies]
stratum       = { path = ".", editable = true }
stratum-emit  = { path = "plugins/stratum-emit", editable = true }
spectral-util = { path = "vendor/SpectralUtil", editable = true }

So the Dockerfile copies those four things — the manifest, the lock, the sources — and runs pixi install --locked. Nothing in the image is resolved a second time, which is the property that stops it drifting from the environment your tests ran in.

Packaging a plugin has the two routes in and the whole pyproject.toml a plugin needs. Whichever you used, check the image before deploying it — this is "did my plugin make it in?", answered rather than assumed:

make image-local
docker run --rm stratum-dev:<tag> stratum plugins list

make image-local prints the exact docker run line for the tag it built.

Terraform never builds

make image builds and pushes; the deployment root points a function at the digest that produced. That split is what keeps an apply from needing Docker and a working copy, and it is what makes the deployed code identifiable from an immutable digest rather than from whatever was checked out when someone ran apply. ADR-0003 has the reasoning.

8. Apply the deployment root

make stratum-infrastructure
make infra-output   # prints the function name, and the command to run

This root creates no IAM, so anyone with bucket and image-repository write may apply it. It creates the worker function from your digest, a log group with explicit retention, a reserved-concurrency ceiling, and a monthly budget alarm scoped by the Deployment tag. It reads the platform root's outputs through terraform_remote_state, under its own state key.

SettingDefaultWhy that
Memory4 GBLambda gives CPU in proportion, so this is the compute knob too. A 720 × 720 block with up to 14 candidates measures well under 3 GB
Timeout900 sLambda's hard maximum. The slowest measured item is about 19 s; the margin is for a cold start plus a granule download
/tmp10 GBHolds the storage mirror and the staged granules. Lambda's maximum
Reserved concurrency64A guard rail, not a throughput target: it stops one run exhausting the account's Lambda concurrency and starving another
Log retention30 daysThe default for a log group is "never expire", which is a real line item at tens of thousands of invocations
Budget100 USD/monthAn alarm, not a cap — AWS does not stop the work. Set STRATUM_BUDGET_ALERT_EMAIL or nobody hears it

All six are platform settings. None of them is a manifest field, and changing one is an apply that touches no role.

If the apply fails

Four ways a first deployment goes wrong, and what each looks like.

MessageCause and fix
STRATUM_IMAGE_DIGEST is not setStep 7 has not run, or its digest never reached .env. The check is deliberate: there is nothing to deploy before there is an image
The image manifest, config or layer media type … is not supportedThe pushed reference is a manifest list, which Lambda refuses. make image passes --provenance=false to prevent exactly this; you get it by pushing with a bare docker buildx build --push instead
Lambda does not have permission to access the ECR imageRare in one account and expected across two. Add ecr:BatchGetImage and ecr:GetDownloadUrlForLayer for lambda.amazonaws.com to the repository policy — a change to the platform root, so a privileged apply
InvalidParameterValueException … concurrent executionsThe reserved concurrency (64) exceeds what is unreserved in the account. Lower reserved_concurrency, or raise the account limit. It is a guard rail, so lowering it costs only dispatch width
A budget with nobody subscribed

If STRATUM_BUDGET_ALERT_EMAIL is empty the budget is still created, and still tracks spend you can look at — but nothing is sent to anyone, which is most of the value. Set it before the first real fan-out; a runaway is otherwise discovered by the bill.

9. Run it

Two things beyond the manifest: the function name, and a manifest whose outputs.bucket is the deployment's bucket.

outputs:
  bucket: s3://stratum-dev-<account-id>/     # ./scripts/tf.sh platform output -raw storage_root
export STRATUM_LAMBDA_FUNCTION=$(./scripts/tf.sh deployment output -raw function_name)
stratum run -m manifest.yaml --executor aws

Every work item of every stage becomes one invocation. Your laptop dispatches and collects outcomes; it holds no state, because every result is in the bucket before the invocation returns. Losing the laptop loses the dispatch, never the work. --workers is how many invocations are in flight (default 32); the ceiling that actually binds is the function's reserved concurrency.

A local storage root is refused, by design

--executor aws with outputs.bucket: ./out stops before the first invocation and says so. A Lambda cannot read your laptop's filesystem, and the failure is much cheaper here than 700 invocations later.

When something fails, the outcome records are the same shape a local run writes — a handler exception included — so stratum status --run <id> --failed reads one format whichever executor produced it. The worker's own logs are in the log group make infra-output names.

How the storage root works

A bucket root gets a node-local mirror: every stage is handed a real path, so the read path is the same code as a local run — which matters because GDAL and netCDF4 want a file, and Lambda has 10 GB of /tmp against blocks of about 1 GB. A cache probe that misses locally probes the bucket before it is a miss, so whoever computed an artifact, every other worker gets a hit. A mirror is a cache and never the record: delete it and a worker recovers everything from the bucket.

S3 has no rename, so a directory artifact commits by writing its members first, then .members.json — its own list of what it covers — then the .inputs.json sidecar. A hit needs the sidecar and every listed member, which is how a prefix that lost an object is told from a complete artifact. Caching & reruns explains why a partial artifact at a key is the one corruption content addressing cannot detect.

Pointing a run at the deployment is a one-field change — the executor is never a manifest field, so the same science runs in both places:

outputs:
  bucket: s3://stratum-dev-<account-id>/     # was: ./out

Keeping it out of git

The repository is designed so that a clone contains nothing account-specific. The ignore rules are what keep it that way.

IgnoredWhy
.envThe one private file. .env.example is committed
*.tfvars, *.tfvars.jsonThe likeliest place for a value to be typed by hand
terraform.tfstate*Local state should never exist; if it does it must never be committed
backend.hcl (in each root)Generated, and names the account
.terraform/, crash.*.logProvider binaries; crash dumps embed variable values

The provider lock file is committed

.terraform.lock.hcl is the Terraform peer of pixi.lock. Excluding it defeats reproducible plans, so it is deliberately not ignored.

Teardown

terraform destroy deliberately will not take the data bucket: it carries prevent_destroy, because the cache is expensive to rebuild and the products are the deliverable. A genuinely clean slate needs a manual step, which is the intended friction. Everything else in a deployment is reconstructible from this repository — which is what makes an experimental deployment safe to tear down at all.
