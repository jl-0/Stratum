Running a mosaic

Write a manifest, check what it would cost, submit it, collect the output.

The workflow

# 1. See what would run. Reads (or, for a directory of granules, builds) the index; starts nothing.
stratum plan -m manifest.yaml

# 2. Run it. On this machine, by default; everything lands under outputs.bucket.
stratum run -m manifest.yaml

# 3. Read the report. --run is the run directory, or the run id under --root.
stratum report --run cuprite-2024-3f9a1c2e --root ./out

The manifest is the entire interface. It is versioned in git, reviewed like code, and hashed into the provenance record — so a run can be traced back to the exact document that produced it.

This runs on your machine

Stratum is an ordinary Python package. stratum run executes the whole pipeline locally by default — no cloud account, no cluster, no infrastructure to stand up. Storage is a directory instead of a bucket: outputs.bucket is a path, relative to the manifest, and cache/, runs/ and products/ are created under it.

Bigger runs change where the work is dispatched, not the code, the manifest, or the result: --executor slurm or --executor aws. Neither is built yet; both refuse with their spec section. See Running at scale.

A minimal manifest

Enough to produce a single-epoch mosaic of one area from granules you already have on disk, preferring the most nadir look. This is the shape the first trial run used (examples/trial-nevada/manifest.yaml in the repository):

run_id: cuprite-2024

grid:
  crs: EPSG:4326
  resolution: [0.000277778, -0.000277778]   # one arcsecond
  origin: [-180, -90]
  tile_size: 1.0
  block: 720

aoi:
  zones: [cuprite-nv]
  registry: ./zones.yaml    # zone name -> [w, s, e, n]; or use bbox: / tiles: instead

time:
  start: 2024-01-01
  end:   2025-01-01         # half-open: [start, end)
  epoch: P1Y                # one epoch = one vote; here there is only one
  deliver: P1Y              # so no temporal reduction happens at all

inputs:
  index: ./index.parquet    # built here by `stratum plan` if it does not exist
  source:                   # how the index is built; never read by a run
    kind: local
    root: ./granules
    patterns:               # {collection: {asset: glob}}; the granule id is what * matched
      EMITL2BMIN:
        MIN: "EMIT_L2B_MIN_001_*.nc"
      EMITL1BOBS:
        OBS: "EMIT_L1B_OBS_001_*.nc"
  roles:
    geometry: {collection: EMITL1BOBS, var: obs}
    mineral:
      collection: EMITL2BMIN
      var: group_1_mineral_id
      class_table: {source: embedded, path: /mineral_metadata, key: index,
                    attributes: [name, record, library, group, url]}
  band_aliases:
    view_zenith: {role: geometry, band: 2}    # 0-based; 2 = to-sensor zenith

granule_filter: []          # a directory has no cloud fraction; a cloud filter would refuse everything

pixel_mask:
  - {ref: edge_trim, columns: 7}

scorer:
  ref: min_view_zenith

snapshot:
  name: cuprite-v1
  layers:
    mineral:
      kind: categorical
      source: mineral
      classes: source          # adopt the granules' own class table; no lumping
      aggregate: {method: vote, ignore: []}   # see the note below

outputs:
  bucket: ./out             # the local root; s3:// is the same layout, not yet supported
  formats: [cog]
  stac: true
  render:
    mineral: {mapper: categorical, on_unmapped: grey}

budget:
  max_tiles: 4
  max_granules: 500
  max_vcpu_hours: 20
  on_exceed: fail
One epoch and ignore

With a single epoch, ignore: [none] turns every cell that was observed and had nothing identified into nodata — the vote has nothing left to count. Say ignore: [] for a single-epoch product so class 0 is delivered as itself; reach for ignore when there are several epochs to vote over.

The snapshot block says what each epoch records and how epochs combine. With a single epoch every aggregation is the identity, so this run is a plain mosaic; shorten epoch below the time range when you want a vote through time. See what the snapshot carries.

The full field list is in the manifest reference.

inputs.index is the only input a run touches. inputs.source says how that index is built — here from a directory of files you already have, which is what makes this manifest runnable with no network and no Earthdata account. Point it at NASA's archive instead and nothing else in the document changes; see Reading data.

Check before you run

stratum plan resolves everything and provisions nothing. It reports the real fan-out — tiles × epochs × blocks × granules — before a worker starts, and writes the run directory ({bucket}/runs/{run_id}/) with the merged manifest, the frozen index, plan.json, the work lists and report.md. The report is what it prints:

$ stratum plan -m manifest.yaml

# Stratum plan report: cuprite-2024-3f9a1c2e

- manifest_hash: `sha256:3f9a1c2e…`
- run_dir: `…/out/runs/cuprite-2024-3f9a1c2e`

## Selection

- granules in AOI x time: 14
- granules after filters: 14 (28 index rows)

| filter | removed | on_missing |
|---|---|---|
| meets a tile of the AOI | 0 | - |
| provides an asset for every role read ['geometry', 'mineral'] | 0 | - |

### Build versions consumed
- `010635`: 14 granule(s)

### Class-table fingerprints (the vintage check)
- mineral: `sha256:fc392354…` on 14 granule(s)

## Fan-out

| stage | work items |
|---|---|
| regrid | 14 |
| resolve | 25 |
| reduce | 25 |
| publish | 1 |

## Budget

- tiles: 1 / 4
- granules: 14 / 500
- vcpu hours: not estimated / 20.0
- status: within budget (on_exceed: fail)

Exit code 2 means the plan is valid but over budget; the run directory is still written so you can read why. vCPU-hours are not estimated yet — only the tile and granule ceilings gate.

Review this in the pull request

Attach the dry-run output to the same PR as the manifest diff. The difference between one zone and the globe is one line of YAML, and the plan output is where that shows up before it costs anything.

Budgets

The budget block is required and cannot be infinite.

budget:
  max_tiles: 64
  max_granules: 12000
  max_vcpu_hours: 400
  on_exceed: require_approval      # require_approval | fail | warn

With require_approval, a run that exceeds a ceiling pauses before it provisions anything and waits for a human. Approve or reject it with:

stratum approve --run cm-zones-2026-annual-r3
stratum reject  --run cm-zones-2026-annual-r3

Those two commands are not built yet, so today require_approval behaves like fail and says so. warn reports the exceedance and proceeds; use it when you have read the plan and mean it.

Selecting granules

Filters run against the index before any pixel is read, so rejecting early is free. They apply in order, and each one's effect is counted and reported.

granule_filter:
  - {max_cloud_fraction: 0.5, on_missing: fail}
  - {max_solar_zenith: 70}
  - {build_version: "010635"}                     # optional — see below
  - {month_in: [8, 9, 10, 11]}                    # recurring seasonal window

The built-in predicates are max_cloud_fraction, max_solar_zenith, month_in, build_version, product_version, collection_version and day_night; a {ref: …, params: …} entry names a filter plugin. Two selection steps run after your filters and appear in the report as rows of their own: granules that meet the query box but no tile of the area are dropped, and so are granules lacking an asset for a role the run will read — a mineral granule with no matching geometry file, say.

Absolute versus seasonal windows

time.start / time.end give you an absolute interval. month_in gives you a window that recurs — August-to-November over several years, avoiding peak vegetation without discarding whole years. The two compose: the time range bounds the run, the month filter selects within it.

Missing metadata is a decision you make

Every filter that reads an optional field takes an on_missing policy:

ValueEffect on a granule whose field is absent
failPlan-time error naming the granules. Default.
rejectDropped, and counted separately in the report
keepPasses the filter, and counted separately in the report

The default is fail because a granule with no cloud metadata and a granule that is too cloudy are different situations, and silently merging them loses data with no signal. If you know which you want, say so.

Mixed vintages are refused

Checked at plan time

Stratum fingerprints the class table embedded in every contributing granule. If they do not all agree, stratum plan fails unless the manifest explicitly opts in with allow_mixed_vintage: true and a mixed_vintage_reason, and then only when every table resolves into an explicit classes file — classes: source cannot span vintages.

Upstream reprocessing regenerates products and can shift class definitions. A run that spans a reprocessing boundary blends two incompatible products into a result that looks entirely plausible and is not. Nothing in the data announces the problem, so Stratum refuses rather than warns.

The check is on the class table, not on a build number. One collection already carries eight software builds with no change to its classes, so build_version is a filter you may apply and never the guard. The plan output states every build the run consumed and the fingerprint it validated.

Masking pixels

Masks compose by conjunction — a pixel is eligible only if every mask admits it — and are applied in resolve as each observation is read, so masked pixels never enter the observation stack. Regrid does not see them, which is why changing a mask never rebuilds geometry.

pixel_mask:
  - {ref: edge_trim, columns: 7}
  - {ref: l2a_standard, flags: [cloud, cirrus, water, spacecraft]}
  - {ref: soil_fraction, min_soil: 0.65}

Masks say unusable, not worse. If you want to express a preference between two usable observations, that is a scorer, not a mask.

Running variants

A variant is a patch on a base manifest, not a copied file that drifts out of sync:

stratum plan -m base.yaml -p zones-pilot -p scorer-v3

Patches merge in the order given, before validation, so the merged document is what gets validated and hashed. Lists replace rather than append. Patch composition is not built yet — -p is refused — so for now a variant is a second manifest file.

Because cached geometry does not depend on your scorer, running several competing cost functions over the same area costs roughly one regrid plus n cheap passes. Comparing scorers is meant to be routine; see Caching & reruns.

What you get back

{outputs.bucket}/products/{run_id}/
  collection.json                   # STAC collection over every tile x period
  {tx}_{ty}/{start}_{end}/          # e.g. -118_41/20260601_20260701/
    {band}.tif                      # one file per delivered band: mineral.tif,
                                    #   mineral_agreement.tif, mineral_runner_up.tif, n_epochs.tif ...
    {name}_rgba.tif                 # RGBA rendering, one per outputs.render entry
    {name}_legend.json              # its legend: class table or ramp stops
    classes.json                    # the product's class table
    item.json                       # STAC item

{outputs.bucket}/runs/{run_id}/
  manifest.merged.yaml              # the document that was hashed
  index.parquet                     # the frozen granule set
  plan.json                         # everything a worker needs beyond the manifest
  work/{stage}.jsonl                # the work lists
  work/{stage}.results.jsonl        # per-item outcomes: ok, key or error, cache hit, seconds
  report.md                         # the human-readable summary
  provenance.json                   # what ran, against what

Categorical bands are uint16 with nodata 65535 — class 0 is a real value, "observed, nothing identified". Continuous bands are float32 with NaN nodata; counts are uint16 with no nodata. The data product always ships alongside the image. Re-rendering with a different mapper without re-running the pipeline (stratum render) is specified but not built yet.

Reading the report

stratum report prints report.md: how many granules each filter removed; the builds consumed and the class-table fingerprint validated; work items per stage; the budget verdict; and, once the run has executed, items, cache hits and seconds per stage. stratum status --run … --failed lists failed items with their errors.

A diff against the previous run of the same manifest lineage is specified but not built. It is the most useful check in practice — "this run selected 812 fewer granules than the last one" is how you catch an upstream reprocessing or an index change before it becomes a mystery in the product — so until it exists, compare the two reports' selection sections.

Reproducing a run

Every run is reproducible from its manifest hash. The provenance record pins the frozen granule index, the container image by digest, the plugin wheel by content hash, and the content version of every ancillary source.

stratum run --from-provenance ./runs/cuprite-2024/provenance.json

This re-runs against the frozen index rather than re-querying, so it reproduces the original result rather than asking the same question of a catalogue that has since changed. It works across executors too — a run planned locally can be reproduced on a cluster, and vice versa. The flag is not built yet; today, re-running the same manifest against the same index gives the same run_id and hits every cached artifact.

When one machine is not enough

Nothing about the pipeline changes; only the dispatcher does. Blocks are already sized to fit a single worker, so the same code path runs everywhere.

stratum run -m manifest.yaml --executor slurm --max-concurrent 64
stratum run -m manifest.yaml --executor aws

The cache is content-addressed and shared, so a run you started locally and stopped can be finished on a cluster — completed items are hits and get skipped. Neither executor is built yet; what exists is the seam they will use, stratum exec --plan DIR --stage STAGE --index N, which runs one work item and is what an array task will call. See Running at scale.
