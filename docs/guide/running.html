Running a mosaic

Write a manifest, check what it would cost, submit it, collect the output.

The workflow

# 1. See what would run. Reads the index; provisions nothing.
stratum plan -m manifest.yaml

# 2. Run it.
stratum submit -m manifest.yaml

# 3. Watch it.
stratum status --run cm-zones-2026-annual-r3

# 4. Read the report.
stratum report --run cm-zones-2026-annual-r3

The manifest is the entire interface. It is versioned in git, reviewed like code, and hashed into the provenance record — so a run can be traced back to the exact document that produced it.

A minimal manifest

Enough to produce a single-epoch mosaic of one area, preferring the most nadir look:

run_id: cuprite-2024

grid:
  crs: EPSG:4326
  resolution: [0.0003, -0.0003]
  origin: [-180, -90]
  tile_size: 1.0
  block: 512

aoi:
  zones: [cuprite-nv]

time:
  start: 2024-01-01
  end:   2024-12-31
  epoch: P1Y
  deliver: P1Y

inputs:
  index: s3://emit-l3/index/emit-granules.parquet
  roles:
    geometry: {collection: EMITL1BOBS, var: obs}
    mineral:
      collection: EMITL2BMIN
      var: group_1_mineral_id
      class_table: {source: embedded, path: /mineral_metadata, key: index,
                    attributes: [name, record, library, group, url]}
  band_aliases:
    view_zenith: {role: geometry, band: 5}

granule_filter:
  - {build_version: b0107_v02}
  - {max_cloud_fraction: 0.5, on_missing: fail}

scorer:
  ref: min_view_zenith

outputs:
  bucket: s3://emit-l3-products
  formats: [cog]
  stac: true

budget:
  max_tiles: 4
  max_granules: 500
  max_vcpu_hours: 20

No reducer block means no temporal reduction — the single epoch passes through unchanged. Add one when you want to combine epochs; see Writing plugins.

The full field list is in the manifest reference.

Budgets

The budget block is required and cannot be infinite.

budget:
  max_tiles: 64
  max_granules: 12000
  max_vcpu_hours: 400
  on_exceed: require_approval      # require_approval | fail | warn

With require_approval, a submitted run that exceeds a ceiling pauses before provisioning compute and waits for a human. Approve or reject it with:

stratum approve --run cm-zones-2026-annual-r3
stratum reject  --run cm-zones-2026-annual-r3

Selecting granules

Filters run against the index before any pixel is read, so rejecting early is free. They apply in order, and each one's effect is counted and reported.

granule_filter:
  - {build_version: b0107_v02}                    # required — see below
  - {max_cloud_fraction: 0.5, on_missing: fail}
  - {max_solar_zenith: 70}
  - {month_in: [8, 9, 10, 11]}                    # recurring seasonal window

Absolute versus seasonal windows

time.start / time.end give you an absolute interval. month_in gives you a window that recurs — August-to-November over several years, avoiding peak vegetation without discarding whole years. The two compose: the time range bounds the run, the month filter selects within it.

Missing metadata is a decision you make

Every filter that reads an optional field takes an on_missing policy:

ValueEffect on a granule whose field is absent
failPlan-time error naming the granules. Default.
rejectDropped, and counted separately in the report
keepPasses the filter, and counted separately in the report

The default is fail because a granule with no cloud metadata and a granule that is too cloudy are different situations, and silently merging them loses data with no signal. If you know which you want, say so.

Vintage pinning is required

Required

A run must pin a product vintage. If the frozen granule set spans more than one, stratum plan fails unless the manifest explicitly opts in with allow_mixed_vintage: true and a documented reason.

Upstream reprocessing regenerates products and can shift class definitions. A run that spans a reprocessing boundary blends two incompatible products into a result that looks entirely plausible and is not. Nothing in the data announces the problem, so Stratum refuses rather than warns.

The plan output always states the vintage or vintages selected.

Masking pixels

Masks compose by conjunction — a pixel is eligible only if every mask admits it — and are applied during regrid, so masked pixels never enter the observation stack.

pixel_mask:
  - {ref: emit.masks:EdgeTrim, columns: 7}
  - {ref: emit.masks:L2AStandard, flags: [cloud, cirrus, water, spacecraft]}
  - {ref: emit.masks:SoilFraction, min_soil: 0.65}

Masks say unusable, not worse. If you want to express a preference between two usable observations, that is a scorer, not a mask.

Running variants

A variant is a patch on a base manifest, not a copied file that drifts out of sync:

stratum plan -m base.yaml -p zones-pilot -p scorer-v3

Patches merge in the order given, before validation, so the merged document is what gets validated and hashed. Lists replace rather than append.

Because cached geometry does not depend on your scorer, running several competing cost functions over the same area costs roughly one regrid plus n cheap passes. Comparing scorers is meant to be routine; see Caching & reruns.

What you get back

s3://{bucket}/products/{run_id}/
  {tile}/
    {tile}_{period}_data.tif        # bands your reducer declared
    {tile}_{period}_image.tif       # RGBA rendering
    {tile}_{period}_legend.json     # class table or ramp stops
    {tile}_{period}.json            # STAC item

s3://{bucket}/runs/{run_id}/
  index.parquet                     # the frozen granule set
  provenance.json                   # what ran, against what
  report.md                         # the human-readable summary
  failures.jsonl                    # per-item outcomes, if any

The data product always ships alongside the image. If you only want to change how it looks, you do not need to re-run anything:

stratum render --run cuprite-2024 --mapper my_colours

Reading the report

stratum report answers, without opening JSON: how many granules each filter removed and why; cache hit rate by artifact type and what a rerun would cost; which blocks failed; cost against budget; and a diff against the previous run of the same manifest lineage.

That last one is the most useful in practice. "This run selected 812 fewer granules than the last one" is how you catch an upstream reprocessing or an index change before it becomes a mystery in the product.

Reproducing a run

Every run is reproducible from its manifest hash. The provenance record pins the frozen granule index, the container image by digest, the plugin wheel by content hash, and the content version of every ancillary source.

stratum submit --from-provenance s3://.../runs/cuprite-2024/provenance.json

This re-runs against the frozen index rather than re-querying, so it reproduces the original result rather than asking the same question of a catalogue that has since changed.
