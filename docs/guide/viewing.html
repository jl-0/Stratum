Viewing products

A published products tree is a STAC catalogue, so looking at it needs no configuration — point a viewer at the root and it finds the runs, the layers and the colours on its own.

Looking at a run on your machine

stratum preview --root out

That serves a map on http://127.0.0.1:8787/ and opens it. Three pickers: run is the run directories under products/, layer is the assets each item declares, and basemap is the imagery underneath. Nothing about the run is configured anywhere — a run that delivers a new band shows it in the layer list.

--root takes either the storage root or the products directory inside it, and it takes a bucket:

stratum preview --root s3://my-bucket/

Over a bucket it reads with your own credentials and copies each raster into a local mirror the first time a tile needs it, so the first look at a tile is slow and every later one is not. The catalogue itself is read without fetching a single raster.

The server binds to loopback and has no authentication. It is a development tool. A path from a URL cannot leave the products root, but do not put it on a public address.

Reading a point

Click anywhere on the map. The popup reports every band the run delivered at that point — not just the layer being drawn — with class names resolved and raw values beside them:

mineral_1              Goethite_Thin_Film WS222 W1R1Ba (8)
mineral_1_agreement    0.6667
mineral_1_runner_up    nHematit+fg-Goethit 34B2+MPC W1R1Hb (46)
depth_1                0.02843
n_epochs               3

This is usually faster than the legend, and it is the only practical way to read a map with a few hundred classes whose colours are necessarily close together. The number is shown next to the name because they are different facts: the name comes from the product's own class table, the number is what is in the pixel.

Which bands are categorical is not guessed from the band name. Published items carry the STAC Classification extension, and each categorical band declares its own classification:classes — so mineral_1_runner_up is named and mineral_1_agreement, which merely shares a prefix, is not.

The legend also takes a filter, for when you want to go the other way and find a class you can name.

What the layers mean

Asset roleDrawn as
visual — a published renderingStraight through. The colours are the ones publish wrote into the image; the viewer chooses nothing.
data, with a legend asset beside itEach value looked up in that legend. Resampled nearest, always — averaging class ids would invent classes nothing identified.
data, continuousStretched between the band's 2nd and 98th percentile through a colour ramp. Averaged when zoomed out, which is what makes a whole tile readable.

Two values are always transparent: the band's nodata, and — in a categorical band — class 0. Those are different facts, and drawing either one would hide the difference:

nodata is nothing observed this cell. Class 0 is observed, and nothing was identified. A viewer that painted class 0 would make an area that was looked at and found empty indistinguishable from one that was never looked at.

Handing someone a URL

The same server, run as a Fargate task inside your VPC. It reads the bucket with the task role and serves the map on its own private IP, so nothing about the bucket changes: no public access, no website hosting, no bucket policy, no CORS.

make viewer-up      # start one; prints its URL
make viewer-url     # the URL of whatever is already running
make viewer-down    # stop it
make viewer-logs    # tail the container log

There is no service and no load balancer, so the address is the task's own private IP and it changes each time you start one. Nothing runs, and nothing is billed, between looks.

What it needs once

One site input in .env, and it is the deployment's, not the viewer's — the same VPC will carry the data plane when that arrives. Leave it empty and no workload that needs a network is created:

STRATUM_VPC_ID=vpc-0a1b2c3d

Then make stratum-infrastructure creates the cluster, the log group, the task definition and a security group. The task runs in the VPC's subnets, reuses the task and task-exec roles the deployment already has, and is never given a public IP. There are no other network settings.

The security group

Created here rather than asked for, because it is the only network control in front of a server with no authentication of its own, and a group inherited from elsewhere is a group whose rules this deployment cannot see. Three rules:

DirectionRuleWhy
inTCP 8787 from anywherethe viewer. The control is the port, not the source — with no public IP, "anywhere" is whatever can route to the task
outTCP 443 anywhereECR, S3 and CloudWatch Logs — whether by NAT or by VPC endpoint, all of it is HTTPS
outTCP + UDP 53 to the VPC CIDRthe VPC resolver. Without it the task resolves none of the above and fails in a way that reads like a routing problem

Terraform drops the allow-all egress rule AWS adds to a new group by default, so that list is the whole of it. The task cannot reach anything else.

The preview server has no authentication, in the task exactly as on your laptop, and the group admits the port from any source that can route to it — the VPC, and whatever is peered, VPN'd or attached to it. Anything that reaches the port can read every product in the bucket. Stop the task when you are done; that, and the absence of a public IP, are what bound the exposure.

One image, two pins

The viewer runs the same image as the worker — the entrypoint runs any command when it is not under the Lambda runtime, so there is nothing viewer-specific in it. What is separate is when the digest moves:

STRATUM_IMAGE_DIGEST=sha256:aaa...          # the worker, and the viewer with it
STRATUM_VIEWER_IMAGE_DIGEST=sha256:bbb...   # the viewer only; empty tracks the worker

Leave the second empty and both run the same bytes, which is what you want most of the time. Set it when the worker is pinned for a campaign and you still want to rebuild the viewer, so a viewer rebuild cannot repoint a worker you have frozen. make image prints one digest either way; which line it lands on is the decision.

The task definition pins a digest, so make viewer-up is a start button, not a deploy. Editing the viewer and starting a task runs the old code. Shipping a change is make image, the new digest into .env, then make stratum-infrastructure. viewer-up and viewer-url print the digest they are running so you can tell. For iterating, use make viewer locally against the same bucket.

The preview server has no authentication, in the task exactly as on your laptop. Anything that can reach the port can read every product in the bucket. The security group is the only thing standing in front of it, so scope it to the range you browse from and stop the task when you are done.

Why a task and not a static page in the bucket. A browser cannot sign an S3 request, so serving the products directly to one means granting anonymous GetObject on the prefix — and the products sit in the same bucket as cache/ and runs/, behind a public access block. The task sidesteps the question entirely: it signs the requests itself with the task role, and speaks plain HTTP only to your VPC.

What it is not

It is a way to look at products, not a way to serve them. There is no styling beyond the ramp picker, no per-pixel inspection, no time slider, and no way to compare two runs side by side — the run picker swaps one for the other. It reads the products tree and never writes to it, so nothing you do in the viewer can change a run.
