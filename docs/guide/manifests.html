Authoring a manifest

A manifest says what to mosaic, from what, and how a cell picks its winner. Everything else — which files are downloaded, what a scorer sees, what gets rebuilt when you change your mind — follows from it.

How data reaches a scorer

The single most useful thing to hold in your head is that four manifest blocks form one chain, each answering a different question at a different time.

BlockQuestion it answersWhen
inputs.source.patternsWhich files exist, for every granule?stratum index build
inputs.rolesWhich of those files, and which variable inside, does this run read?stratum plan
inputs.band_aliasesWhich single band of a role do I want to name?stratum plan
auxWhat do I need that is not an observation at all?stratum plan

obs is not a file. It is assembled per granule per block, and its keys are exactly the names you wrote under roles and band_aliases — one namespace, so a name that appears in both is a validation error.

Why patterns is separate from roles

patterns is a discovery filter, shaped {collection: {asset: glob}} and matched against each catalogue record's file names. A file matching no glob is never indexed, and therefore can never be downloaded.

patterns:
  EMITL2BMIN:
    MIN:       "EMIT_L2B_MIN_001_*.nc"
    MINUNCERT: "EMIT_L2B_MINUNCERT_001_*.nc"
  EMITL1BRAD:
    OBS:       "EMIT_L1B_OBS_001_*.nc"     # RAD is not listed, so it is invisible
That one rule is load-bearing

An EMITL1BRAD record contains a 1.85 GB radiance file beside the small geometry file. Listing only the OBS glob is the entire mechanism that keeps the big one off the network — not a special case, not a size check.

roles is a reading binding: of the files the index knows about, which one and which variable, under a name your plugins use. You may index more than you read — that costs only metadata. You may not read what you did not index, and the planner refuses that rather than letting a worker discover it.

This is also why widening patterns forces an index rebuild: the index records the collections, area and time range it was built for, and a run refuses an index built for less.

A granule is an acquisition, not a file

Several collections publish products derived from the same overpass. They share a granule id, and the index merges their rows into one record whose assets are keyed {collection}/{asset}. So a single obs can hold four files:

obs[...]Declared asComes from
mineralrole → EMITL2BMIN, var group_1_mineral_idEMIT_L2B_MIN_001_*.nc
mineral_depthrole → EMITL2BMIN, var group_1_band_depththe same file
geometryrole → EMITL1BRAD, asset OBSEMIT_L1B_OBS_001_*.nc

solar_zenithalias → geometry band 4the same array
frcovrole → EMITL2BFRCOV, asset FRCOVBAREEMIT_L2B_FRCOVBARE_001_*.tif
Use the same globs everywhere

The granule id is what the first asset's wildcards matched. So EMIT_L2B_MIN_*.nc yields 001_2026… while EMIT_L2B_MIN_001_*.nc yields 2026… — and two collections globbed inconsistently produce ids that do not match, so their rows never merge. You get twice as many granules, each missing half its roles, and every one fails the missing-role check with a confusing message.

Roles, aliases, and when you need which

A role reads a whole variable. EMIT's obs variable is (downtrack, crosstrack, 11) — eleven geometry bands in one array — so obs["geometry"] is (H, W, 11), which is not what a scorer wants. A band alias names one band of it:

band_aliases:
  view_zenith:  {role: geometry, band: 2}   # 0-BASED
  solar_zenith: {role: geometry, band: 4}

Two reasons this is not simply another role:

  • Cost. An alias slices an array that has already been read. Eleven roles on one variable would be eleven reads of the same file.
  • Portability. The scorer says obs["solar_zenith"]; the manifest says which band that is for this instrument. Point the same scorer at a different sensor and only the manifest changes.

For spectra, where counting bands is hopeless, name the band by an attribute the reader reports instead. The planner resolves it to an index at plan time and fails unless exactly one band matches:

band_aliases:
  swir_2200: {role: reflectance, match: {wavelength: 2200}, tolerance: 10}

A single-band variable needs no alias. frcov is one band, so obs["frcov"] works directly. Reach for an alias only when the variable has a band axis.

Roles or aux?

Both arrive at a plugin as arrays on its block, which is what makes them easy to confuse. The test is one question: would this be a different file for a different granule?

A roleAn aux source
What it isAn observation — part of the acquisition being scoredAnything else: a DEM, a landcover map, claim polygons
Declared ininputs.roles: collection, asset, variableaux: one URI or several, a kind, a resampling method
Resolved throughThe frozen index, per granuleThe manifest, once for the run
Read asobs["frcov"]aux.raster("landcover")
Declared by a plugin asrequired_rolesrequired_aux
Varies perGranuleNothing

EMIT's fractional cover is a role, even though it is a different collection from the mineral product, because it is the same overpass of the same ground at the same moment. ESA WorldCover is aux, because it would be the same map whichever granule you were scoring.

A role can still need warping. Ortho-native products such as L2B FRCOV ship already on a map grid, so they have no sensor geometry and no lookup table, and the framework warps them onto the block directly. From inside a plugin that looks like aux — but it is still per-granule, still found through the index, and still carries the granule's checksum into the cache key. Such a role must declare resampling; a sensor-space role must not.

What an input dataset has to provide

Stratum is built around a catalogue — CMR today. That tie-in is what makes it useful, and it is also what it requires. A loose directory of files you want merged is better served by a different tool; what follows is what a dataset must carry to be usable here.

For discovery

Every granule, in every collection, needs each of these. They are the non-nullable columns of the index, so a source that cannot supply one cannot index that granule at all.

NeededFrom CMRFrom a local directory
A stable granule id, identical across every collection of the same acquisitionWhat the first asset's glob wildcards matchedThe same rule, on filenames
Time coverage (start and end)TemporalExtent.RangeDateTimetime_coverage_start / _end in the ACDD header
A footprint — a polygon, or at least a bounding boxSpatialExtent: a GPolygon, else a BoundingRectangleThe four *most_longitude / *most_latitude attributes
One URL per assetRelatedUrls, type GET DATAThe file path
A checksum per asset (strongly wanted)Published per fileNone — recorded honestly as absent
Cloud fraction, build and product versions (optional)CloudCover and additional attributesHeader attributes, when present
A missing checksum is a real hole, not a nuisance

An asset's catalogue checksum is what enters the cache key as that observation's identity. Without one, a granule re-delivered under the same id with new bytes reads as a cache hit forever. A local source records no checksums and says so; a catalogue source is what makes reprocessing safe.

For reading

  • A reader registered for the collection. Readers are selected from what a role declares, never from what a file is called. Readers ship in a plugin package; stratum plugins list shows what an environment provides.
  • Declared fill values. The reader resolves them to a mask, so nothing above it ever sees a sentinel. A product that encodes "missing" as a magic number nobody declared will silently average it in.
  • At least one sensor-space role, with per-pixel latitude and longitude. This is the geolocation role, and the lookup table built from it is what decides which granules reach which block. A run in which every role is ortho-native is refused at plan time.
  • A CRS on every ortho-native input. There is nothing to warp from without one.
  • An embedded class table, for any categorical layer whose classes come from the product rather than from a checked-in file — matched on attributes, never on the integer.

For a run that means anything

  • Every collection agrees on the granule id. Check it before trusting a run: the index prints one row count per collection and one granule count overall, and the granule count should not be the sum.
  • Every sensor role shares one sensor array shape. One lookup table indexes one sensor grid, so roles read together must agree; the planner checks this against real headers.
  • Class tables agree across granules, by fingerprint, unless you opt out explicitly. Mid-reprocessing archives are mixed-vintage and will otherwise blend two incompatible products into something entirely plausible.

Walkthrough: the bare-earth manifest

examples/emit-cmr-cuprite/manifest-bare-earth.yaml scores 18 tiles around Cuprite over all of 2025 on how much bare ground a pixel actually shows, rather than on where the sensor was looking — twelve monthly votes reduced to one annual product. It is the smallest manifest that uses every input path at once, so it is worth tracing end to end.

1. What it declares

inputs:
  source:
    patterns:
      EMITL2BMIN:   {MIN: "EMIT_L2B_MIN_001_*.nc", MINUNCERT: "..."}
      EMITL2BFRCOV: {FRCOVBARE: "EMIT_L2B_FRCOVBARE_001_*.tif"}
      EMITL1BRAD:   {OBS: "EMIT_L1B_OBS_001_*.nc"}
  roles:
    geometry: {collection: EMITL1BRAD, asset: OBS, var: obs}
    mineral:  {collection: EMITL2BMIN, var: group_1_mineral_id, class_table: {...}}
    frcov:
      collection: EMITL2BFRCOV
      asset: FRCOVBARE
      var: EMIT_L2B_FRCOVBARE     # the BAND DESCRIPTION, not an index
      resampling: bilinear        # required: this role is ortho-native
  band_aliases:
    solar_zenith: {role: geometry, band: 4}

aux:
  landcover:
    uri: https://esa-worldcover.s3.eu-central-1.amazonaws.com/…_N36W120_Map.tif
    kind: categorical
    resampling: mode

scorer: {ref: prefer_bare_earth, params: {hard_floor: 0.65, sun_weight: 0.25}}
pixel_mask:
  - {ref: edge_trim, columns: 7}
  - {ref: landcover, exclude: [water, built-up, tree]}

2. Index build — metadata only

CMR is searched once per collection, over the manifest's box and time range. Each record's file names are matched against that collection's globs; anything unmatched is not indexed and can never be fetched.

wrote index/granules.parquet: 300 row(s), 105 granule(s)
  EMITL1BRAD    105 row(s)  105 with checksums
  EMITL2BFRCOV   90 row(s)   90 with checksums
  EMITL2BMIN    105 row(s)  105 with checksums

300 rows, 105 granules — that gap is the id merge working. Had the three collections disagreed on ids you would see 300 granules, and every one would be missing two of its three roles. Fifteen granules have no fractional cover; they are exactly the fifteen the cloud filter drops anyway, so requiring the role costs nothing here. Not a byte of pixel data has moved.

3. Plan — where cheap failures happen

The plan selects granules, applies the filters, freezes the survivors, and only then opens real files to check the manifest against the data: that each role's variable exists, that the sensor roles agree on shape, that every granule's class table has the same fingerprint. It also stages, digests and warps every aux source onto every tile:

"aux": {"sources": {"landcover": {"digest": "sha256:a667a785…",
                                  "resampling": "mode"}},
        "tiles_warped": 18}

Warping here rather than in a worker matters on a cluster: the artifact cache is shared but the download cache is per worker, so warping once at plan time means no worker ever opens the source. Eighteen tiles of WorldCover cost a few seconds and about 4 MB of cache.

Note the source is four files. WorldCover ships as 3° tiles and this AOI spans the corner of four of them, so the manifest names all four and they are composited later-over-earlier. The digest is over the parts in order, which is why reordering them would be a different artifact.

The plan also records what it worked out so no worker has to repeat it — including each role's space, which is why a worker never instantiates a reader just to decide how to read something:

frcov          EMITL2BFRCOV   space=ortho    resampling=bilinear
geometry       EMITL1BRAD     space=sensor   resampling=None
mineral        EMITL2BMIN     space=sensor   resampling=None

4. Regrid — one lookup table per granule per tile

A lookup table maps every cell of one tile to a pixel of one granule. It is built from the geolocation role's per-pixel latitude and longitude and from nothing else — not the mineral data, not the fractional cover. So the manifest does not control what goes into one; it controls how many get built: every (granule, tile) pair whose footprints meet. Here that is 482 of the 18 × 90 = 1,620 possible pairs.

Its key is the granule, the grid, the search radius and the algorithm version. No scorer, no mask, no role, no time range. That is why this run rebuilt none of them:

stage    items  hits  seconds
regrid    482    476   19.69
resolve  1803      0  216.94
reduce    288      0   59.93
publish    18      0    6.28
total    2591    476  302.85

The 476 regrid hits are from an earlier attempt at the same run that was interrupted after building them; a cold run pays those plus about 15 GB of downloads. The shape worth noticing is elsewhere: when this manifest's area was widened from 6 tiles to 18, every artifact from the smaller run stayed valid. A lookup table is keyed on its granule and grid, a snapshot on its own block's window — neither mentions the AOI.

5. Resolve — where obs is assembled

For each block and month, for each granule reaching it: read the lookup-table window, gather the sensor roles through it, warp the ortho roles onto it, and hand the scorer an ObsWindow. Only now does obs["frcov"] exist, and it exists on the block's grid, at the block's resolution — not on FRCOV's 60 m ortho grid.

def score(self, obs, aux):
    soil = np.clip(obs["frcov"], 0.0, 1.0)           # ortho role, warped
    sun  = np.cos(np.radians(obs["solar_zenith"]))   # band 4 of the geometry role
    s = soil + self.sun_weight * sun
    s[soil < self.hard_floor] = np.nan               # may not occupy this cell
    return s

The landcover mask runs beside it on the same block, reading aux.raster("landcover") — already warped, already windowed, already cached. Neither the scorer nor the mask does any geometry, and neither knows that one input came from a granule and the other from a public bucket in Frankfurt.

6. Changing your mind

Re-running with only hard_floor and min_soil changed:

stage    items  hits  seconds
regrid    327    327   3.85     # every lookup table already existed
resolve  1184      0  19.28     # recomputed, but the warps behind them were hits
reduce    288      0  51.05
total    1817    327  80.44

Every snapshot was recomputed, because the thing that changed is in their key. But no lookup table and no fractional-cover warp was rebuilt — those are keyed on the granule and the grid, which did not move. An 80-second experiment over 18 tiles, from a run that first cost three and a half minutes.

The shape of a good iteration

Geometry is expensive and rarely changes. Selection is cheap and changes hourly. Keeping them in separate artifacts with separate keys is what turns "try a different cost function" from a rebuild into a re-read.
