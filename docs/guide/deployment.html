Deployment

For whoever operates the platform. Users writing manifests do not need this page.

What Terraform owns

The rule

Terraform owns the platform. The manifest owns the science. One deployment serves many concurrent runs; a new experiment is a new manifest, never a new deployment.

TerraformManifest
ECR repositories, image build and pushGrid, tiling, block size
Batch compute environments, queues, job definitionsArea of interest and zones
Lambda functions, the state machineTime range, epoch, cadence
S3 buckets and lifecycle rulesFilters, masks, scorer, reducer, mapper
IAM roles, the Earthdata credentialAncillary source declarations
Account budgets, alarms, dashboardsRun budget ceilings, output formats

Terraform contains no zone names, no dates, no thresholds and no class names. A CI check greps for them, because the leak is gradual and worth catching early. If a science parameter needs an infrastructure pull request to change, the boundary has moved and should be moved back.

Reach for a second deployment only on a real boundary — a separate account for delivered products versus experimentation, or a different region. Never for an experiment.

Placement is a routing decision the planner makes from measured properties, not a static configuration:

def route(item, plan) -> Literal["lambda", "batch"]:
    if plan.capability == "tile":       return "batch"   # needs a global view
    if item.est_peak_bytes > 7 * GB:    return "batch"
    if item.est_seconds    > 600:       return "batch"   # 15-min ceiling, with margin
    if item.est_bytes_read > 8 * GB:    return "batch"
    return "lambda"

Estimates come from block cell count × bands × dtype × observation count, plus per-stage constants refined from previous runs. A small pilot routes almost entirely to Lambda and finishes in minutes with nothing to warm up; a global campaign routes to Batch on Spot. Same code, same image, same manifest.

The container image

One image, two entrypoints: a Lambda Runtime Interface Client entrypoint and a plain CLI entrypoint. Identical code runs on Lambda, on Batch, on a cluster and on a laptop — so a stage can be reproduced locally from its .inputs.json with no AWS involvement.

Lambda container images are required, not zip layers: layers cap at 250 MB unzipped across all layers, which GDAL, netCDF4, scipy and numpy exceed before any project code. Container image Lambdas allow 10 GB.

The state machine

Plan                # Lambda: manifest -> frozen index -> work list -> S3
BudgetGate          # Choice: within budget? else -> ApprovalWait (task token)
RegridMap           # Distributed Map over (granule x tile), ItemReader = S3 JSONL
  └─ CacheProbe -> Regrid          # skipped entirely on hit
EpochMap            # Distributed Map over epochs
  └─ BlockMap       # nested Distributed Map over (tile x block)
       └─ Resolve
ReduceMap           # Distributed Map over (tile x block)
PublishMap          # Distributed Map over tiles: stitch, COG, render, STAC
Finalize            # provenance record, run report, notification

Distributed Map reads its work list from an S3 object rather than from execution state and fans out to 10,000 concurrent children. Nested maps keep payloads small. Variables and JSONata carry the manifest hash and cache prefix between states.

Credentials

Source data sits in lp-prod-protected (us-west-2) behind Earthdata Login, and the S3 credentials it issues are temporary — roughly one hour.

  • The Earthdata credential lives in Secrets Manager and never in the image.
  • A refresh wrapper re-fetches before expiry and wraps every long read.
  • Batch jobs must assume refresh is needed. Lambda's 15-minute ceiling makes it a non-issue there, which is a quiet argument for routing to Lambda wherever it fits.

Failure handling

MechanismEffect
Retry with backoffAbsorbs Spot reclaim, throttling and credential expiry
Content addressingA retried block recomputes to the same key, so retry is safe
Atomic writesAn interrupted task cannot leave a truncated artifact that later reads as a hit
ResultWriterPer-item outcomes land in failures.jsonl — a queryable list, not a log grep
ToleratedFailurePercentageA run completes and reports a handful of bad blocks rather than failing 44,000 items over one corrupt granule
Block-level blast radiusOne failure loses one block, which is what makes Spot sensible

Set tolerance per deployment: permissive for experimentation, zero for delivered products.

Running many runs at once

One deployment serves many runs. Guard rails:

  • Tag every job with run_id for cost allocation.
  • Set MaxConcurrency per execution so one run cannot starve another.
  • Outputs are prefixed by run_id; the cache stays shared, which is the point.

The granule index

The index is a GeoParquet dataset queried with DuckDB directly from S3 over range requests, so there is no database to operate — the planner Lambda reads it in place.

Building it is a separate periodic job, deliberately. A run never depends on an upstream catalogue being reachable, and stage 1 freezes the granule set it selected into the run prefix so the same manifest reproduces the same inputs later.

stratum index build   --collection EMITL2BMIN --since 2026-08-01
stratum index verify  --collection EMITL2BMIN

The index records when each row was last observed, so a re-index after upstream reprocessing is detectable rather than silent.
