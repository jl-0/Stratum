Algorithms, step by step

Every arithmetic operation between a granule on disk and a cell in the product, in order, with a link to the line that performs it.

The other guides describe what Stratum does. This one follows one number from the sensor to the map and states, at each step, what is computed, which library computes it, and where that code lives. Nothing here is a summary of intent — if a step is arithmetic, the arithmetic is written out. Start with Concepts if you want the model rather than the operations.

The question this page exists to answer

Stratum puts granules on a common grid, which is what SpectralUtil already does for AVIRIS and EMIT mosaics. The geometry is not reimplemented. The nearest-neighbour search and the interpolation clean-up are called from SpectralUtil unchanged; Stratum contributes the grid definition, the index bookkeeping around that call, and everything downstream of the lookup table. Section 8 is the line-by-line ledger of which is which.

How to read this page

Links in the Code column open the file on GitHub at the line that implements the step. Stratum links follow main, so they track the code as it changes and a line number may drift by a few; the symbol is always named, so it stays findable. SpectralUtil links are pinned to 590dafd — the commit the vendor/SpectralUtil submodule points at, which is the code a run actually executes.

1. The through-line

A value in the product is the end of this chain. Each arrow is a stage; each stage is a section below.

granule (sensor grid)
  │  regrid — geometry only, no pixel is read
  ▼
GLT: for each map cell, which sensor (row, col)          cached forever
  │  resolve — read the pixels the GLT names, score them, keep one per cell per epoch
  ▼
snapshot: one winning value per cell per epoch, + its score
  │  reduce — combine the epochs in the delivery window
  ▼
product bands: winner, agreement, runner-up, counts, continuous statistics
  │  publish — colour, tile, catalogue
  ▼
COG + RGBA image + legend + STAC item

Two properties hold throughout and are worth keeping in mind while reading:

  • No value is ever resampled. Every step is a selection — a nearest neighbour, an argmax, a mode. A cell's value is always some sensor pixel's value, never a blend of several. The one exception is explicit and opt-in: the continuous aggregations in section 5, which average across epochs, never across space.
  • Validity is carried, not inferred. Each step produces a boolean mask alongside its values, and the masks are combined by conjunction. A cell is only as good as the weakest step that touched it.

2. Grid, tile, block

A grid is a CRS, a resolution and an origin — a rule for where cell edges fall, with no extent. A tile is a bounded rectangle of it; a block is a subdivision of a tile and the unit one worker processes. Cell centres come straight from the tile's affine transform, north-up, row 0 at the northern edge:

x[c] = t.c + (c + 0.5) * t.a          # t.a  = +resolution east
y[r] = t.f + (r + 0.5) * t.e          # t.e  = -resolution north

Two derived quantities are used later:

QuantityDefinitionCode
Cell diagonalhypot(rx, ry) in the grid's own units — degrees for EPSG:4326types.py:88
Cell centresthe two lines above, as (y, x) meshes over the whole tileregrid:67

3. Plan — selection, no pixels

Plan decides what will be processed. It touches the granule index, which is a table of metadata: URLs, footprints, times, cloud cover, checksums. It reads no pixel data at all (one geometry file is opened at the end, purely to prove the reader and the credential work).

StepWhat is computedCode
Resolve the AOI AOI bbox → the set of tiles on the grid lattice that intersect it; time range → epochs plan/run.py:677
Filter Each filter is a predicate over the index table, combined by conjunction. e.g. cloud_fraction <= threshold, with an explicit policy for a null value rather than a silent drop filters.py:80
Reconcile class tables Every granule declares its own mineral class ids. Plan builds a per-granule remap — an integer lookup array from that granule's ids to the run's ids — and fails if two granules disagree irreconcilably. The remap is applied later, at the gather, where the granule is still known block.py:96
Freeze The surviving granule set is written to the run directory and hashed. Every later stage reads the frozen set, never the live catalogue, so a re-run cannot silently include a granule that appeared since plan/run.py:773

4. Regrid — the geometry

Regrid answers one question per granule per tile: for each cell of the output grid, which sensor pixel is nearest? The answer is a GLT — a geographic lookup table, (H, W, 3) int32, band 1 the sensor column, band 2 the sensor row, both 1-based with 0 meaning "no pixel", band 3 the file index. It depends only on where the granule's pixels fall, so it is cached by content and never rebuilt.

The input is the granule's loc array and nothing else — latitude and longitude per sensor pixel. No band, no mask, no science value is opened at this stage.

The six steps

#StepComputedWhoseCode
1 Valid points Drop every sensor pixel whose lat or lon is masked or non-finite. Keeps a ledger rc of the surviving (row, col) so indices can be mapped back to the full array Stratum regrid:78
2 Cell centres (y, x) meshes for the whole tile from its transform (section 2) Stratum regrid:67
3 Nearest neighbour A KD-tree is built over the sensor points and queried with the cell centres. The tile is first cropped to the granule's coordinate bounding box, so the query is over the overlap only. Returns, per cell, the index of the nearest sensor point and its distance SpectralUtil mosaic.py:91
4 Distance cutoff A cell whose nearest sensor point is further than max_distance keeps the index but with its sign flipped — the "interpolated" marker. Default cutoff 1.5 × cell diagonal SpectralUtil, threshold restated by Stratum regrid:58
5 Index remap Turn the returned flat index back into a (row, col) of the full sensor array via the ledger from step 1, sign preserved, and write the three GLT bands Stratum regrid:90
6 Contiguity clean Where interpolated cells cluster, the fill is not trustworthy: a 3×3 convolution counts flagged cells in each neighbourhood and any cell with ≥ 3 is zeroed in all three bands SpectralUtil mosaic.py:17

The metric, exactly

The KD-tree is built on (lat, lon) pairs and queried with (y, x) cell centres, so distance is Euclidean in the grid's coordinate units. For the EMIT grids that means degrees, and a degree of longitude is shorter than a degree of latitude everywhere off the equator. The cutoff inherits the same units.

Inherited on purpose

This is SpectralUtil's metric, and Stratum uses it unchanged so that a Stratum mosaic and a SpectralUtil mosaic of the same granules select the same pixels. At EMIT's 60 m posting the cutoff sits well beyond one cell, so the anisotropy changes which pixel wins only where the sensor sampling is already coarser than the grid. It is listed in section 9 as a review item rather than defended as ideal.

Why the cutoff appears in two places

Called with max_distance=None, SpectralUtil derives the threshold itself, inline, from the grid it was handed:

md = sqrt((y[1,0]-y[0,0])**2 + (x[0,1]-x[0,0])**2) * 1.5   # SpectralUtil, inline
D  = MAX_DISTANCE_FACTOR * grid.diagonal                   # Stratum = 1.5*hypot(rx,ry)

These are the same number. Stratum computes it explicitly, and passes it, for one reason: a value that changes the output has to be in the cache key. A threshold decided inside the call is invisible to the key, so a grid change could return a stale GLT. Restating it is bookkeeping, not a second algorithm — and if the two ever diverge, the parity harness (section 8) is what catches it.

Consequences of step 6

The contiguity clean is a stencil: a cell's fate depends on its neighbours. That is why a GLT is always built for a whole tile and never per block — blocks would each apply the 3×3 independently and leave a seam at every internal boundary. It is the single reason regrid's unit is the tile while everything downstream can be a block.

Algorithm version and sign-off

GLT output feeds every downstream cache. REGRID_ALGO_VERSION enters the GLT cache key, and a hash of the whole stratum/regrid/ package is recorded beside the code in ALGO_HASH. Editing anything in that package fails the test suite until someone re-records the hash — an explicit assertion, by a person, that they considered whether output changed. regrid:344

When the product is already on our grid

EMIT products ship a lookup table of their own, on the grid their producer chose (location/glt_x, glt_y). Those grids are all one lattice: same CRS, same cell, and origins that share a phase to 2 × 10−9 of a cell across 1360 granules from three collections. So a run whose grid is laid on that lattice can set grid.regrid_method: adopt and skip the search entirely — the cells are already right, and regrid becomes a crop onto the tile.

lattice_offset(grid, transform, crs)     # same CRS, same cell size, and an origin a
                                         # whole number of cells away, within 1e-6 cell
adopt_glt(embedded, tile)                # crop/pad onto the tile; no value recomputed

The precondition is checked at plan time, on one granule header, so a grid that cannot be adopted fails before anything is downloaded — and it refuses per granule rather than falling back, since a silent fallback would mix two derivations under one cache key. regrid:131

Adopt is not a faster kdtree

On a measured tile the two methods pick the same sensor pixel for 57.8 % of cells — every disagreement at most one pixel, and one-sided. The reason is registration: a lookup built here is exactly centred on the cell (mean offset 0.000 of a cell, which an inverse nearest query must be), while the product's table sits about a fifth of a cell west and a third south of that, by an amount that varies from granule to granule. Adopting takes the producer's registration; it is not a cheaper route to ours. It also inherits their fill decisions: an EMIT table carries no interpolated markers at all, so max_distance and the contiguity clean have nothing to act on, and the GLT key records max_distance: null plus the source asset's checksum instead.

5. Resolve — read, score, keep one

Resolve is where pixel data is first read. The unit is one block × one epoch; the output is a snapshot: one winning value per cell, plus the score that won it and a validity mask.

#StepComputedCode
1 Candidates Granules in the frozen set whose footprint intersects this block and whose acquisition time falls in this epoch block.py:72
2 GLT window A windowed read of the cached GLT — internal tiling means only the block's own bytes are fetched. A block with no hit is skipped before any granule is opened regrid:254
3 Sensor window The bounding box of the sensor pixels this GLT window names: [min|gy|-1, max|gy|) × [min|gx|-1, max|gx|). This is the only part of the granule that is read types.py:533
4 Read Each role (geometry, mineral, mask…) read over that window as a masked array — fill values arrive already masked observation.py:110
5 Sensor-space masks Every PixelMask evaluated in the granule's own geometry, combined by conjunction — cheaper here than on the map, and some masks (slit artefacts, edge trims) only make sense in sensor space observation.py:177
6 The gather The lookup itself — see below gather.py:31
7 Map-space masks Masks that need map geometry or ancillary rasters, on the block, by conjunction observation.py:200
8 Class remap The granule's own class ids → the run's, by the lookup array plan built. A value with no mapping is marked invalid rather than guessed observation.py:215
9 Score and keep The scorer runs on the block; the running best is updated — see below block.py:154

The gather, written out

hit          = fi != 0                          # band 3: a sensor pixel was found
interpolated = ((gy < 0) | (gx < 0)) & hit      # beyond max_distance, kept but flagged
r            = |gy| - 1 - sw.row0               # GLT is 1-based; sw is the sensor window
c            = |gx| - 1 - sw.col0
band[hit]    = data[r, c]                       # the value, verbatim
valid        = hit & ~mask[r, c] & ok[r, c]     # fill, and the sensor masks

That is the whole of it: an integer index into an array. No weighting, no averaging, no sub-pixel interpolation. SpectralUtil's apply_glt performs the identical indexing —

outdata[valid_glt, :] = dat[glt[valid_glt, 1], glt[valid_glt, 0], :]

— and the two lines are worth diffing during review: gather.py:66 versus mosaic.py:385. Stratum does not call apply_glt because it is a whole-file operation — it loads the entire GLT and the entire raster and writes an output file — and resolve needs the same arithmetic on a windowed read, under a mask, one block at a time, with the per-granule class remap applied in the same pass.

Scoring and the running best

The scorer is the part you write. It receives the observation on the block and returns one float per cell; NaN means refuse this cell. The demo's rule is one line — the most nadir look wins:

def score(self, obs, aux):
    return -obs["view_zenith"]        # negated: resolve keeps the HIGHEST score

Observations are streamed in candidate order and a running best is kept, so memory does not grow with the number of overlapping granules:

take = obs.valid & ~isnan(score) & (~won | (score > best))
best[take]   = score[take]
layers[take] = values[take]
won         |= take

The comparison is strictly greater, so on an exact tie the first candidate in order wins. That makes the result depend on candidate order, which is why the order is fixed by the frozen granule set rather than by whatever the filesystem returned (section 9).

What lands on disk is the snapshot: each schema layer's winning value, the winning score, and valid. snapshot.py:66

6. Reduce — combining epochs

Reduce takes the stack of snapshots covering one delivery period and produces the delivered bands. Every kernel is vectorised over (H, W); the only loops are over the epoch axis and over the class ids actually present. builtin.py:39

The support count is the starting point for everything else:

n_epochs = valid.sum(axis=0)          # how many epochs had anything to say here

Categorical: mode through time

The default for a class layer, in this decision order (builtin.py:165):

  1. Invalid epochs are discarded. What remains is n_epochs.
  2. Ignored classes (named in the manifest; none is class 0) leave the tally but stay in n_epochs — being repeatedly told "nothing here" is information, and hiding it would inflate agreement.
  3. counts[k] = (vals == k & counted).sum(axis=0) per class; the modal class is counts.max(axis=0).
  4. The winner is suppressed to nodata where its count is below min_count.
  5. Ties are broken by tie_break: earliest / latest by epoch order, highest_score by the best score any tied class holds, or nodata to refuse. Equal keys fall to the lowest class id, so the result is deterministic either way. builtin.py:143

Two companion bands come out of the same tally:

agreement = modal_count / n_epochs     # NaN where n_epochs == 0
runner_up = second mode, same tie rule

agreement is reported even where the winner was suppressed by min_count or a refused tie: it describes the tally, not the decision.

Continuous: aggregation across epochs

Each method is nan-aware, so a non-finite value inside a selected epoch is skipped by the statistic but still counted in <layer>_n. builtin.py:229

MethodComputed
median, mean, min, max, percentilethe nan-aware numpy reduction over the epoch axis
bestthe value from the highest-scoring epoch — no arithmetic on values at all
score_weightedw = score - min(score) + 1e-6, then Σwx / Σw. The shift exists because a score is only an ordering — MinViewZenith returns negative numbers — and a raw score cannot be a weight. The lowest-scoring epoch gets weight ε; equal scores reduce to a plain mean
inverse_variancew = 1/u² from the layer's uncertainty band, dropping epochs whose u is NaN or ≤ 0 from both the estimate and the count

Optional spread is the standard deviation or the interquartile range over the same selected epochs. A layer may be conditional_on a categorical layer, which narrows the epoch set to those that agreed with the winning class before any of the above runs — so a mean band depth is a mean over the epochs that actually saw that mineral.

7. Publish — colour, tile, catalogue

Publish performs no science. Blocks are assembled into full-tile arrays, cells no block covered taking the band's nodata (stitch.py:74), then:

  • Data COGs — one tiled, deflate-compressed GeoTIFF per delivered band, with nodata, band descriptions, units, and the run's provenance tags. Categorical bands carry a GDAL colour table so a plain viewer can render them. cogs.py:77
  • Images — a categorical mapper is a class → RGBA lookup (mappers.py:91); a continuous mapper clips to a domain and interpolates a ramp (colors.py:156). Optional alpha_from interpolates a confidence band linearly into an alpha range, so a low-agreement cell renders faint. Nodata is transparent.
  • Legend and STAC — the class table as published, and an item recording the granules, the manifest hash and the run id.

9. Known properties worth reviewing

Not defects — decisions, each with a consequence a reviewer should weigh.

PropertyConsequence
Nearest-neighbour distance is Euclidean in grid units (degrees for EPSG:4326) The metric and the cutoff are anisotropic away from the equator. Inherited from SpectralUtil deliberately, for parity; a projected grid removes the question entirely
Ties in resolve go to the first candidate (score > best) The result depends on candidate order. Order comes from the frozen granule set, so it is reproducible — but two runs with different filters can order differently
The contiguity clean is a stencil GLTs must be built per whole tile. Any future attempt to parallelise regrid below the tile would produce seams
A score is an ordering, not a physical quantity Anything that treats it as a magnitude has to say how — which is what the shift in score_weighted is, and why it is documented at the constant
GLT band 3 is always 1 One GLT per granule, so there is no file index to carry. The band is kept so SpectralUtil and other EMIT mosaic tooling can open a Stratum GLT unmodified
Interpolated cells are kept, not dropped A cell filled from beyond max_distance reaches the product unless step 6 removed it. The flag survives into the snapshot, so a scorer or mask can refuse them
