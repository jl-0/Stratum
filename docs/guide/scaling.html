Running at scale

The same pipeline on a laptop, a cluster, or AWS. What changes is who dispatches the work — not the code, the manifest, or the result.

One pipeline, three executors

Stratum is an ordinary Python package with a CLI. Everything it does runs on one machine; the other backends exist because some runs are too big for one machine, not because the pipeline needs them.

ExecutorDispatches work viaGood for
localA process pool on this machine. Default.Development, a zone, a few tiles, anything you want to debug
slurmA job array on a shared filesystemAn institutional cluster you already have an allocation on
awsFans out to Lambda, one invocation per work itemContinental or global runs; bursty campaigns with nothing to keep warm
 
stratum run -m manifest.yaml                      # local, the default
stratum run -m manifest.yaml --executor slurm
stratum run -m manifest.yaml --executor aws
The executor is not a manifest field

Where a run executes is a platform decision, not a science one, so it is a CLI flag or a deployment profile — never part of the manifest. The same manifest must produce the same result on a laptop and on a 10,000-way fan-out, and a manifest that named its executor could not make that promise. Same rule as Terraform versus manifest.

What makes this work

The plan stage emits a work list — a flat file of independent items, each naming a (granule, tile) or a (tile, epoch, block). Every executor does the same thing with it: run each item, somewhere. Items do not talk to each other, and each writes to a content-addressed key.

plan  ──▶  work list  ──▶  [ executor ]  ──▶  content-addressed artifacts

So the executor is genuinely swappable. A run started locally and interrupted can be finished on the cluster: the completed items are already in the cache, and the second run skips them.

Local

No infrastructure, no credentials beyond data access, no configuration. Storage is a directory instead of a bucket, and paths are used wherever a URI would be:

cache:    ./cache            # instead of s3://bucket/cache
outputs:
  bucket: ./products         # local paths work anywhere a URI does
stratum run -m manifest.yaml --workers 8    # default: one per core

Worth knowing what this is good for, since it is easy to assume local means toy:

  • A pilot zone at block granularity is minutes of work, not hours.
  • Blocks are sized to fit a worker, so a laptop runs the same code path a Lambda would — there is no separate "small" implementation to diverge.
  • Stage-in of granules to local disk is the simple path, and staging is what a cluster does anyway.

What you actually run out of is time and disk, in that order. When a run stops fitting, change the executor and nothing else.

SLURM

The natural mapping: a work list is a job array. Each array task takes its index, reads that item, and runs it. Stages become dependent array jobs.

# 1. plan on the login node - cheap, no compute needed
stratum plan -m manifest.yaml --out $SCRATCH/run-01

# 2. one array task per work item
sbatch --array=0-724%64 --cpus-per-task=4 --mem=16G --time=00:30:00 \
       --wrap "stratum exec --plan $SCRATCH/run-01 --stage regrid --index \$SLURM_ARRAY_TASK_ID"

Or let Stratum submit the chain, which is the same thing with the dependencies filled in:

stratum run -m manifest.yaml --executor slurm \
    --partition normal --cpus-per-task 4 --mem 16G --max-concurrent 64
ConcernHow it maps
Fan-out--array=0-N, throttled with %K so one run cannot take the whole partition
Stage ordering--dependency=afterok:<jobid> between stages
Shared stateThe cache is a directory on the shared filesystem. Content addressing means concurrent tasks never collide.
Retries--requeue, plus the fact that a retried item recomputes to the same key
Partial failureFailed array indices are re-submittable on their own — the work list index is the identifier
Sizing

Ask for what a block needs, not what a tile needs. The reason existing cluster jobs request 32 GB and long walltimes is that they materialize a whole tile; a 512×512 block is about a gigabyte, so short, small, high-concurrency array tasks are the better shape and they fail more cheaply.

One thing to check on a cluster: --cpus-per-task must match what the regrid actually uses. The KD-tree query is the compute-bound step and takes a worker count; requesting four CPUs and running single-threaded wastes three of them for the whole regrid phase.

AWS

For runs where the fan-out is the point. The unit of work is a block, not a tile, and blocks are sized so that the work fits a serverless worker — which turns out to settle the architecture.

Standing one up

This section is what the AWS executor is. Deploying to AWS is how you build one: the private .env, the state bucket, the platform Terraform root, and who is allowed to apply which part.

Everything fits Lambda

Measured from the reference archive run — one tile, eight months, 33 granules — against Lambda's ceilings of 15 minutes, 10 GB of memory and 10 GB of /tmp:

StageItemsTotalWorst single itemHeadroom
plan193 s93 s, stages 1.55 GB to /tmp10×
regrid3399 s19 s per granule plus its download22×
resolve1466 s~0.5 s per 720×720 block900×
reduce2521 s~0.5 s per block300×
publish14 s~1.6 s per tile225×

Memory is not close either: a whole-tile GLT is 0.14 GB and the compute unit is a block. Three consequences, each of which removes work:

  • No Batch, and therefore no EC2 to provision.
  • No router. A route() function exists to choose between Lambda and Batch; with one destination there is no choice, so the per-stage cost constants it would need stop being on the critical path.
  • No state machine, for the reason below.

This is a property of this workload, not a general result. A continental run will exceed fifteen minutes somewhere — most likely in plan, which is why plan is routed like any other work item and checkpoints per-tile work lists as it goes. Batch returns then, on Fargate, so the deployment stays free of EC2.

Inline fan-out

The aws executor walks the stages in order and invokes one Lambda per work item, concurrently, collecting outcomes. That is the shape executors/local.py already has — per stage, submit every item, collect per-item outcomes, fail all-or-nothing — with a thread pool over lambda:InvokeFunction in place of a process pool.

The orchestrator is not infrastructure. It is the CLI, so it runs wherever the CLI runs: on a laptop, which needs nothing deployed at all, or in a Fargate task when a run should survive a closed laptop. Identical code either way.

The first row decides it wherever IAM role creation is a rationed privilege. A quieter benefit: the orchestrator never reads granules — the workers do — and no worker runs past fifteen minutes, so the one-hour Earthdata credential expiry never arises on this path.

The container image

One image, two entrypoints: a Lambda Runtime Interface Client entrypoint and the same plain CLI you run locally. That is what keeps the executors honest — identical code, so a stage can be reproduced on a laptop from its .inputs.json with no AWS involvement.

Lambda container images are required, not zip layers: layers cap at 250 MB unzipped across all layers, which GDAL, netCDF4, scipy and numpy exceed before any project code. Container image Lambdas allow 10 GB.

Step Functions, when it earns its place

Deferred, not rejected. It becomes the right answer at item counts beyond a thread pool's comfort, or for a delivered product that needs a managed audit trail — not for scheduling, which is an EventBridge rule against the orchestrator task and needs no state machine. Adopting it later replaces the orchestrator and nothing else, because the work lists are already the S3 JSONL that ItemReader consumes.

What Terraform owns

The rule

Terraform owns the platform. The manifest owns the science. One deployment serves many concurrent runs; a new experiment is a new manifest, never a new deployment.

Terraform is a deployment method for the AWS executor — it stands up ECR, Batch compute environments and queues, Lambda functions, the state machine, S3 buckets and lifecycle rules, IAM roles, the Earthdata secret, and budgets and alarms. It is not involved in a local or SLURM run at all.

TerraformManifest
ECR repositories, image build and pushGrid, tiling, block size
Batch compute environments, queues, job definitionsArea of interest and zones
Lambda functions, the state machineTime range, epochs, delivery windows
S3 buckets and lifecycle rulesFilters, masks, scorer, reducer, mapper
IAM roles, the Earthdata credentialAncillary source declarations
Account budgets, alarms, dashboardsRun budget ceilings, output formats

Terraform contains no zone names, no dates, no thresholds and no class names. A CI check greps for them, because the leak is gradual and worth catching early. If a science parameter needs an infrastructure pull request to change, the boundary has moved and should be moved back.

Reach for a second deployment only on a real boundary — a separate account for delivered products versus experimentation, or a different region. Never for an experiment.

Credentials

Source data sits in lp-prod-protected (us-west-2) behind Earthdata Login, and the S3 credentials it issues are temporary — roughly one hour. This applies to every executor, not just AWS.

ExecutorWhere the credential lives
localYour ~/.netrc (tried first) or EARTHDATA_USERNAME/EARTHDATA_PASSWORD, as earthaccess expects. Read on the first download, never at import; one re-login on 401/403; never logged or written to a run directory. Built.
slurmSame, on the shared filesystem. Long array tasks must refresh.
awsSecrets Manager, never in the image

The one-hour expiry is a real constraint on long-running work: a refresh wrapper re-fetches before expiry and wraps every long read. Lambda's 15-minute ceiling makes it a non-issue there, which is a quiet argument for routing to Lambda wherever it fits — and an argument for short, small SLURM array tasks over long ones.

Failure handling

Most of this is executor-independent, because it comes from content addressing rather than from any scheduler.

MechanismEffect
Content addressingA retried item recomputes to the same key, so retry is always safe
Atomic writesAn interrupted task cannot leave a truncated artifact that later reads as a hit
Block-level blast radiusOne failure loses one block — which is what makes Spot, and preemptible cluster queues, sensible
Per-item outcomesFailures land in failures.jsonl as a queryable list, not a log grep. Re-running the same manifest retries only those items.
Retry with backoff awsAbsorbs Spot reclaim, throttling and credential expiry
--requeue slurmThe scheduler's equivalent
Tolerated failure percentageA run completes and reports a handful of bad blocks rather than failing 44,000 items over one corrupt granule. Permissive for experiments, zero for delivered products.

The granule index

The index is a GeoParquet dataset queried with DuckDB, over range requests from S3 or straight from a local file. There is no database to operate in any of the three cases.

stratum index build  -m manifest.yaml --collection EMITL2BMIN --since 2026-08-01
stratum index verify -m manifest.yaml --collection EMITL2BMIN

Building it is a separate periodic job, deliberately: a run never depends on an upstream catalogue being reachable, and the plan stage freezes the granule set it selected into the run prefix so the same manifest reproduces the same inputs later. The index records when each row was last seen, so an upstream reprocessing is detectable rather than silent.
