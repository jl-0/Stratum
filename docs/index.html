Stratum

Build mosaics from overlapping imaging-spectroscopy granules, where you control which observation wins.

Pre-release

These pages describe the interface as specified. The package is not yet implemented — see Status for what exists. Commands and contracts shown here are the contract being built to, not a shipped API.

What it does

You give Stratum an area, a time range, and a rule for choosing between overlapping observations. It gives you back a mosaic — as a data product, a rendered image, and a provenance record that says exactly which granules went into it.

stratum plan -m manifest.yaml     # what would run, and what it would cost
stratum run  -m manifest.yaml     # run it - on this machine, by default

It is an ordinary Python package: the whole pipeline runs locally with no infrastructure. Larger runs change only where the work is dispatched — a cluster job array, or AWS — not the code, the manifest, or the result.

The rule for choosing is the part you write. Everything else — finding granules, putting them on a common grid, fanning the work out, caching, cataloguing — is the framework's job.

The pipeline

Five stages. You configure all of them, and each one takes a hook — the two in the middle are where the answer is decided.

1

Plan

unit: run

Resolves your area to tiles and your time range to epochs, queries the granule index, applies your filters, and freezes the surviving granule set. Reports the fan-out and stops if it exceeds your budget.

2

Regrid PixelMask

unit: granule × tile

Puts each granule on the output grid by nearest-neighbour lookup, producing a GLT. Your pixel masks are applied here, so masked pixels never enter the stack. Cached indefinitely.

3

Resolve Scorer

unit: tile × epoch × block

Runs your cost function over the observations covering each cell and keeps the winner. Writes the winning value, the score that won it, and how many observations competed.

4

Reduce Reducer

unit: tile × block

Collapses the per-epoch snapshots through time — mode, median, consensus, or whatever you write. Skip it and you get the single-epoch result unchanged.

5

Publish OutputMapper

unit: tile

Stitches blocks into tiles and writes the data product, the rendered image, the legend, a STAC item and the provenance record.

Where you plug in

HookYou use it to sayRuns
GranuleFilterWhich granules are candidates at all — dates, seasons, cloud cover, product versionOnce per run, against the index
PixelMaskWhich pixels are unusable — cloud, water, detector edgesPer granule, during regrid
ScorerWhich observation wins a cellPer block, per epoch
ReducerHow epochs combine into the delivered productPer block
OutputMapperWhat the rendered image looks likePer tile, at publish

The first four decide which observation wins; the fifth decides what it looks like. Most mappings and filters are configuration, not code — you only write a plugin when the built-ins do not cover what you need. See Writing plugins.

Two more hooks sit underneath those, and they exist to add a data source rather than to change an answer:

HookYou use it to sayRuns
GranuleSourceWhere the catalogue of granules comes from — a directory, CMR, a STAC APIIndex build, ahead of any run
GranuleReaderHow one product family's bytes become arraysPer block, in every worker

A new instrument is a reader; a new archive is a source. Neither changes what a mosaic means, which is why they are kept apart from the five above. See Reading data.

Changing your mind is cheap

Regridding is the expensive stage and depends only on geometry. Scoring is cheap and is the thing you will change constantly. Stratum keeps them separate and content-addresses everything, so what you change determines what re-runs:

You changeRe-runsRe-uses
Your scorerStages 3–5Every cached GLT — no regridding
Your reducerStages 4–5Every epoch snapshot
Your coloursRendering onlyThe published data — no pipeline run
Your pixel masksStages 2b–5The GLTs — geometry does not depend on cloudiness

Running several competing cost functions over the same area is therefore cheap: the first pays for the geometry and the rest reuse it. See Caching & reruns.

What it is and is not

Stratum doesStratum does not
Mosaic granules that are already science productsProduce those products — it consumes them, it does not generate them
Nearest-neighbour regrid onto a shared gridAtmospheric correction, unmixing, or spectral fitting
Temporal aggregation you defineImpose a temporal model of its own
Render an image and ship the data behind itServe tiles — that is MMGIS's job, downstream

The core is instrument-agnostic. It knows about grids, tiles, blocks, GLTs, class tables and caching — not about minerals, spectral libraries or EMIT. Instrument and domain knowledge lives in a plugin package:

PackageProvides
stratumThe pipeline, the plugin contracts, the CLI, caching, provenance
stratum_emitEMIT granule readers, the CMR source, detector-edge masks, mineral scorers, FRCOV support, lumping
