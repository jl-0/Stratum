Serverless is right for three stages and wrong for two

The honest answer is a split, not a choice.

PlaneServiceStagesWhy
ControlStep Functions + Lambda1, 5, all cache probesSeconds, hundreds of MB, thousands of invocations. Serverless genuinely pays here.
DataAWS Batch on EC2 Spot2, 3, 4 when largeMinutes to hours, GBs of RAM, GDAL in the image. Spot with block-level retries.
Eitherrouted per work item2, 3, 4 when smallBlocks make Lambda viable where whole tiles never were

Lambda’s ceilings are hard: 15 minutes, 10 GB memory, 10 GB /tmp. EMIT-AMD asks Slurm for 32 GB and up to 24 hours per 1° bin. Those numbers do not meet, which is why block decomposition is load-bearing rather than a tuning detail: it shrinks the unit until Lambda fits, and turns the answer from a verdict into a router.

One image, two entrypoints

Zip layers cap at 250 MB unzipped across all layers. GDAL + netCDF4 + scipy + numpy exceeds that before any of our code, so container image Lambdas — 10 GB — are the only viable path. The same image carries a Lambda Runtime Interface Client entrypoint and a plain CLI entrypoint, so identical code runs on Lambda, on Batch, on the JPL cluster, and on a laptop.

That last property is worth more than it looks. It means a plugin author debugs the same code path that runs in production, and that a stage can be reproduced locally from its .inputs.json without any AWS involvement.

Routing

def route(item, plan) -> Literal["lambda", "batch"]:
    if plan.capability == "tile":       return "batch"   # needs a global view
    if item.est_peak_bytes > 7 * GB:    return "batch"
    if item.est_seconds    > 600:       return "batch"   # 15-min ceiling, with margin
    if item.est_bytes_read > 8 * GB:    return "batch"
    return "lambda"

Estimates come from the planner: block cell count × bands × dtype × observation count, plus measured per-stage constants refined from prior runs. A pilot zone at block granularity routes almost entirely to Lambda and finishes in minutes with nothing to warm up; a global reprocessing campaign routes to Batch on Spot. Same code, same image, same manifest.

State machine

Plan                # Lambda: manifest -> frozen index -> work list -> S3
BudgetGate          # Choice: within budget? else -> ApprovalWait (task token)
RegridMap           # Distributed Map over (granule x tile), ItemReader = S3 JSONL
  └─ CacheProbe -> Regrid          # skipped entirely on hit
EpochMap            # Distributed Map over epochs
  └─ BlockMap       # nested Distributed Map over (tile x block)
       └─ Resolve
ReduceMap           # Distributed Map over (tile x block)
PublishMap          # Distributed Map over tiles: stitch, COG, render, STAC
Finalize            # provenance record, run report, notification

Distributed Map is the feature that makes this shape work: it reads its work list from an S3 object rather than from execution state, and fans out to 10,000 concurrent child executions. Nested maps — tiles into blocks — keep payloads small. Variables and JSONata carry the manifest hash and cache prefix across states without a chain of Pass states.

Failure handling

Neither existing pipeline retries anything, and the supervision that exists does not work. watch.sh infers a job id by regexing a log filename, counts finished bins, and greps stderr for error|fail|oom — so any library warning containing “error” reads as failure, and an OOM-killed task that wrote no stderr reads as success. It is also broken as written: it matches *Finished* against tail -n 1, but pipeline.sh’s last line is Done. A failed 1° bin stays failed until a human notices.

The answer is not a better supervisor. It is a structure where most of those failure modes cannot occur:

Mechanism
1Retry with backoff on transient failures — Spot reclaim, throttling, credential expiry
2Content addressing makes retry safe — a retried block recomputes to the same key
3Atomic writes, so an interrupted task cannot leave a truncated artifact that later reads as a hit
4ResultWriter captures per-item outcomes — failures are a queryable list, not a log grep
5ToleratedFailurePercentage, so a run completes with a handful of bad blocks and reports them rather than failing 44,000 items because one granule is corrupt
6Blast radius is one block — which is what makes Spot economically sensible

Credentials

EMIT data lives in lp-prod-protected (us-west-2) behind Earthdata Login, and S3 credentials are temporary — roughly one hour.

AMD’s 24-hour Slurm jobs would simply fail partway through if ported naively. So: the EDL credential lives in Secrets Manager and never in the image; a refresh wrapper re-fetches before expiry and wraps every long read; Batch jobs must assume refresh is needed. Lambda’s 15-minute ceiling makes it a non-issue there, which is a quiet argument for routing to Lambda wherever it fits.

Many runs, one deployment

Boundary

Running five competing cost functions is a manifest concern, not an infrastructure concern. Terraform stands up one run-agnostic deployment; a run is a manifest plus a run_id that becomes an S3 prefix and a Step Functions execution.

Because GLTs carry no dependence on the scorer, every experiment over the same zone shares one GLT cache. Guard rails: tag every job with run_id for cost allocation; set MaxConcurrency per execution so one run cannot starve another; give outputs a run_id prefix while the cache stays shared.

Reach for a second deployment only on a real boundary — a separate account for delivered products versus experimentation, or a different region — never for an experiment.

The budget gate

The difference between one zone and the globe is one line of YAML, and this pipeline actively invites that mistake. So the planner computes the real fan-out — tiles × epochs × blocks × granules — before any compute is provisioned, compares it to a declared ceiling, and on exceedance parks the execution on a Step Functions task token awaiting human approval.

stratum plan emits a dry-run report by default: tile count, granule count, estimated bytes read, projected cache hit rate, estimated vCPU-hours. It should be reviewed in the pull request alongside the manifest diff.
