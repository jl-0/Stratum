EMIT Critical Minerals · L3 Mosaic · Architecture Proposal

Stratum

A cost-function-driven mosaic engine for the cloud

Three times now, EMIT has written a mineral mosaic pipeline from scratch. Each one hard-codes a different answer to the same question: when several observations cover the same patch of ground, which one wins? This proposal factors that question out into a plugin contract, puts the expensive geometry behind a cache, and runs the whole thing on AWS as a declarative, budget-limited job. Science teams then iterate on a cost function instead of on a pipeline.

00Thesis

Every mosaic EMIT has built decomposes into the same four operations, and only the third and fourth are science:

  1. Select which granules are candidates — a query over an index.
  2. Regrid each granule onto a common grid — pure geometry, deterministic, expensive, and completely independent of the science.
  3. Resolve which observation wins in each cell — the cost function.
  4. Reduce a stack of per-period snapshots into one product — the temporal aggregator.

The three existing lineages differ almost entirely in steps 3 and 4, yet each reimplements 1 and 2 to get there. Worse, V002 fuses step 3 into step 2, which is why changing the selection criterion means rebuilding all the geometry.

The proposal in one sentence

Build a small framework that owns steps 1, 2 and the execution plumbing; expose steps 3 and 4 as versioned Python plugins; content-address the step-2 output so that iterating on a cost function is minutes of compute rather than days; and drive the whole thing from one declarative manifest that carries its own spatial, temporal and budget limits.

Everything below is downstream of that. The AWS choices matter less than the decomposition — but they matter, and §08 argues for a specific one that is not “the engine is a Lambda.”

01What the code actually does

Before generalizing, it is worth being exact about what the two working pipelines do, because they disagree in a way the design documents do not capture — and the disagreement is the most useful thing in this whole analysis.

V002 fuses selection into the regrid

SpectralUtil’s build_obs_nc walks the candidate granules one at a time, and keeps a running best-score array over the output grid. The entire selection mechanism is an argmin/argmax over a single scalar band:

SpectralUtil/spectral_util/mosaic/mosaic.py — the selection seam 
if criteria_band is not None:
    raw_ob = obs[:, :, criteria_band]
    ob = raw_ob[np.abs(sub_glt[...,1])-1, np.abs(sub_glt[...,0])-1]
    existing_crit = criteria[sub_glt_insert_idx[...,0], sub_glt_insert_idx[...,1]]
    valid = np.logical_and(sub_glt[...,0] != meta.nodata_value,
                           ob != local_meta.nodata_value)

    if criteria_mode == "min":
        crit_mask = np.logical_and(ob < existing_crit, valid)
    elif criteria_mode == "max":
        crit_mask = np.logical_and(ob > existing_crit, valid)
    # first observation in a cell always wins
    crit_mask = np.logical_or(crit_mask,
                              np.logical_and(valid, np.isnan(existing_crit)))
    criteria[...] = ob[crit_mask]
else:
    crit_mask = sub_glt[...,0] != 0   # no criteria: last writer wins

V002 passes --criteria_band 5 --criteria_mode min: OBS band 5 is view zenith, so the winner is the most nadir look. The result is one GLT per tile encoding (GLT X, GLT Y, File Index), which is then applied to every raster of interest.

Property worth preserving

This is a streaming reduction: memory is O(grid), not O(grid × N granules), no matter how many observations there are. That is a real engineering virtue and the generic design must keep it available — see the streaming capability in §04.

AMD defers selection entirely

EMIT-AMD does something structurally different, and the difference is easy to miss because it calls the same CLI. In pipeline.sh the mosaic build is invoked once per granule, with no --criteria_band at all:

EMIT-AMD/pipeline.sh — one GLT per granule 
build="--n_cores 1 --x_resolution 0.0003 --y_resolution -0.0003 \
       --target_extent_ul_lr ${lon[0]} ${lat[1]} ${lon[1]} ${lat[0]}"

for ((i=0; i< ${#obs[@]}; i++ )); do
    file=$(basename "${min[i]}")
    $mosaic build-obs-nc $build "glt/$file.tif" "${obs[i]}"
    $mosaic apply-glt "glt/$file.tif" "${min[i]}" "applied/min_$file.tif"
    $mosaic apply-glt "glt/$file.tif" "${unc[i]}" "applied/minunc_$file.tif"
    $mosaic apply-glt "glt/$file.tif" "${msk[i]}" "applied/mask_$file.tif"
done

amd run   -c config.yml -p "generated"   # classify each observation
amd stack -c config.yml -p "generated"   # integrate across all of them

Nothing is discarded. Every observation is orthorectified onto the shared tile grid and kept, and all reconciliation happens afterwards, in classification space, across the full stack. That is precisely why AMD can do temporal integration and V002 cannot: V002 throws the observations away at regrid time.

Two details from the downstream chain are worth carrying forward. AMD’s outputs are laid out as groups/{group}/{freq}/{kind} — the frequency level confirms that a temporal dimension already survives into the delivered layout, which is a useful precedent for stage 5. And gdal.sh tiles the colors product but explicitly skips the other kind: 

# Skip counts for now, doesn't work
if [[ "$kind" == "counts" ]]; then
    continue
fi

The cause is visible in the step that follows: the coastal mask is applied as gdal_rasterize -b 4 -burn 0 — band 4, burned to zero. That only works on a 4-band RGBA raster, so it cannot be applied to a single-band counts product, and skipping it is the path of least resistance.

What the AMD config settles

James’s configs/config.yml (now vendored at refs/config.yml in this task folder) confirms the RGBA reading outright. Classes map to four-channel colour, with alpha carrying nodata: 

colors:
  #      R,   G,   B,   A
  -3: [128, 128, 128,   0]   # "fake NaN"  -> fully transparent
  -2: [128, 128, 128, 255]   # Tetracorder NaN
   1: [220,   5,  12, 255]   # pyrite
   2: [174, 118, 163, 255]   # goethite

So AMD does ship rendered colour rather than class indices, and the colormap exists — it just lives in a config on the cluster and never travels with the product. No consumer can restyle, requantise or recount from what MMGIS receives.

Design consequence for stage 5

Stratum must publish the data product and the rendered image as separate artifacts, with the colour mapping a declared, versioned transform over the former (§06a). The image is what MMGIS and QGIS consume, and it genuinely is the deliverable people look at — but if it is the only output, the archive stops being analysis-ready and counts and agreement become casualties of an RGBA assumption, exactly as they did here.

… and what it overturns

The same config contains the entire temporal surface of amd stack. It is two keys: 

v5:  stack: {mincount: 3}          # suppress weakly-supported pixels
v7:  stack: {ignore: [0, -4]}     # classes excluded from the tally

There is no period, window, month or year key — in a config that otherwise parameterizes subsetting, downloads, classification, masking, lumping and colour. Combined with the fact that no filename anywhere carries a date, that points somewhere different from the assumption this design started with.

Reinterpretation — carries real consequences

freq-<N> is most likely a frequency rank, not a time chunk: freq-0 the most frequent class, freq-1 the runner-up, with counts as the vote tally and mincount the support threshold. On that reading AMD never bins time at all — it takes the mode over every observation ever acquired, which is consistent with amd query being called with no date arguments.

If so, AMD is a precedent for the voting half of what Critical Minerals needs and not the temporal half, and mode-through-time is more new work than Background.md implies. This is still an inference. It resolves with one question to James: “is freq-N the Nth most frequent class, or the Nth time period?” — and it should be asked before anyone sizes the temporal work.

Two things the config settles that are unambiguously good news. The lumping step is already parameterized: hashmap maps Tetracorder mineral indices to display classes and is versioned v1…v7, so the debate Phil expects fights over is a YAML block rather than a code change. And mincount plus ignore are almost exactly the parameters proposed for ModeThroughTime in §04, which suggests the shape of that reducer is right even if its temporal axis is new.

Landmine in the lumping tables

AMD’s hashmap is keyed on positional index values (goethite: [3, 5, 6, 7, 8]). The reference matrix that assigns those positions, tetrapy/data/v6.00a6.csv, now carries both an index and a stable id slug — the id column was added in tetracorder-lite PR #20 precisely because positions shift when rows are added, removed or deduplicated.

A grouping table keyed on index therefore silently reassigns minerals to different classes on a Tetracorder version bump, with no error. Stratum must resolve lumping through the stable id, and the manifest must pin the reference-matrix version. This affects the 5.27 → 6.00a mapping work too and is worth raising with Phil independently of this design.

Two smaller cautions from the same chain. gdal.sh writes the full mosaic through gdal_translate with no creation options and then modifies it in place, so the intermediate is uncompressed and untiled — at 0.0003° a CONUS-scale run implies a multi-hundred-gigabyte scratch file, which suggests this has only ever been run at regional scale. And despite the README stating that gdal.sh “builds tiles for MMGIS,” there is no gdal2tiles, pyramid or XYZ step anywhere in the repo: the directory is merely named tiles/ and the chain stops at one COG per (group, freq).

Correction to a common assumption

spectral_util mosaic stack-glts is not temporal aggregation. It is a first-wins gap fill — to_copy = (glt[...,2] == 0) & (converted[...,2] > 0) — which only writes into cells that are still nodata, in input order. Mode-through-time does not exist in SpectralUtil today. The real temporal logic lives in amd stack, which is a separate package that is not vendored in this monorepo and lives only in a shared micromamba env on the cluster. We cannot currently read it. Getting that source from James is a Phase 0 blocker, not a nicety.

Read that table as a unification, not a fork. Both are reductions over a stack of observations. V002 uses a reducer that happens to be decomposable, so it can be fused into the regrid loop for free. AMD uses a reducer that is not, so it must materialize the stack. One framework can express both if the plugin declares which kind it is.

02The core abstraction

Five stages. The cached marker is the load-bearing part: everything before the cost function is deterministic geometry and never needs to run twice.

1
Plan unit: run Lambda

Manifest → granule index query → frozen candidate set → work list of (tile, epoch, block). Applies granule-level filters and enforces the budget guardrail. Emits a manifest hash that identifies the run forever.

↓
2
Regrid unit: granule × tile Lambda or Batch

KD-tree nearest-neighbour from granule loc to tile grid → GLT COG. Pure geometry: depends only on the granule footprint and the grid definition. Content-addressed and cached indefinitely — changing a cost function never invalidates it.

↓
3
Resolve unit: tile × epoch × block Lambda or Batch

Apply the GLTs for this block, run the Scorer plugin, collapse the observation stack into one epoch snapshot plus a score band and a contributing-observation count. This is where a science team’s code runs.

↓
4
Reduce unit: tile × block Lambda or Batch

Collapse the epoch snapshots through time via the Reducer plugin — mode-through-time for Critical Minerals — emitting the value, a spread/agreement measure, and the epoch count. A no-op reducer reproduces V002.

↓
5
Publish unit: tile Lambda

Stitch blocks → COG / CF-NetCDF, write the STAC item and provenance record, register MMGIS layers. Provenance carries the manifest hash, the plugin versions and the frozen granule list.

Why the split at stage 2/3 is the whole design

Stage 2 is the expensive part (KD-tree over ~1.6M granule points against ~11M grid points) and the part that never changes. Stage 3 is the cheap part and the part scientists want to change hourly. V002 welds them together; AMD accidentally separates them. Separating them deliberately is what turns “try a different selection rule” from a full rebuild into a re-read of cached GLTs.

03Five hooks, not one

“A generic cost function class” is the right instinct, but collapsing every decision into one hook would be a mistake: the decisions a mosaic makes have wildly different cost profiles and run at different stages, and putting them behind one interface would force the cheapest to pay the price of the most expensive. Keep them separate, and let the manifest compose them. The first four decide which observation wins; the fifth decides what the result looks like.

GranuleFilter
Runs against the index, before any pixel is read. Date range, cloud fraction, solar zenith, orbit, quality flags, footprint overlap. This is where the temporal range limits live. Rejecting here is free; rejecting later is not.
per granule
~microseconds
PixelMask
Per-pixel validity from co-registered mask products — cloud, cirrus, water, spacecraft quality — plus Dana’s additions (snow, high vegetation). Produces a boolean; does not rank. Applied during regrid so masked pixels never enter the stack.
per granule×block
vectorized
Scorer
The cost function proper. Ranks the observations that survive the mask and picks a winner per cell within one epoch. Replaces criteria_band/criteria_mode. Declares whether it is streaming or needs the whole stack.
per tile×epoch×block
vectorized
Reducer
Collapses epoch snapshots through time. Mode-through-time, median, percentile, trend, agreement/spread. Always needs the full epoch stack, but that stack is small — one snapshot per epoch, not one per granule.
per tile×block
N = #epochs
OutputMapper
Runs at publish time, not selection time. Turns finished bands into the rendered image consumers actually look at — enum→colour, continuous ramps, confidence-driven alpha. Declared in config for the ordinary cases, a callable for the elaborate ones. Emits its legend as a sidecar.
per tile
presentation only

Note what this taxonomy buys immediately: the “limits on temporal range” requirement is a GranuleFilter in the manifest, not pipeline code. EMIT-AMD applies no temporal filter: pipeline.sh invokes amd query -lat … -lon … with no date arguments, so every observation ever acquired over the bin is handed downstream. (Whether amd query offers a date option is not knowable from this repo — only which flags are used. The design is deliberate either way: AMD treats time-slicing as the stacker’s job.) For a versioned annual product the range still has to be declared, pinned and recorded, which is what putting it in the manifest achieves.

04The cost-function contract

Two protocols, both vectorized over a block, both handed an accessor for pulling in whatever other geo-tagged data they need. The capability attribute is what lets the planner choose an execution mode.

stratum/contracts.py 
class Scorer(Protocol):
    """Rank observations within one epoch; higher score wins."""

    # "streaming" -> fused into regrid, O(block) memory, V002-style
    # "stack"     -> needs every observation at once, O(block x N)
    capability: Literal["streaming", "stack"]

    def score(self, obs: ObsWindow, aux: AuxAccessor) -> FloatArray:
        """Return (H, W) float32. NaN marks a cell this observation
        may not occupy. Called once per granule when streaming,
        once with a stacked (N, H, W) ObsWindow otherwise."""


class Reducer(Protocol):
    """Collapse per-epoch snapshots into the delivered product."""

    outputs: tuple[BandSpec, ...]   # declared up front, drives the COG schema

    def reduce(self, snaps: SnapshotStack, aux: AuxAccessor) -> dict[str, Array]:
        ...

What a plugin actually sees

ObsWindow is the thing that makes a cost function readable. Bands are addressed by role name, not index, so a scorer is portable across instruments — the manifest maps roles to bands per collection:

Reimplementing the V002 criterion as a plugin 
class MinViewZenith:
    """V002 parity: the most nadir look wins."""
    capability = "streaming"

    def score(self, obs, aux):
        return -obs["view_zenith"]        # negate: higher wins


class CleanestNadir:
    """Nadir-preferring, but penalise steep terrain and any pixel
    that a snow index says was covered on the acquisition date."""
    capability = "streaming"

    def score(self, obs, aux):
        s = -obs["view_zenith"] / 90.0
        s -= 0.5 * (aux.raster("s3://.../copernicus-slope.tif") > 30)
        s[aux.raster("s3://.../snow/{date}.tif", date=obs.granule.date) > 0] = np.nan
        return s

AuxAccessor is the “helper methods to access data” layer, and it is where most of the framework’s value sits. Every call returns an array already windowed to this block, already reprojected onto this block’s grid, and cached for the life of the worker: 

aux.raster(uri, date=None)   # windowed COG read via GDAL range requests
aux.vector(uri, field=...)  # GeoParquet/GeoJSON, rasterized to the block
aux.table(uri).at(date)     # time series lookup, nearest or interpolated
aux.dem()                   # conveniences for the common ones
aux.granule_index           # the frozen index, for stack-level reasoning

Open science question this design surfaces

Phil’s open question — “mode over mineral ID directly, or over something continuous first?” — becomes a choice between two Reducer implementations rather than a pipeline fork. So does the tie-break policy at low observation counts. That is the payoff of the whole abstraction: the argument moves into a 40-line class that two people can read in a meeting.

Registration and discovery

Plugins register through standard Python entry points, so stratum plugins list can enumerate what a given image or wheel provides, and the manifest refers to them by name:

cleanest_nadir  = "stratum_emit.scorers:CleanestNadir"

[project.entry-points."stratum.reducers"]

05Blocks: the scaling move

AMD’s deferred-reduction design is the right one scientifically, and it is why AMD asks Slurm for 32 GB, 4 CPUs and up to 24 hours per 1° bin. Ported naively to AWS, that is a large, long, expensive Batch job per tile — and a single failure late in the job throws away everything.

The fix is to make the unit of work a block rather than a tile. A 1° tile at 0.0003° is 3334 × 3334; a 512 × 512 block is 1/42 of it:

Materialized stack, per unit1° tile512×512 block
Cells11.1 M0.26 M
× 100 observations × 10 bands × float32~44 GB~1.0 GB
Observations actually intersecting the unitalla subset
Fits a 10 GB Lambda?noyes
Blast radius of one failurewhole tile1/42 of a tile

Three things fall out at once. The materialized reduction fits in a serverless worker, so the Lambda instinct becomes viable exactly where it was previously impossible. Parallelism goes up by a factor of ~40, which matters because a Distributed Map can hold 10,000 child executions in flight. And retries get cheap, which is what makes Spot capacity safe to use for the jobs that do need Batch.

The catch, stated honestly

Block decomposition is only sound for reducers that are spatially local — each output cell depends only on the observations over that cell. Mode, median, percentile and count all qualify. Anything with a spatial term does not, and this is not hypothetical: the existing regrid already contains one. remove_negatives(clean_contiguous=True) runs a 3×3 convolve2d over the interpolated-pixel mask and zeroes any cell with three or more flagged neighbours — a stencil that reads one pixel beyond the block edge and would produce visible seams if applied block-wise without overlap.

So the framework must let a plugin declare halo: int and materialize that overlap itself, and anything genuinely global — segmentation, connected components — declares capability = "tile" and routes to Batch. A seam-equivalence test belongs in CI from the first commit: block-wise output must be bit-identical to tile-wise output on a fixture.

06Caching geometry

Every artifact is written to a content-addressed key derived from a hash of the inputs that actually determine it. Nothing else. This is what makes iteration cheap, and it is worth being pedantic about which inputs go into which key:

ArtifactKey derived fromInvalidated by a new scorer?
GLT
granule × tile		 granule_id, grid_def, max_distance, regrid_algo_version No
Masked observation
granule × tile × block		 glt_key, asset_roles, pixel_mask_spec No
Epoch snapshot
tile × epoch × block		 obs_keys[], scorer_ref, scorer_version, params Yes
Product block
tile × block		 snapshot_keys[], reducer_ref, reducer_version, params Yes

So the iteration loop the science team cares about — change the scorer, rerun — skips stages 1 and 2 entirely and re-reads GLTs that are already sitting in S3. Changing only the reducer skips stage 3 as well. The first run over a zone is expensive; the twentieth is not, which is the property that decides whether people actually iterate.

Precedent

This is a principled version of something the team already does by hand: pipeline.sh carries a steps=([query]=1 [apply-glt]=1 [classify]=1 [stack]=1) toggle map so an operator can skip work they know is still good. Content addressing makes that decision correct automatically instead of relying on the operator remembering what changed.

A useful side effect: because the GLT cache is keyed on the granule and the grid, two different projects on the same grid — Critical Minerals and AMD, say — share it. The second project’s first run is nearly free over ground the first has already touched.

06aOutput mapping

The artifact people actually look at is an image. A mineral class is not meaningful on screen until something turns it into colour, and that mapping is a genuine part of the product — it is argued over, versioned, and tuned far more often than the algorithm underneath it. It deserves a first-class hook rather than being buried in the writer.

The rule that keeps both audiences

The mapper is a presentation layer over a data product that still ships. Stage 5 writes the class indices, counts and agreement bands and the rendered image, from the same block, in the same run. The image is what MMGIS serves; the data is what makes the archive re-usable. AMD’s difficulty was not that it rendered colour — it is that rendering was the only thing it emitted, so nothing downstream could restyle or recount.

Config for the ordinary cases

Most mappings are a lookup table or a ramp, and should never require code. These are declared in the manifest and validated at plan time, so a bad domain or a missing class is caught before compute is provisioned rather than after: 

outputs:
  mineral_id:
    mapper: categorical
    classes: "@ref:lumping/cm-v1.yaml"   # id-keyed, not positional (§01)
    colors:
      pyrite:    [220,   5,  12]
      goethite:  [174, 118, 163]
    nodata: transparent
    alpha_from:                     # confidence drives opacity
      band: agreement
      domain: [0.3, 0.8]
      range: [60, 255]

  band_depth:
    mapper: continuous
    ramp: viridis
    domain: [0.0, 0.15]
    clip: true

alpha_from is worth calling out. It generalizes what AMD did by hand — alpha 0 for nodata — into something more useful: low-agreement pixels fade rather than asserting a confident colour they have not earned. For a mode-through-time product where support varies enormously with revisit, that is close to a requirement, and it is exactly the kind of thing that is painful to retrofit once rendering is hard-coded.

A callable for the elaborate ones

The escape hatch is the same plugin mechanism as the other four hooks, so a mapper is versioned, entry-point registered, and hashed into provenance like anything else: 

class OutputMapper(Protocol):
    outputs: tuple[ImageSpec, ...]

    def render(self, bands: BandStack, aux: AuxAccessor) -> RGBAArray:
        """(H, W, 4) uint8. Free to consult any finished band, not just one."""

    def legend(self) -> Legend:
        """Class table or ramp stops. Written as a sidecar and into STAC."""

That covers the cases config cannot express: blending two minerals where they co-occur, hillshading the classification against a DEM pulled through aux, or rendering a bivariate map of class against confidence.

Non-negotiable

legend() is not optional. Every rendered product ships its class table or ramp stops beside it — as a sidecar and in the STAC item. That single requirement is what prevents Stratum from recreating the situation where the only record of what a colour means lives in a config file on someone’s cluster account.

06bAncillary data on other grids

A cost function will want data that has nothing to do with EMIT’s grid — a DEM, a snow index, a landcover raster, mining-claim polygons. The framework’s job is to make that a non-event, and one rule does most of the work:

The contract

The block grid is the contract. Everything AuxAccessor returns is already windowed to the block, already on the block’s exact grid and CRS, and already cached. A scorer never does geometry, never sees a CRS, and never resamples anything. If a plugin author has to think about projections, the framework has failed.

Readers dispatch on shape

Source shapeOperationMust be declared
Raster, different CRS or resolutionWarp to the block gridResampling — bilinear/cubic for continuous, nearest or mode for categorical
Vector polygons or linesRasterize, burning an attributeWhich field; all-touched vs centroid
Swath or irregular pointsKD-tree — the same path as stage 2Max distance
Date-keyed table, no geometryScalar lookup; no gridding at allNearest vs interpolated
The failure that does not throw

Resampling method must be declared, never defaulted. Bilinear-interpolating a landcover class or nearest-neighbouring a DEM are both wrong, and neither raises an error — they just quietly produce a cost surface nobody can explain later. Categorical and continuous aux data must be distinguishable in the manifest, and the reader should refuse to guess.

Warp once, slice many

A DEM is static; naively warping it per block per epoch per granule would re-do the same work thousands of times. Aux sources are therefore warped once per (source, tile, grid), content-addressed exactly like a GLT (§06), with blocks reading windows out of the cached result. The cost of an aux source is paid on first touch and never again.

Declare aux in the manifest

Sources are declared up front rather than reached for at runtime, which buys three things: the planner can validate they exist and are readable before provisioning compute; it can prefetch and warp them in stage 1; and their identity can be hashed into the cache key.

Why the declaration is load-bearing

A scorer that quietly opens an undeclared raster produces a cache key that lies. Swap that file and every cached snapshot is silently stale, with no signal that anything changed. The accessor should therefore refuse undeclared URIs outright rather than trusting plugin authors to remember — a small restriction that protects the reproducibility guarantee everything else rests on.

07The run manifest

One declarative document is the entire interface for driving a run. It is versioned in git, reviewed like code, hashed into provenance, and — critically — it is not Terraform. Terraform owns the platform; the manifest owns the science. Confusing the two is how platforms become unusable by the people they were built for.

Budget as a first-class field

The budget block is not decoration. The planner Lambda computes the real fan-out — tiles × epochs × blocks × granules — before any compute is provisioned, compares it against the declared ceiling, and on exceedance parks the execution on a Step Functions task token awaiting human approval. A one-character typo in a date range is otherwise a five-figure mistake, and it is exactly the kind of mistake this pipeline invites: the difference between one zone and the globe is one line of YAML.

The same planner emits a dry-run report — tile count, granule count, estimated bytes read, cache hit rate, estimated vCPU-hours — which should be the default behaviour of stratum plan and the thing reviewed in a PR alongside the manifest diff.

Borrowed from AMD

amd config print -c base.yml -p "mosaic<-v6<-filter-fit" composes a config from a base plus an ordered patch chain. That layering instinct is good and the manifest should keep it: stratum plan -m base.yaml -p zones-pilot -p scorer-v3, so a variant is a patch, not a copied file that drifts.

08AWS topology

The instinct to reach for Step Functions is right, and the stateful features that make it right are real: Distributed Map (up to 10,000 concurrent child executions, reading its work list straight from an S3 object rather than from the 256 KB state payload) and Variables + JSONata, which let a run carry its manifest hash and cache keys across states without a chain of Pass states.

The instinct to make the engine a Lambda is right for three of the five stages and wrong for the two that matter most. The honest recommendation is a split plane.

Control plane

Step Functions + Lambda

Planning, index queries, fan-out, cache probes, stitching, STAC registration, approval gates. Seconds of runtime, hundreds of MB of memory, thousands of invocations. Lambda is the correct and cheapest answer here, and this is where the serverless story genuinely pays.

Data plane

AWS Batch on EC2 Spot

Regrid, resolve, reduce. Minutes-to-hours, gigabytes of memory, GDAL and netCDF4 in the image. Spot with Graviton where the wheels exist; block-level retries make interruption cheap. The same container image runs locally and on the cluster.

One image, two executors

Do not pick between Lambda and Batch statically. Build one container image with both an AWS Lambda Runtime Interface Client entrypoint and a plain CLI entrypoint, then let the planner route each work item on measurable properties: 

def route(item, plan) -> Literal["lambda", "batch"]:
    if plan.scorer_capability == "tile":        return "batch"
    if item.est_peak_bytes  > 7 * GB:            return "batch"
    if item.est_seconds     > 600:               return "batch"   # 15 min hard ceiling
    if item.est_bytes_read  > 8 * GB:            return "batch"
    return "lambda"

A pilot zone at block granularity routes almost entirely to Lambda and finishes in minutes with no infrastructure warm-up — which is the outcome the serverless instinct is reaching for. A global reprocessing campaign routes to Batch and runs on Spot at a fraction of the Lambda price. Same code, same image, same manifest.

The state machine

Nested Distributed Maps keep the payloads small: the outer map fans out over tiles, the inner over blocks, and each child receives a pointer into S3 rather than the work item itself. 

Plan            # Lambda: manifest -> frozen index -> work list -> S3
BudgetGate      # Choice: within budget? else -> ApprovalWait (task token)
RegridMap       # Distributed Map over (granule x tile), ItemReader = S3 JSONL
  └─ CacheProbe -> Regrid            # skipped entirely on hit
EpochMap        # Distributed Map over epochs
  └─ BlockMap   # nested Distributed Map over (tile x block)
       └─ Resolve
ReduceMap       # Distributed Map over (tile x block)
PublishMap      # Distributed Map over tiles: stitch, COG, STAC
Finalize        # provenance record, run report, notification
Constraints to design around, not discover later

Distributed Map’s ItemReader and ResultWriter require S3 buckets in the same account and region as the state machine — which, given the data lives in us-west-2 (§10), pins the whole deployment there. Child execution input is capped at 256 KiB regardless of how large the item source is, so items must be keys and hashes, never inline geometry or band lists. And Standard workflows bill per state transition: at hundreds of thousands of blocks that is a real line item, which argues for Express child workflows on the inner maps.

09Packaging & Terraform

Lambda layers will not work here — but the ergonomics can

A zip-based Lambda layer is capped at 250 MB unzipped across all layers. GDAL plus netCDF4 plus scipy plus numpy does not fit; community GDAL layers land around 150 MB before any of our own code, and SpectralUtil pulls gdal>=3.0.0, netCDF4<1.7.1, scipy, pyproj, spectral and earthaccess. Container image Lambdas allow 10 GB, and that is the only viable path for this dependency stack.

But the reason layers are appealing is real: a scientist should be able to change a cost function without rebuilding and pushing a container image. Get that ergonomic without the layer:

Iteration path

Plugin wheel from S3

The manifest names a wheel URI. The worker fetches and installs it into /tmp at cold start, then resolves the scorer through entry points. Edit → stratum plugins publish → rerun, in about ninety seconds. The wheel hash goes into the cache key and the provenance record, so a run is still exactly reproducible.

Production path

Baked into the image

For delivered products, the plugin is pinned in the image and the wheel-fetch path is disabled by policy. Reproducibility comes from an immutable image digest rather than a mutable bucket object. The manifest records which mode was used.

What Terraform owns

Many experiments, one deployment

Running five competing cost functions at once is a manifest concern, not an infrastructure concern. Terraform stands up one run-agnostic deployment; a run is a manifest plus a run_id that becomes an S3 prefix and a Step Functions execution. Five experiments are five executions on shared infrastructure — no second terraform apply, no duplicated queues.

The cache makes this pay

Because GLTs are content-addressed on (granule, grid) and carry no dependence on the scorer, every experiment over the same zone shares one GLT cache. The first run pays for the geometry; the second through fifth skip stages 1–2 entirely and re-read it. Comparing cost functions is the cheapest thing the system does, which is precisely the behaviour we want to encourage.

Practical guardrails: tag every Batch job and Lambda invocation with run_id so cost allocation is per-experiment; set MaxConcurrency per execution so one run cannot starve another on a shared queue; and give outputs a run_id prefix while the cache stays shared. Reach for a second deployment only on a real boundary — a separate account for delivered products versus experimentation, or a different region — never for an experiment.

Stratum should wrap, not fork. The KD-tree regrid is good code and Phil owns it. 10Data access reality

This section exists because it contains the two findings most likely to derail a schedule, and both are invisible from the architecture diagram.

The delivered L2B mineral product cannot be read at all

Blocker — verify this first

spec_io.open_netcdf dispatches on filename substrings and has readers for EMIT rdn, rfl, obs and l2a_mask, plus the airborne sensors. There is no reader for the L2B mineral products — searching spec_io.py for l2b, min, abun or mineral returns nothing, so an EMIT_L2B_MIN_*.nc falls through to raise ValueError(f'Unknown file type for {input_file}').

AMD never hit this because it reads cluster ENVI .img files, which take the extension-based branch and need no product-specific reader. A cloud pipeline consuming the delivered NetCDF cannot. Writing open_emit_l2b_min_nc is a small, concrete, early deliverable — and it must be reconciled with the L2B output contract now moving in tetracorder-lite PR #14, or the two will diverge immediately.

While in there: substring dispatch ('emit' in name and 'rfl' in name) is fragile in a pipeline that stages files into cache-keyed paths. Stratum should pass the product type explicitly from the manifest’s role declaration rather than relying on a filename surviving the round trip through S3.

S3 is closer than it looks

The good news is that this is a shallower problem than a first pass suggests. spec_io.py contains no s3, boto3, fsspec or /vsis3/ references — but the NetCDF and TIFF paths go through libraries that already speak object storage. What actually blocks remote access is two guards: 

# spec_io.load_data, first statement in the function
if not os.path.exists(input_file):
    raise FileNotFoundError(f'{input_file} not found.')

# and every mosaic CLI argument
@click.argument('glt_file', type=click.Path(exists=True))

So the sequencing is: stage-in shim now, streaming later. The shim downloads the assets a work item needs to ephemeral disk, calls the existing code unmodified, and uploads the result — Lambda offers up to 10 GB of /tmp, Batch whatever the instance has. It costs wall-clock and forces whole-file reads, but it works immediately and is the right first move. Relaxing those two guards so GDAL and netCDF4 can stream via /vsis3/ then turns a block-level read into a range request over the pixels it actually touches, which is the property that makes cloud-native raster processing economical. That is worth contributing upstream rather than working around.

One caveat to carry: write_cog builds the whole output raster through GDAL’s in-memory MEM driver before writing, so output size is bounded by worker RAM. Blocks (§05) keep that comfortable; whole-tile writes at 0.0003° would not be.

Path resolution cannot be a port of convert_fids.py

convert_fids.py maps FIDs to ENVI paths under /store/emit/ops/data/acquisitions/{date}/{name}/{lvl}/ with the build version b0106_v01 hard-coded in a module-level dict. None of that survives the move: ENVI header/binary pairs have no meaning in object storage, and the layout is cluster-specific.

Replace it with a role resolver over the granule index. The manifest declares mineral → (EMITL2BMIN, mineral_id); the resolver returns an asset URI plus the variable within it, and the build version becomes an indexed field that a GranuleFilter can pin — which is also how a reprocessing campaign gets pinned to a specific build instead of a hard-coded string.

Replace the coverage GeoJSON with a frozen index

Both existing pipelines select granules by scanning a coverage_pub.json. In V002 that file is fetched, if not supplied, straight off the MMGIS load balancer: 

wget -O {coverage_save_file} \
  https://earth.jpl.nasa.gov/emit-mmgis-lb/Missions/EMIT/Layers/coverage/coverage_pub.json

Each feature carries properties.fid, start_time/end_time, Total Cloud Fraction, and a polygon ring. subset_from_coverage.py then applies ROI, time and cloud filters as three sequential passes, each of which deepcopys the entire coverage document and rebuilds a Shapely Polygon per feature. Phil left a vectorized pandas implementation commented out directly above the loops, so the cost was clearly known. There is no STAC or pgSTAC anywhere in the repo.

Three problems, in increasing order of seriousness. It is slow — a linear scan plus three full deep copies over a file that grows with the mission. It is irreproducible — AMD refreshes the file whenever it is over 24 hours old, so the same manifest run on two days silently selects different granules and nothing records which. And the archival L3 product’s granule selection depends on a viewer service’s web endpoint being up and current, which inverts the dependency Background.md is careful to draw between L3 and MMGIS.

Silent data loss in the cloud filter

The cloud filter drops any feature whose properties lack the key entirely: 

if 'Total Cloud Fraction' in feat['properties'] and \
   feat['properties']['Total Cloud Fraction'] <= max_cloud_fraction:
    subdir['features'].append(feat)

A granule with a missing cloud-fraction record is therefore excluded from the mosaic with no warning, no count, and no way to distinguish “too cloudy” from “unlabelled.” Any GranuleFilter in Stratum must report its exclusions by reason into the run report, and missing metadata must be an explicit policy choice in the manifest rather than an accident of a truth-test.

So stage 1 should materialize the candidate set into a GeoParquet index frozen into the run — granule id, footprint, datetime, cloud fraction, build version, asset URIs, quality flags — queried with DuckDB spatial (which reads directly from S3 over range requests, with no server to operate) and hashed into provenance. A run then names exactly the granules it consumed, forever; the scan becomes a columnar predicate pushdown; and the dependency on an MMGIS endpoint disappears.

11Where this diverges from the sketch

Four places where the research pushed back on the starting proposal. Recording them explicitly, because the reasoning matters more than the conclusions.

Diverges

“The main engine is a Lambda”

Right for planning, stitching and cataloguing; wrong for the reduction. Lambda caps at 15 minutes and 10 GB, and AMD asks for 32 GB and up to 24 hours per 1° bin. But block decomposition (§05) shrinks the unit until Lambda does fit — so the answer is a router, not a choice.

Diverges

“Custom Lambda cost functions”

A cost function evaluates per pixel inside a vectorized loop; a Lambda invocation per pixel is six orders of magnitude too coarse, and shipping the observation stack to a separate function destroys the data locality that makes any of this affordable. The cost function must run in-process. What the Lambda-layer idea is really reaching for is fast iteration without an image rebuild — delivered by the plugin wheel in §09.

Refines

“A single output raster series mapped to a GLT”

True of V002, false of AMD, which builds one GLT per granule and keeps them all. The GLT is better understood as a regrid operator than as the mosaic itself; selection is a separate reduction that may or may not be fused into it. That reframing is what makes temporal aggregation expressible at all.

Adds

Terraform scope

Terraform for layers was the starting thought; the dependency stack rules layers out entirely (§09). Terraform still earns its place — ECR, Batch, Step Functions, IAM, budgets — but it must stay out of the science parameters, or every experiment becomes an infrastructure review.

One thing the sketch got exactly right and worth restating: the principles across the three lineages really are the same, and the leverage really is in tooling that makes the mosaic flow easy to implement so the science team iterates on a cost function. That framing survived contact with the code intact — the corrections above are all about where the seams go, not whether they exist.

12Cost & sizing

These are estimates, not measurements

Every number below is derived from stated assumptions, not from a run. Granule counts per tile in particular are guesses about ISS revisit over specific ground and could be off by 3× either way. Phase 0 exists to replace this table with measured numbers, and no commitment should be made against it.

Assumptions: one 1° pilot tile at 0.0003°; 4 years; monthly epochs (48); ~100 granules intersecting the tile across the mission; L2B MIN + MINUNCERT + L2A MASK + L1B OBS staged, no reflectance.

That is the argument for the cache boundary in §06, and it is the number Phase 0 should actually go and measure — specifically, the wall-clock and byte count for one tile, which sizes everything else.

Levers, in rough order of impact

  • Stay in us-west-2. Egress on a reflectance-scale campaign dwarfs compute.
  • Cache GLTs across projects. Shared grid means AMD and Critical Minerals amortize the same geometry.
  • Spot for Batch. Block-level retries make interruption cheap enough to take the discount.
  • Express workflows on inner maps. Standard-workflow state transitions add up fast at hundreds of thousands of blocks.
  • Intermediate lifecycle rules. Epoch snapshots are reproducible; expire them on a short clock. Keep GLTs, which are expensive and immortal.
  • Skip reflectance unless a scorer asks for it. At ~1.8 GB/granule it is the single largest input; make it opt-in per manifest.
  • Actually use the cores you pay for. AMD requests --cpus-per-task=4 but hardcodes --n_cores 1, which is what feeds KDTree.query(..., workers=n_cores) — the compute-bound inner loop — and its per-granule loop is strictly serial. Three of four CPUs idle through the entire regrid phase. Before buying bigger workers, check the parallelism already available.
What the 32 GB is really buying

Probably not the KD-tree. write_cog materializes the full tile array, then a GDAL MEM copy, then overview levels before CreateCopy — so peak memory scales with tile area, not swath size or granule count. That is a strong independent argument for blocks (§05): shrinking the output unit attacks the term that actually dominates, which is why a block-wise worker can be small even when AMD’s tile-wise one could not.
