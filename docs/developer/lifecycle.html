Lifecycle of a run

From stratum run to the last COG: which function calls which, where the process boundaries fall, and what has to cross them.

Algorithms follows a number from sensor to map. This page follows control: the call stack, the files written between stages, and the one contract that holds the whole thing together.

1. Two kinds of process

Everything Stratum does happens in one of two roles, and the difference is absolute.

The plannerA worker
RunsOnce per runOnce per work item — thousands of times
Entryplan_runexec_item
ReadsThe manifest, the index, and a handful of real granulesplan.json, one work list line, and the assets that line names
DecidesEverything: tiles, epochs, granules, plugins, schema, class lumping, fan-outNothing. It executes a decision already recorded
WritesThe run directoryOne cache artifact, and one outcome line
The rule that follows from this

A worker must be able to reconstruct everything it needs from plan.json plus the installed code. It never re-derives a decision, never queries the catalogue, and never consults the manifest's intent — only the planner's resolved answer. If you find yourself wanting a worker to look something up, the thing to change is what the planner writes down.

2. stratum run, in call order

cli.run                                        # cli.py
├─ executor_available("local")                 # refuses slurm/aws in this slice
├─ plan_run(manifest, out, patches)            # plan/run.py — section 3 below
│    └─ writes {run_dir}/…

     │      └─ ProcessPoolExecutor(spawn)
     │           └─ exec_item(run_dir, stage, i)   # executors/worker.py

     └─ Finalize: STAC collection, provenance.json, report.md

With one worker run_stage calls exec_item in-process rather than submitting to a pool — deliberately the identical function, so a debugger, a profiler or a stack trace sees the real thing. It is the first thing to reach for when a worker fails inexplicably.

3. What planning decides, in order

plan_run is about two hundred lines of sequence, and the order is load-bearing.

#StepWhy here
1Load and merge the manifest, then validate_staticEvery check that needs no data happens before anything is opened
2Resolve grid, tiles, epochs, delivery periodsPure arithmetic on the manifest
3Resolve a reader per collection; pick the geolocation roleA missing reader must be a plan refusal, not a worker traceback
4Build the index if absent, then check its recorded scope covers this manifestA wider AOI or time window than the index was built for is a rebuild, not a silent short answer
5Query, pin collection versions, apply granule_filterMetadata only; no pixel has been read
6Drop granules that meet no tile, then granules lacking a role's assetThe AOI is its tiles, not the box around them — a granule in the gap between two distant zones can be read by no work item, so it must not be frozen, counted or budgeted
7Freeze the survivors to index.parquet and hash the fileThe candidate set is now immutable for the life of the run
8The budget gateBefore the data-dependent checks, because against a catalogue source those download real bytes, and a run that is going to be refused must not pay for one
9inspect_granules: open real granules, resolve band aliases, resolve per-granule class lumping, check table vintagesThe only place the planner touches pixels; staged assets become cache hits for the run
10Validate outputs against the resolved schemaA render that cannot work should fail now, not after regrid has run for an hour
11Build the PlanContext, then the four work listsThe fan-out is now fully determined
12Write plan.json, the work lists, and report.mdEverything a worker will ever need is now on disk
Step 8 before step 9 is not an accident

Swapping them would make an over-budget plan download granules before refusing. The comment at plan/run.py:776 says so explicitly; treat it as a constraint on any reordering.

The run directory

{root}/runs/{run_id}/
  manifest.merged.yaml       # the document that was hashed
  index.parquet              # the frozen candidate set
  plan.json                  # every resolved decision
  work/regrid.jsonl          # one work item per line
  work/regrid.results.jsonl  # one outcome per item, from the executor
  work/resolve.jsonl   …
  report.md                  # dry-run report, extended by the executor
  provenance.json            # written by Finalize

Beside it, and not inside it, are the two shared stores: {root}/cache/, which is content-addressed and survives across runs, and {root}/products/{run_id}/, which is what you ship. A run directory is disposable; the cache is not.

4. The four work lists

A work item is one JSON object on one line, and it is the entire input to a worker besides plan.json. build_work_lists emits all four in a single pass over the tiles.

StageItemOne perEmitted when
regrid{granule_id, collection, asset, uri, tile}granule × tilethe granule's bbox meets the tile
resolve{tile, epoch, block}tile × epoch × blockthe block meets the AOI and at least one granule is a candidate for that epoch
reduce{tile, block, period, epochs}tile × block × delivery periodat least one of the period's epochs produced a resolve item — and it lists exactly those
publish{tile, period}tile × delivery periodat least one reduce item exists for it

Two details in that table carry weight:

  • The scorer's halo widens the candidate test, not the output. build_work_lists reads halo off the scorer instance and tests candidacy against the haloed block, so an observation that only reaches the halo still produces a resolve item. The snapshot is still written for the core window.
  • A reduce item lists its epochs explicitly. An epoch with no candidates has no snapshot, so "every epoch in the window" would name files that were never written. Listing the epochs that actually resolved is what lets the reduce handler treat a missing snapshot as a hard error instead of a normal case.

5. Inside a worker

exec_item(run_dir, stage, index)
├─ load_cached(run_dir)              # plan.json → RunPlan, cached per process
├─ read_work(run_dir, stage)[index]
├─ HANDLERS[stage](item, run)        # regrid_item | resolve_item | reduce_item | publish_item
└─ {index, stage, ok, key, hit, seconds}

The outcome record is the whole worker API: an executor appends it to work/{stage}.results.jsonl and stratum status reads nothing else. A failure is folded into the same record shape — ok: false with the error and traceback — so a crashed item is queryable rather than lost.

HandlerReadsWritesCode
regrid_itemThe geolocation asset, only on a missOne GLT GeoTIFFworker.py:52
resolve_itemGLT windows, then every contributing granuleOne snapshot directoryworker.py:105
reduce_itemThe listed epochs' snapshotsOne product-block directoryworker.py:127
publish_itemEvery product block of the tile × periodCOGs, RGBA images, legends, a STAC itemworker.py:153

publish_item is the one handler that reads a work list rather than only its own item: it re-reads work/reduce.jsonl to find the blocks belonging to its tile and period. That is the seam where per-block output becomes per-tile output.

6. The key-agreement contract

This is the single most important internal invariant, and the reason the stages can be sequential processes that never speak to each other.

Every consumer recomputes its producer's key

Nothing is passed between stages. A stage that needs an input derives the content address that input would have, from the same plan.json the producer used, and looks it up. If the two derivations ever disagree, the consumer sees a miss for an artifact that exists — so both sides deriving identically is a correctness requirement, not an optimisation.

ConsumerRecomputesThrough
resolveEach candidate granule's GLT keyglt_key_for
reduceEach listed epoch's snapshot key — candidates, GLT window hit test and all, without resolving anythingsnapshot_key
publishEach block's product keyproduct_key

Two guards make a divergence loud rather than silent:

  • regrid_item derives the GLT key itself and compares it against the key regrid_granule_tile actually wrote to, raising if they differ — worker.py:100. Without it, a drift between the two derivations would look like "resolve never hits the cache".
  • regrid_item also refuses outright when the plan was made under a different REGRID_ALGO_VERSION than the installed build — a stale plan against new geometry code is a re-plan, not a rerun.

Why a partial write can never read as a hit

CacheRoot.hit requires both the artifact and its .inputs.json sidecar. Both write paths commit the artifact first and the sidecar last — a file via os.replace onto the key path, a directory by filling a sibling temp directory and renaming it whole. A worker killed mid-write leaves either nothing or a temp name, never a half-artifact that the next run would trust.

7. Failure paths

RaisedMeansSurfaces as
PlanErrorThe manifest, the data or the index make the run impossibleA clean CLI message; nothing is written
BudgetExceededFan-out exceeds the manifest's budget and on_exceed is not warnExit 2, with the plan and report still written so you can see why
FileNotFoundError from a handlerAn upstream stage did not run for this itemOne failed outcome record, naming the missing key path and the stage to run
ExecutionErrorOne or more items of a stage failedThe stage stops the run; up to ten failures listed, plus the first traceback in full
FilterErrorA granule_filter met missing metadata under on_missing: failWrapped into a PlanError — a policy decision, not a traceback

Locally a run is all-or-nothing: any failed item stops it. The tolerated-failure percentage of spec 08 §4 is a later slice. Outcomes are written either way, so stratum status --failed can answer afterwards.

Later slices

The SLURM and AWS executors, stratum approve at a paused budget gate, and --from-provenance re-runs all resolve to the same exec_item seam and the same work lists. What changes is the dispatcher above them, not anything on this page below section 5.
