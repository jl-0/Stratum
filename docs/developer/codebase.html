Codebase map

Two packages, an acyclic layer graph, and fifty-odd modules. What each one owns, what it is allowed to import, and where to look first.

The Guide explains what Stratum does and Algorithms writes out the arithmetic. This section is about the shape of the source tree: which module holds which decision, which object crosses which boundary, and what breaks if you put something in the wrong place.

Who this section is for

Someone about to change Stratum itself — add a stage, a reader, an executor, or track down why a cache key moved. If you only want to write a cost function, you want Writing plugins instead; nothing on these pages is needed to author a hook.

How to read this section

Links in a Code column open the file on GitHub at the line that defines the symbol, on main. Each carries the text of the line it claims, and tests/test_docs_links.py:48 re-reads the file, so a link that has drifted onto the wrong line fails the suite rather than quietly misleading you. Line numbers may be a little stale between runs; the symbol name is always right.

1. Two packages, one boundary

The wheel installs two top-level packages, and the split is the most important structural fact about the repository:

PackageContainsMay know about
src/stratum/The framework: grids, tiling, indexing, caching, the stages, the executors, the CLIImaging spectroscopy in the abstract. Never EMIT, Tetracorder, minerals, or any instrument
src/stratum_emit/The EMIT plugin package: NetCDF readers, instrument masks, mineral scorersEverything about EMIT, and only the public types of stratum

The dependency runs one way and only one way. stratum_emit imports exactly one thing from the framework — stratum.types — and nothing in stratum imports stratum_emit at all. The two packages are joined at run time by entry points declared in pyproject.toml, never by an import.

This is what makes Stratum re-targetable

A different instrument is a different plugin package beside stratum_emit, with no framework change. The moment an import stratum_emit appears under src/stratum/, that stops being true — which is why a test asserts it does not. See Extension wiring for how the two halves actually meet.

2. The layer graph

Within stratum, package-level imports form a directed acyclic graph eight levels deep. Nothing at a level imports anything at the same level or above it.

LevelPackageImports from
0types, plugins— nothing in the repository
1hooks, cache, classes, time, index, reduce, accesstypes (and plugins, for access)
2regrid, publishlevel 0–1
3resolve, manifestlevel 0–2
4filtershooks, manifest, plugins
5planeverything below
6executorsplan and the four stages
7cliexecutors, plan, and the rest

Three consequences worth internalising:

  • types is the universal leaf. Around thirty modules import it and it imports nothing of ours. Adding a dependency to types.py makes that dependency universal, so it takes an argument to justify.
  • The four stages do not import each other. regrid, resolve, reduce and publish are siblings that meet only in plan (which builds the work lists) and executors (which dispatches them). Stage-to-stage coupling goes through the cache, not through Python.
  • plan is the widest module and that is deliberate. Planning is where every decision is made once, written down, and then never re-made; the breadth of its import list is the price of a worker that only has to read JSON.

What each module owns, and the symbol to open first.

Core

The four stages

ModuleOwnsStart at
regrid/Pure geometry: sensor loc arrays to a GLT by KD-tree, or a product's own embedded lookup table adopted onto the run's lattice. Also the recorded module hash that guards the algorithm version.regrid_granule_tile
resolve/The block read path, masks, the gather, scoring, and the streaming argmax that produces one epoch snapshot. The densest package in the tree.resolve_block
reduce/The schema-driven built-in reducer: vote, best, and the continuous aggregations, plus the derivation of which bands a schema delivers.reduce_stack
publish/Stitching blocks into a tile, data COGs, colour resolution, RGBA rendering, legends, STAC items and collections, and the run record.publish_period

plan/document.pyThe serialisation seam: plan.json, the work lists, and the paired *_to_doc / *_from_doc functions that let a worker rebuild a planner's context from plain JSON.RunPlan

The spec is authoritative, the code is not

When the two disagree, the spec wins and the code is a bug — unless the code was changed deliberately, in which case the spec edit is part of that change, not a follow-up. See CLAUDE.md for the full keep-them-in-step rule and the spec → site map.
