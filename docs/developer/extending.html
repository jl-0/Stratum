Extension wiring

How a string in a manifest becomes an object in a worker, what identity that object carries into a cache key, and what it takes to add a new kind of thing.

Writing plugins teaches the five science hooks from the author's side. This page is the mechanism underneath: the registries, the resolver, the binding, and the checklists for extending the framework rather than plugging into it.

1. Seven registries, one resolver

Every extensible thing in Stratum is an entry-point group, and they are declared in one dictionary: plugins.py:12.

KindEntry-point groupContractShipped here
scorerstratum.scorersScorer4, in stratum_emit.scorers
maskstratum.masksPixelMask4, in stratum_emit.masks
reducerstratum.reducersReducernone — the built-in schema reducer is not a plugin
mapperstratum.mappersOutputMappernone — the config mappers are built in
filterstratum.filtersGranuleFilternone registered — the built-ins are named by keyword
readerstratum.readersGranuleReader4, keyed by EMIT collection name
sourcestratum.sourcesGranuleSourcelocal and cmr

The three that ship nothing are not oversights. A Reducer or OutputMapper plugin is only needed for what the schema vocabulary and the config mappers cannot express, and the built-ins deliberately cover the ordinary cases without anyone writing code. The group exists so that the uncommon case has somewhere to go.

Readers and sources are not science hooks

They sit in the access tier because a new instrument or a new archive does not change what a mosaic means. Keeping them out of the five-hook list is what keeps that list short enough to learn.

2. From a manifest string to a live object

A ref is an entry-point name when one is registered, and a module:Class path otherwise. Both forms work everywhere, which is what lets you develop a plugin before packaging it.

"prefer_bare_earth"                      # registered entry point
"my_lab.scorers:SnowAware"               # module:Class, nothing installed
manifest.scorer.ref
    │  resolve(kind, ref)              # plugins.py — entry point first, then module:Class
    ▼
  the class
    │  instantiate(kind, ref, params)  # plan/run.py — constructor gets the params verbatim
    ▼
  the instance
    │  PluginBinding(ref, version, params, instance)
    ▼
  ctx.scorer  ──plugin_to_doc──▶  plan.json  ──plugin_from_doc──▶  ctx.scorer in every worker
StepDoesCode
resolveEntry-point name first, then module:Class; a LookupError names both attempts, so a typo does not read as "no plugins installed"plugins.py:28
instantiateCalls the class with the manifest's params as keyword arguments. No adaptation layer: a plugin's constructor signature is its parameter schemaplan/run.py:341
PluginBindingPairs the instance with the three things that enter a cache key: the ref as written, the distribution version, the paramscontext.py:109
Round tripA worker re-instantiates from {ref, params} but keeps the version the planner recordeddocument.py:189

Resolution happens at plan time for every kind. A plugin that cannot be imported, or whose constructor rejects the manifest's params, is a plan refusal — validate_static instantiates each named plugin precisely so that stratum validate catches it without touching data.

3. Version identity, and what "unversioned" costs

A plugin's version enters the cache key, so Stratum has to determine it from an arbitrary object. plugin_version tries three strategies in order:

  1. Look the object's top-level package up in the installed distributions' metadata.
  2. Failing that, try a distribution named the same as the top-level package.
  3. Failing that — the editable-install case, which records no top-level list — find the distribution whose direct_url.json source directory actually contains the module file, checking the package directory specifically so that a test or example under the same source tree does not match.
A plugin that resolves to "unversioned" is a cache hazard

Its cache keys stop distinguishing versions, so editing the plugin's code without changing its ref or params leaves stale artifacts looking like valid hits. The long-term answer is a content hash beside the version (spec 06 §3 rule 3); until then, install plugin packages with real metadata, and treat "unversioned" in a .inputs.json as a warning rather than a detail.

What each plugin kind contributes to a key

KindEntersSo changing it rebuilds

That last row is the load-bearing one. A reader is expected to produce the same array from the same bytes; if a reader change alters values, the cache will not notice. Reader changes that affect data are a deliberate cache concern and belong with a discussion of spec 06, not a silent merge.

4. Adding a reader

A reader owns band meaning and is where sentinel fills die. The four EMIT readers subclass EmitNetCDFReader, which is a convenience, not a requirement — the contract is the GranuleReader protocol.

  1. Implement open, variables, read, and geolocation; add glt if the product ships its own lookup table and class_table if it carries categorical classes.
  2. Declare space — "sensor" or "ortho". The planner picks the geolocation role by asking each reader for this, so getting it wrong misroutes the whole regrid stage.
  3. Return masked arrays. Every sentinel the format uses must already be masked before the value leaves the reader; nothing downstream knows what -9999 means.
  4. Honour the SensorWindow, origin included. A reader that ignores it and returns the whole scene is correct but slow; one that treats the window as a shape is wrong.
  5. Register it under the collection name in [project.entry-points."stratum.readers"]. A manifest can override the choice per collection via inputs.readers.

L2BFrcov is the instructive example: an already-orthorectified product, so it overrides read and reports no geolocation at all.

5. Adding a source

A source runs at index build and never during a run. That constraint is what makes a run reproducible: the catalogue is consulted once, the answer is frozen, and the run reads the frozen file.

  1. Implement search, assets, and checksums. Return GranuleRecord objects — source-shaped, not schema-shaped; the translation to index rows belongs to row_from_record.
  2. Carry the source's metadata through verbatim. Promoted columns are the ones the index schema names; everything else lands in attributes stringified, which is what lets a filter like MaxSolarZenith work without the framework knowing what solar zenith is.
  3. Report checksums when the catalogue has them, and honestly report none when it does not — LocalSource records none rather than inventing them.
  4. Register under [project.entry-points."stratum.sources"] and add the kind to source_from_manifest.

6. Adding a stage

Rarer, and a bigger change. There are six places a stage exists, and missing one gives a confusing failure rather than a clean one:

What to addWhere
1The stage name, in pipeline orderSTAGES
2An artifact kind, if it writes to the cacheARTIFACT_KINDS and a *_inputs function beside it
3A work list, with the fan-out rule that decides when an item existsbuild_work_lists
4A handler returning (key_or_path, hit)HANDLERS
5A key function the next stage can call to recompute this stage's output address without doing the workbeside the handler — snapshot_key and product_key are the models
6The CLI's --stage choices, and the docscli.py:150, Commands

Item 5 is the one people skip. Without it the next stage has to either trust that its input exists or do the producing work to find out — and both defeat the key-agreement contract that lets stages run as independent processes.

7. Adding an executor

The least invasive extension of the three, because the seam was designed for it. An executor's whole job is to call exec_item(run_dir, stage, index) once per item and collect the outcome records.

  • Add the name to EXECUTORS so executor_available stops refusing it.
  • Dispatch the items of one stage however the platform prefers — a SLURM array task and a Lambda invocation both reduce to stratum exec --plan … --stage … --index N.
  • Write work/{stage}.results.jsonl in the same shape. stratum status and stratum report read nothing else, so they keep working for free.
  • Honour the budget gate before dispatching anything.

Nothing about a stage handler, a cache key or a plugin changes. That is the payoff for insisting that a worker takes only a run directory, a stage name and an integer.

8. Inspecting what is installed

stratum plugins list                   # every registered plugin, by kind
stratum plugins list --kind scorer
stratum plugins show prefer_bare_earth # resolve a ref and print what it declares
stratum plugins show my_lab.scorers:SnowAware

show accepts either ref form and resolves it the same way a manifest would, which makes it the fastest check that a plugin is visible to the environment a run will use — usually the real answer when a LookupError appears at plan time.
