Objects & ownership

Which object is constructed by whom, how long it lives, whether it can be mutated, and which ones have to survive a trip through JSON.

Type reference says what each type is and what fields it carries. This page is about lifecycle: the questions you hit when changing the code rather than using it.

1. One leaf, thirty dependents

types.py holds every object that crosses an interface and imports nothing else from the repository. Around thirty modules import it, including both EMIT plugin modules. That makes it the one file where a change is guaranteed to be felt everywhere, and the one file where adding a third-party dependency makes that dependency universal.

The rule this implies

A type belongs in types.py when more than one package has to name it. A type used inside a single package — Resolved, ObsContext, Gathered, ResolveItem — stays in that package, however central it feels there.

Four lifetimes, and knowing which one an object has tells you most of what you need.

The process-lifetime row is worth dwelling on. load_cached memoises the RunPlan per run directory in a module-level dict, and reader_for memoises one reader instance per (collection, ref). So parsing plan.json, instantiating plugins and scanning entry points happen once per process, not once per item — which is what makes a pool of long-lived workers chewing through thousands of small items affordable.

Readers must therefore be stateless between files

One reader instance serves every granule of its collection in that process. Anything a reader needs to remember about a particular file belongs in the ReaderContext it returns from open(), never on self. Both caches have a clear_cache() for tests; neither has one for production, on purpose.

3. PlanContext — the worker's whole world

PlanContext is what a resolve worker needs that is not in the work item. Every field is either plain data or an already-constructed plugin instance — deliberately, so that the planner and a freshly-spawned worker can build equivalent ones from the same files.

Its __post_init__ is the cheapest correctness gate in the codebase. It refuses a name that is both a role and a band alias (one namespace), an alias naming an unknown role, a mask that declares neither sensor nor map space, and a scorer whose capability is not streaming. All four fail at context construction — in the planner, before a single work item exists.

4. The observation objects

Reading one granule over one block builds a short chain, and the interesting part is where sensor space becomes block space.

ObsContext        plan + block + epoch + granule + glt_key + glt window
    │  read_observation
    ├─ SensorWindow.covering(glt_x, glt_y)     # the sensor rectangle the GLT names
    ├─ reader.read(rctx, var, sensor_window)   # per role
    ├─ ObsWindow(space="sensor", …)            # only if sensor masks exist
    ├─ gather(arr, glt, sw, ok) → Gathered     # the one place the spaces meet
    ├─ ObsWindow(space="block", …)             # what the scorer and map masks see
    └─ Observation(obs, layers)                # + per-layer values, already remapped
ObjectSpaceNote
SensorWindowsensorCarries its origin, not just a shape. A sensor-space mask that needs the absolute cross-track column — EdgeTrim — is wrong without it
ObsWindowbothOne class, two forms; the difference is one axis. space is explicit and checked, never inferred from shape
GatheredblockThe output of the only function that touches both spaces
ObservationblockThe block ObsWindow plus each schema layer's values, with categorical remapping already applied
Resolvedblock, coreThe streaming argmax over every observation, trimmed from the haloed window to the core

Two ownership facts that are easy to get wrong:

  • Remapping happens at the gather, not at the reducer. Raw class keys become product ids inside read_observation, where the granule is still known — because the lookup is per granule. By the time values reach a snapshot they are already in the product's own enumeration, and a granule whose raw key the remap does not describe has been marked invalid.
  • The halo is carried through resolve and dropped at the end. BlockRef has two windows on purpose: window includes the halo, core_window does not. Everything is computed on the haloed window and sliced to the core before writing. Only the core enters the snapshot key — the halo, by invariant, never changes output.

5. Snapshot and product objects

ObjectIsHanded to
SnapshotSchemaOne declaration per run of what a snapshot holds; carries layers_hash and aggregate_hash separatelyEverything downstream of resolve

BandStackFinished bands for one tileAn OutputMapper
BandSpecOne delivered band: name, dtype, nodata, units, descriptionThe COG writer and the STAC item

The two hashes on SnapshotSchema are split because they invalidate different things. layers_hash says what a snapshot contains, so it keys snapshots; aggregate_hash says how layers collapse through time, so it keys product blocks. Changing an aggregation method rebuilds products and reuses every snapshot — which is the whole point of separating them.

6. Frozen, and the eleven that are not

Thirty-eight dataclasses in the tree are frozen=True; eleven are not. The frozen ones are the default and need no explanation. The exceptions are worth knowing, because each is mutable for a reason:

ClassWhy not frozen
PlanContext, RunPlanAssembled field by field and held live handles (a CacheRoot, an AssetStore); freezing would buy nothing since they are never shared across threads
Resolved, Observation, ObsContextShort-lived carriers of NumPy arrays. Freezing a dataclass does not freeze the arrays inside it, so it would be a promise the type cannot keep
GLT, EmbeddedGLTSame reason — array wrappers
RemapHolds a NumPy lookup array indexed by raw key

The pattern: freeze anything that is identity or configuration; do not pretend to freeze anything whose payload is an array.

7. The serialisation seam

plan/document.py is the only module that knows how a live object becomes JSON and back. Every conversion is a pair, and the pairing is the point: a round trip has to produce an object that computes the same hashes.

Three of these carry a check rather than a plain rebuild, and those checks are the ones to respect when editing:

  • schema_from_doc refuses when the rebuilt layers_hash does not match the one recorded in the document. A schema that round-trips to a different hash would silently orphan every snapshot the run already wrote.
  • class_table_to_doc writes columns as lists, because the fingerprint is taken over the values — so a table rebuilt from the document fingerprints identically.
  • plugin_from_doc re-instantiates from {ref, params} but carries the version the planner recorded. A worker with a differently-versioned plugin installed would otherwise compute different keys from the same plan.
The test for adding a field to plan.json

If a worker needs it, it goes in PlanContext and gets a *_to_doc/*_from_doc pair. If only reporting needs it, it goes in the plan document beside the context, not inside it — context_to_doc deliberately carries every field its docstring lists and no more.
